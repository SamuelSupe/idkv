# v0.10.1 并行负载与故障恢复资格验证

本轮针对当前引擎源码 `87d9a1a`，使用未开启 failpoints 的 release 程序。验证分为持续并行负载和独立存储故障两组；结果仅适用于记录的配置、负载与环境。

该轮发现的写入尾延迟问题，后续定位、备份进度优化与新的前后对比另见[尾延迟优化记录](tail-latency-optimization.md)。本页保留优化前资格验证的原始数据。

## 2026-11-06 实测结论

本轮数据正确性、后台任务推进、重启及三类存储错误恢复检查通过。**并行阶段的写入尾延迟明显增加，不能据此宣称满足任意生产 SLA 或租户尾延迟隔离要求。** 负载组在新加坡时间 12:00 开始，完成 120 + 600 + 120 秒前台负载及后续排空/恢复校验；存储故障组在负载结束后单独运行，没有与正式性能窗口混跑。

成功台账共记录 **49,544 个批次、691,944 次文档写操作**（包含种子和对既有主键的更新）。停止写入后，主从各自的 20,200 条当前文档与台账重放结果逐条一致，重启前后正文和原 `_rev` 指纹一致，已确认数据缺失和不一致均为 0。最终备份导入另一个新 Store 后，20,000 条主租户文档亦通过检查点模型核对。

另行恢复了一份**持续写入期间生成的备份**，checkpoint sequence 为 38,546；按该位置截取成功台账后，恢复的 20,000 条正文、原修订号与覆盖索引全部一致。此后这 20,000 个主键都发生过成功更新，故该检查验证了历史检查点内容，而不仅是文档总数。原始证据见[并行备份恢复校验](../bench-results/production-qualification-20261106/load/concurrent-backup-restore.json)。最终停写备份的位置为 40,823，两份恢复各自使用自己的位置模型。

### 后台进展、资源与重启

- combined 的约 595 秒采样窗口内，主租户刷盘约 1.96 GB、合并写约 9.53 GB、合并读约 11.49 GB；同一窗口 GC 回收计数增加 27,696。相关任务有实际 I/O 和位置推进。
- combined 的采样峰值：主节点引擎计费内存 72,067,194 字节，进程 RSS 102,014,976 字节，文件描述符 369；主租户 L0 最高 22 个文件，低于本轮 stop=24。采样未见维护错误。
- GC 到期滞后的采样峰值为 **25,033 ms**，不能描述为全过程无积压。停止新增历史后最终排空，`next_expiration_ms=null`、`expiration_lag_ms=0`，主租户累计回收 33,533 条元信息/历史记录。当前发布仍可读，旧发布明确拒绝；目录中只剩 assets、probes 与当前发布集合，共 3 个集合。逻辑排空不等于所有历史物理字节已经释放。
- 备份在 checkpointing 阶段时 SIGKILL 双节点。重启至可写探针成功并且副本追平耗时 **75.032 ms**；该任务之后恢复为 completed。两个节点均通过重启前成功数据模型核对。该耗时不包含人工发现或基础设施故障，也不代表冷物理设备恢复速度。
- recovery 的 553 次 BUSY 是恢复中的旧备份占用租户任务槽时，新管理操作每 20 ms 有界重试产生的计数，不是 553 次业务写入失败。实际集成应处理单租户备份串行契约，可使用更长退避，避免密集轮询。
- 采样区间估算写放大 `(WAL + flush + compaction write) / document bytes` 分别为 7.32、6.95、6.94。窗口未包含最后一次采样后的全部尾部合并，不可作为完整稳态成本或性能提升结论。

## 验证方法

运行环境为 OrbStack Ubuntu Linux AArch64、Rust 1.90、18 个可见 CPU、约 31 GiB 主机内存。数据、备份和成功回执台账均位于 `/var/tmp` 的 Btrfs 虚拟磁盘，非 tmpfs。虚拟机共享宿主资源，未设置 CPU 或进程 RSS cgroup 上限，未清空 OS 文件缓存。

每节点引擎全局计费内存预算 512 MiB，每租户 128 MiB，缓存 8 MiB、memtable 2 MiB、目标 SST 4 MiB、level base 16 MiB、4 个 I/O worker，L0 stop 为 24。主从位于同一 VM，使用回环 HTTP。备份使用独立 fs 仓库目录、16 MiB/s 流式限速和完整校验，和在线库共用虚拟磁盘。

较小的 64 MiB 租户预算预演中，活跃备份与全量读取重叠曾返回 `RESOURCE_EXHAUSTED`；备份任务本身预留 48 MiB，不能把剩余空间全部留给块缓存而忽略正文、索引和响应。正式测量选择 128 MiB，预演数值不混入性能表，也没有据此确定最低生产内存要求。读取准入失败保留游标，校验按原请求有界重试。

主租户预装 20,000 条文档，每条带 4 KiB 确定性高熵 payload；另有 200 条小文档的轻量租户。两者分别有唯一覆盖索引和 Lookup。先强制刷盘、合并种子数据并让副本追平，再开始计时。

| 阶段 | 目标时长 | 同时运行的工作 |
|---|---:|---|
| baseline | 120 秒 | 持续写入、后台刷盘/合并、主从复制、从库查询 |
| combined | 600 秒 | baseline 工作，加 20 秒历史保留/GC、每 5 秒发布一个新数据集、反复创建/完整校验/保留清理备份 |
| restart | 按实际测量 | 后台备份任务仍活跃时 SIGKILL 两节点；原目录重启、恢复复制、验证写就绪和业务写入，逐条核对两边数据 |
| recovery | 120 秒 | 重启后的 combined 工作负载，核对持续服务能力 |
| drain/restore | 按实际测量 | 等待 GC 排空、检查副本位置和发布版本、创建并校验最终备份，导入独立 Store 后对照成功回执模型 |

负载为闭环限速客户端：主租户每秒目标 40 个批次、每批 20 条更新，即 800 条文档更新/秒；轻量租户目标 20 次单文档更新/秒。从库 Get、20 输入 Lookup、20 条覆盖索引查询分别以 200、100、50 次/秒发起。慢请求会降低实际发起速率，不累积无限排队；这些数据不是最大吞吐或开放到达率测试。

每个阶段保留每次成功请求的延迟样本，输出 P50/P95/P99、实际完成速率、错误与准入重试次数。写延迟包含文档准备、凭据刷新及有界背压重试；客户端 Python、JSON 和 TCP 开销也在观测范围内。每 5 秒记录引擎、复制、GC、备份活动和两节点 RSS/文件描述符等状态。

后台并行的验收以实际观测为准：同一采样区间内必须同时看到刷盘字节、合并写字节、GC 回收数和从库位置增长，并且备份活动标记为真。仅有任务配置或线程启动不算通过。基线同样运行复制与合并，combined 主要增加备份、历史回收与版本发布；阶段顺序、数据历史和缓存状态不同，因此阶段差异不代表单一功能的独立因果开销。

## 已确认数据与恢复契约

客户端在收到成功响应后，将租户、全部主键、generation、原修订号/history、操作 ID 和延迟写入独立台账。每个租户只有一个写线程，顺序明确；按台账重放得到每个主键最后一次被确认的状态。后续合法覆盖不要求旧业务正文永久保留。

每个校验点检查主从全部当前文档、原回执 `_rev`、完整分页、MultiGet、覆盖 Lookup 和引擎完整性；重复、额外、缺失或错误正文均使验证失败。读负载还检查同一批次更新的 20 个键在快照内 generation 一致，覆盖索引不回读正文。

GC 必须在停止生产新历史后排空到 `next_expiration_ms: null`，保留当前文档和当前发布版本；过期发布版本必须明确失败。复制最终必须追平且没有不可用租户。最终备份恢复按 checkpoint sequence 截取台账模型进行核对，不把检查点后的合法回退当作持久化缺陷。

## 独立存储故障注入

三个场景均先创建、确认并校验 2,000 条文档与覆盖索引。故障批次使用 8 个新主键、固定 operation ID 和原 history。故障后再尝试另一批写入，验证引擎保持未知提交隔离；解除故障后 SIGKILL、重启，核对原成功数据。

| 场景 | 注入方式 | 验收边界 |
|---|---|---|
| enospc | 新建专用 256 MiB ext4 loop 文件系统，实际分配填充文件直到可用空间为 0 | WAL 写入收到真实 `ENOSPC`，不涉及填满宿主/其他项目的磁盘；清理后重开恢复 |
| wal-write-eio | 仅对指定节点根目录下 WAL fd 的 write/writev/pwrite64 返回 `EIO` | 错误到达真实 release 写路径，留下 fd 路径和注入日志，未知提交后拒绝继续确认 |
| wal-sync-eio | 对相同范围 WAL fd 的 fsync/fdatasync 返回 `EIO` | 不将同步失败当作确定未提交；重启后先观察未知批次可见性，再用原请求安全重试 |

EIO 使用独立编译的 `LD_PRELOAD` 测试 shim，不修改或开启引擎 failpoints，不注入其他进程、普通文件或网络 socket。它验证系统调用错误传播，不模拟设备控制器、真实掉电或谎报 fsync 成功。故障批次重启后只能完整存在或完整不存在；原请求幂等重试取得确定成功回执后才加入成功模型。

这些磁盘/I/O 场景是独立边界验证；并行负载组中的故障是活跃备份期间的双进程重启。本轮未将真实磁盘写满或 EIO 与长时间并行负载全部组合注入。

## 复现

以下命令在 OrbStack Linux 中从项目根目录执行。根目录必须是新目录，且位于磁盘文件系统。资格脚本只操作自己创建的进程和目录；存储故障脚本需要已有 gcc、ext4/loop 工具与免密 sudo，并在退出时卸载和解绑自己创建的 loop 设备。

```sh
CARGO_TARGET_DIR=/var/tmp/idkv-qualification-build cargo build --locked --release --bin tenant-kv --bin tenant-kv-restore
python3 -B scripts/qualification.py \
  --binary /var/tmp/idkv-qualification-build/release/tenant-kv \
  --restore-binary /var/tmp/idkv-qualification-build/release/tenant-kv-restore \
  --root /var/tmp/idkv-qualification-new
python3 -B scripts/qualification_faults.py \
  --binary /var/tmp/idkv-qualification-build/release/tenant-kv \
  --root /var/tmp/idkv-qualification-faults-new
```

短预演可收紧 `--baseline-seconds`、`--combined-seconds`、`--recovery-seconds` 和 `--rows`，但缩短到 GC 或五路并行尚未发生时，脚本会按验收条件失败。正式测量不要并行运行构建或其他压力测试。

本轮覆盖单机虚拟环境中的有限时长资格检查；真实硬件掉电、跨主机网络分区、真实云 S3、长于本轮的内存/磁盘趋势和目标生产硬件仍需独立验收。

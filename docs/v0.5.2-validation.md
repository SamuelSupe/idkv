# v0.5.2 性能与稳定性验证

验证日期：2026-11-05。本轮修复两个可复现的严重缺陷，优化主键读取，保留一主一从异步复制及现有 HTTP、WAL、SST 格式。发行包提供的 Linux AArch64 服务与恢复工具未启用故障注入。

## 严重缺陷及修复

| 问题 | 后果与修复 |
|---|---|
| P1：删除 journal 发布结果不确定，内存注册表仍为 Active | 原实现可以重新打开租户并确认新写入，而磁盘上的 Deleting journal 会在重启后删除该租户。现在先关闭内存中的入口，再尝试持久发布；失败后租户保持 UNAVAILABLE，close 不能解除，必须重开 Store 恢复 |
| P1：未验证接任资格就持久停写 | 对端误配为同集群主库时，切换失败，原主已经持久 fenced。现在首次停写前校验集群、角色、节点、来源历史和不可用租户；不合格时原主保持可写。已经持久停写的中断仍按原凭据重试，不自动解除停写 |

两个回归用例先在原实现上复现失败：[删除错误后仍确认写入](../bench-results/v052-delete-reproduced.log)、[无效接任导致原主停写](../bench-results/v052-switch-reproduced.log)。删除故障通过在 journal 已成功持久发布后返回错误来模拟“发布可能已完成”的错误边界，不是实际设备掉电测试。

修复后验证删除失败时不能打开或关闭后重开受影响租户；健康租户仍可创建集合；重启完成删除且保留健康租户。复制状态将待恢复生命周期列为 unavailable，从库保留已有副本；待恢复租户不能被忽略后生成计划切换的最终位置。该状态输出与拒绝停写在同一故障回归中验证；已有源端 unavailable 租户保护测试覆盖从库保留副本及健康租户继续同步。

## 主键读取优化

Get/MultiGet 不再每次读取并 JSON 解码集合定义。每个租户实例只保留最近一个集合名称和 UUID，按名称长度加 128 字节计入租户与全局预算，准入失败则跳过缓存。它不加载查询索引目录、不缓存文档结果；普通写入不失效，DDL 通过 catalog_seq 失效，旧快照读取自己的集合身份，迟到读者不能覆盖较新缓存。

回归覆盖：预热后删除集合返回 NOT_FOUND；同名重建后 Get/MultiGet 不返回旧文档；旧快照、新快照及删除期间快照分别解析各自身份。已有恢复、冷实例关闭、租户隔离和复制测试继续通过。

## 前后性能测量

在同一 OrbStack Ubuntu AArch64 VM、18 个可见 CPU、约 31.36 GiB 内存、btrfs 虚拟块设备及回环网络上，分别构建 v0.5.1 和最终 v0.5.2。两边使用完全相同的 [read_perf.rs](../examples/read_perf.rs) 和 [replication_perf.rs](../examples/replication_perf.rs)，每版本每负载三轮、每轮新目录；测量期间没有同时执行本轮编译、持续负载或 HTTP 验收。[环境](../bench-results/v052-environment.json)、[完整汇总](../bench-results/v052-perf-summary.json)、[原始结果集合](../bench-results/v052-perf-raw.json)。

读取基准先装载 10,000 个含 512 字符负载的文档，刷盘、合并并预热。Get 反复读取同一个键；唯一查询使用单个等值条件；Lookup 每批 1,000 个输入。每模式目标 3 秒且最多 200,000 次调用，因此 Get 和唯一查询实际少于 1 秒。以下均为三轮中位数，适用于该短时热读取场景，不是生产 QPS 或冷缓存承诺。

| 模式 | v0.5.1 调用/秒 | v0.5.2 调用/秒 | v0.5.1 P99 | v0.5.2 P99 |
|---|---:|---:|---:|---:|
| 热点 Get | 938,320 | 1,174,835 | 1.416 μs | 1.209 μs |
| 唯一索引查询 | 606,179 | 613,036 | 2.084 μs | 2.125 μs |
| 256 成员 IN、扫描 10,000 行 | 79.09 | 76.61 | 14.30 ms | 20.70 ms |
| 1,000 键 Lookup | 1,000.82 | 1,001.30 | 1.179 ms | 1.698 ms |
| 1,000 个重复键 Lookup | 3,998.65 | 4,062.22 | 0.308 ms | 0.288 ms |

热点 Get 吞吐增加 **25.21%**，P50 从 **0.959 μs 降至 0.750 μs**，P99 降低约 **14.62%**。本轮没有修改通用扫描或 Lookup 执行器；这些场景部分尾延迟测量更高，不能据此宣布全面提速，也不能仅凭路径未改动就排除回退。未建立宿主机负载隔离和长期稳定的尾延迟置信区间。

复制基准为 8,192 个积压事务、1,024 个反复更新的键、一个热点和一个轻量租户、唯一覆盖索引、50 ms 空闲轮询。开始计时前已完成检查点初始化，追赶时读取从库 Lookup。

| 指标，三轮中位数 | v0.5.1 | v0.5.2 |
|---|---:|---:|
| 8,192 事务追赶 | 223.69 ms | 212.57 ms |
| 复制追赶事务/秒 | 36,621 | 38,538 |
| 热点租户完成 I/O 作业 | 96 | 91 |
| 轻租户可见延迟 | 2.83 ms | 6.83 ms |
| 从库 Lookup P99 | 189 μs | 747 μs |

从库 Lookup P99 三轮范围为旧版 **64–206 μs**、新版 **694–1,391 μs**。每轮仅有 **65–99 个查询样本**，P99 接近最大观测值，不能作为稳定的生产 P99；测量仍显示需要继续调查的尾延迟问题。本轮未增加自适应复制限速，也未以降低持久化强度换取性能。追赶时间的轻微差异同样不被表述为确定的复制优化收益。

## 实际进程与兼容性

正式二进制的双进程示例通过检查点初始化、两个租户的正文与索引一致性、从库只读、断线追赶、双向计划切换、持久角色重启和外部停止旧主后的显式故障升主。[正式运行](../bench-results/v052-pair-release.log)

故障注入二进制通过：从库合并追加 WAL 时截断最后一个事务并中止进程；旧主刚持久停写即崩溃；新主已持久升主但尚未响应即崩溃。重启后恢复完整事务、追平、验证覆盖 Lookup，重试切换完成。[故障运行](../bench-results/v052-pair-faults.log)

使用 v0.5.1 正式二进制为初始主库、v0.5.2 正式二进制为初始从库，初始化、增量、A→B/B→A 切换、重启及显式故障升主全部通过。[混合版本](../bench-results/v052-pair-mixed.log)

HTTP、DSL 及 OpenDAL fs 备份/校验/恢复/保留清理通过；OpenAPI 3.1 校验通过，版本 0.5.2，44 个路径、48 个 schema。[HTTP](../bench-results/v052-native-http-smoke.json)、[DSL](../bench-results/v052-http-smoke.json)、[OpenAPI](../bench-results/v052-openapi-validation.json)

## 三分钟多租户持续负载

使用现有 [soak.rs](../examples/soak.rs) 运行 180 秒：8 个活跃租户、32 个冷租户、8,000 个约 1 KiB 驻留文档、每集合 3 个索引、2 个写线程和 16 个读线程。写线程每次原子更新 20 条，读线程读取并周期性核对 MultiGet 批次一致性和唯一索引，读循环间隔 1 ms。全局引擎预算 512 MiB、每租户 64 MiB。

- 完成 **1,500,800 次文档更新、1,207,717 次 Get**；没有返回读写错误或预算拒绝，采样未见维护错误。这里是重复更新 8,000 个文档，不是百万条驻留数据验证。
- 四个热点读线程 Get P99 为 **81–86 μs**，其余轻租户线程为 **12 μs**。
- 引擎计费内存峰值约 **34.13 MiB**，独立采样 Linux VmHWM 为 **60.40 MiB**。预算不等同进程 RSS。
- 结束后刷盘、完整合并和 SST 校验通过；重新打开 8 个活跃租户，核对 **8,000 个文档及非唯一索引结果**；32 个冷租户自动关闭后重新打开读取正确。

这一阶段同时运行了前述进程功能验收，不能用其吞吐与旧版持续负载结果直接计算性能增益。[汇总](../bench-results/v052-soak-summary.json)、[完整时序](../bench-results/v052-soak.jsonl)、[RSS](../bench-results/v052-rss.json)。

## 复现与未验证部分

从项目目录运行，示例数据目录须不存在：

```sh
cargo test --locked --features failpoints -- --test-threads=1
cargo clippy --locked --all-targets --features failpoints -- -D warnings
cargo fmt -- --check
cargo build --locked --release --example read_perf --example replication_perf --example soak
target/release/examples/read_perf /var/tmp/tkv-read-run 10000 3
target/release/examples/replication_perf /var/tmp/tkv-replication-run 8192
target/release/examples/soak /var/tmp/tkv-soak-run 180

cargo build --locked --release --features failpoints --bin tenant-kv
python3 scripts/replication_demo.py --binary target/release/tenant-kv --root /var/tmp/tkv-fault-run --faults
cargo build --locked --release --bin tenant-kv --bin tenant-kv-restore
python3 scripts/replication_demo.py --binary target/release/tenant-kv --root /var/tmp/tkv-normal-run
```

本轮是有边界的正确性和短时稳定性验证，不能证明不存在其他严重缺陷或内存长期增长。未验证真实设备掉电、独立主机/机房故障、长期网络分区、百万/千万条驻留数据、大于内存的负载或真实 AWS S3。异步复制仍只在主库本地持久化后确认成功；显式故障升主必须外部隔离旧主，并接受尚未复制事务可能丢失。扫描、批量 Lookup 和集中追赶的尾延迟仍需长期、隔离负载下的调查与优化。

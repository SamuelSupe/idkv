# 第二轮深度审查修复与验证（2026-11-07）

基线 `d1ca7e20fc95af3e309314e7e8a5dafa28c01727`。[原审查四项复现](../bench-results/deep-audit2-20261107/summary.json)保持不变；本轮证据归档于 [deep-remediation2-20261107](../bench-results/deep-remediation2-20261107/)。

## 修复

1. **复制全局内存。** 接收缓冲按容量预留，扩容同时覆盖新旧缓冲，去掉按每个网络 chunk 四倍累计的预留及随分块数量增长的预留对象列表。解析前单独预留 JSON 树；解析结束释放原始输入，只保留结果树预算。接收、解析和回放都识别单页自身超过全局预算的情况，使用已有的有界检查点初始化；其他租户占用造成的瞬时全局压力仍按资源错误重试，不自动重放未知 WAL 提交。回放同时计算已经持有的响应树与原始帧/记录预算。
2. **缩容可用性。** 主库先关闭无活动句柄的实例，在新预算下试开 WAL 并校验存储，不修改原配额上限和元数据；新预算不够则保留原配额。副本可能尚未刷盘已在主库刷盘的数据，因此先用旧预算刷盘，再进行同一预检，保留复制日志保留策略。缩容预检包含存储扫描，可能耗时，应停止该租户新流量后执行。长时间预检只关闭本租户入口，不持有节点角色屏障或 slot 锁；发布前按节点、slot 顺序重新取锁并验证角色，避免切换请求等待时阻塞全节点写入。预检成功后才发布新配额；发布发生不确定 I/O 错误时隔离该租户，重开 Store 读取持久结果。
3. **创建发布和回收。** 新库在 staging 完成，通过已有 registry v4 的 Restoring journal 发布目录和 Active 注册。创建中断后，启动完成有日志的创建，回收未发布 staging；不新增格式或协议版本。发布错误期间保留待确认状态，名称不会被重复创建，副本不会误认作已删除；重开 Store 判定结果。旧版本未注册目录仅在持有目录锁并确认没有 checkpoint、SST、WAL 帧时回收；有数据、结构不明或符号链接的目录保留，活跃引擎不会被删除。
4. **并发备份暂存。** 按 job UUID 跟踪预留量；实际工作区已经覆盖的部分不重复计费，超出预留的部分继续计入。没有活跃预留覆盖的失败/中断工作区仍占用预算，forget 后释放。不会以忽略实际文件的方式放宽暂存上限。

## 回归边界

- 64 MiB 全局预算下，40 MiB 租户、16 个覆盖索引、512 KiB HTTP 写入可直接增量同步；60 MiB 租户、768 KiB 写入在单页超预算时自动切到检查点，最终内容与 `_rev` 一致。
- 未刷盘 700 KiB 已确认文档的租户尝试从 8 MiB 降到 2 MiB，缩容被拒绝；原配额、内容、修订号在重开 Store 后保持。另用阻塞 I/O 验证预检期间切换快速返回 BUSY、角色不变且租户入口在结束后恢复。另覆盖主库已刷盘而副本保留超过 2 MiB 内存/WAL 时的配额同步，避免目录同步反复拒绝该租户。
- 创建在 staging、持久 journal、最终 Active 发布三个位置中止，连续重开 Store 两次，确认原租户完整，新库按持久阶段存在或回收。控制目录不可写时连续八次创建失败，注册目录不增加，重启后未发布阶段被回收。旧未注册空库可回收；直接 Engine 持有的目录和含业务记录的未注册目录不会误删。
- 两个约 2 MiB 备份在单份 16 MiB、总暂存 32 MiB 下实际重叠执行并完成。另验证工作区超出预留及失败目录仍被计费。

## 验证结果

- 全量 160 项测试通过；最后的锁交互边界补测 3 项配额测试、14 项恢复测试均通过。Clippy 全目标、failpoints 开启且 `-D warnings` 通过；fmt 和发布构建通过。
- 发布二进制自动复制：64 MiB 全局预算保持不变，512 KiB/16 覆盖索引写入直接追平 seq 34，无重新初始化；768 KiB 写入经一次检查点初始化追平。两例完整内容及修订号一致。
- 两份约 2 MiB 的实际备份在总暂存 32 MiB 下重叠完成，1000 条原记录及修订号核对一致。基线相同负载的第二份任务会错误失败。
- 携带 checkpointing 任务的 ext4 卷填至 0 可用字节，重启约 35.6 ms 到健康检查成功；释放空间前，2000 条已确认数据及覆盖 Lookup 均可读，释放后原备份重试完成。
- ENOSPC、WAL 写入 EIO 和 fsync EIO 三场景通过，各保护 2000 条故障前已确认数据；未知批次按原重试上下文补齐，故障后的第二批拒绝写入没有泄漏。持续 fsync EIO 时计划切换被拒绝，解除故障后切换成功，两端内容、修订号和位置一致。

30 秒基线、120 秒写入/合并/复制/备份/GC 并行、30 秒双节点中止重启后负载，20,000 条重租户和 200 条轻租户，测量期间没有编译或其他本任务压力测试：

| 阶段 | 轻租户写入 P99 ms | 重租户写入 P99 ms | Lookup 20 P99 ms | 最终操作失败 |
|---|---:|---:|---:|---:|
| baseline | 20.882 | 20.181 | 1.549 | 0 |
| combined | 23.101 | 21.455 | 1.295 | 0 |
| recovery | 19.179 | 22.096 | 1.338 | 0 |

并行阶段完成并校验 3 次备份，有 13 个实际五路推进区间；轻租户 P99 从 20.882 ms 到 23.101 ms，约上升 11%。双节点重启到可写及复制追平约 93.1 ms。重启前后和最终主从两租户完整核对一致，最终备份离线导入第三个 Store 后 20,000 条记录和修订号一致，中断备份自动续作完成。

驱动总准入重试为 `{"RESOURCE_EXHAUSTED": 11, "BUSY": 571}`；表中零失败表示最终操作成功，不表示所有 HTTP 调用都没有拒绝。阶段内对比不是版本性能提升的因果结论。原始 ACK、逐操作延迟样本、CRC 校验后的中断任务状态及源码/二进制指纹已归档，验证脚本复算 P50/P95/P99 并检查数据验收条件。


测试期间修正了三个过紧的测试前提：滚动发布的一秒令牌在集合/索引构建后再检查刷新；restore 按既有 BUSY 契约做有界重试；冷导出生命周期单元测试排除维护线程的临时句柄。没有放宽业务期限、忽略最终错误、降低数据校验或跳过测试。初轮失败日志仍归档。

## 复现与限制

使用 OrbStack Linux、Rust 1.90、原生 `/var/tmp`。最终代码运行 `cargo test --features failpoints -- --test-threads=1`，以及 `cargo clippy --all-targets --features failpoints -- -D warnings`。真实进程驱动 `global-replication.py` 与 `backup-staging.py` 位于本轮证据目录，分别验证自动复制循环和并发备份；均要求新的 root 参数。

本轮不包含 macOS 运行、真实设备掉电、内核真实写回错误和长期生产压测。系统调用 EIO 注入只验证限定租户路径的写入/同步错误，不能替代真实硬件故障。现有的异步复制 RPO、合并与刷盘共享锁、单次长 I/O 不可抢占等边界继续保留。

# v0.8.1 可靠性修复与恢复性能验证

本轮修复三个已复现的可靠性缺陷，并优化多文件数据库恢复时的文件归属检查。当前业务状态持续保留、旧发布/知识从被替代时计时、回执从提交事务计时的契约不变。注册表 v4、复制协议 3、WAL/SST v1 均未变更；实际 HTTP OpenAPI 与 v0.8.0 比较，除软件版本号外完全一致。

## 已复现并修复的问题

| 问题 | 修复前复现 | 修复后行为 |
|---|---|---|
| 时钟回拨可能重新授权过期重试 | 缩短期限后，回执与 token 具有相同截止时间；回收可以先删除回执。系统时间低于已持久化的回收水位时，旧 token 仍通过首次提交授权 | 授权、期限计算、token 签发和到期滞后统一尊重持久时间水位；旧请求拒绝，新凭据不会签发到该水位之前；重启后仍拒绝旧请求 |
| 小字节预算使回收不前进 | 16 KiB 原子预算、40 个存量回执、128 字节主体和操作 ID，迁移报 `expanded atomic batch exceeds configured limit` | 在写 WAL 前取消过大批次并缩小重试；存量迁移完成、到期队列排空，40 条当前文档保留 |
| 副本无法越过前台磁盘门槛应用删除 | 将副本占用计数置于配额 80% 的前台门槛，复制删除批次返回 `RESOURCE_EXHAUSTED` | 已由源提交的复制记录可使用维护预留空间；总配额处仍明确拒绝且不推进序号。旧快照保留旧值，新读和重启后确认删除 |

修复前，新增/扩展的三个场景全部失败；保留了[修复前日志](../bench-results/v081-reproduce.log)。时钟场景通过持久水位模拟回拨，没有修改宿主机时间；磁盘场景注入预算计数，不是真实设备写满。

相关实现：[统一时间判断](../src/tenant/retention.rs)、[回收批次适配](../src/tenant/retention/gc.rs)、[复制回放](../src/storage/engine/replication.rs)。过大批次重试仅覆盖提交前的展开大小检查；I/O 故障、总配额不足和其他错误不会被伪装成成功。

## 恢复性能优化

原实现对每个 SST/WAL 文件遍历整个 Manifest，并反复格式化文件名，文件归属检查具有平方级增长成本。现在一次建立文件名集合，按集合检查。临时集合计入内存预算；预算不足时回退到原有逐项检查，避免可选优化阻断故障恢复。

低内存回归确认：没有额外预算时，仍能删除未发布的 SST 输出，并保留权威 WAL。已有刷盘失败重试、缺失/外租户 SST、快照和崩溃恢复测试继续通过。

使用新增的 [recovery_perf](../examples/recovery_perf.rs)，在同一数据文件集上交替运行 v0.8.0 与 v0.8.1，各 5 次独立进程重开。每轮逐条核对所有数据、提交序号、SST 数量，并验证只清理未引用输出。

| 场景 | v0.8.0 引擎打开中位数 | v0.8.1 引擎打开中位数 | 耗时降低 |
|---|---:|---:|---:|
| 1,000 个 SST | 25.335 ms | 3.818 ms | 84.9% |
| 3,000 个 SST | 186.150 ms | 14.723 ms | 92.1% |

这是多小文件场景的引擎重开耗时，不包含完整 HTTP 服务启动；操作系统页缓存没有清空。不能把这些数字解释为设备冷缓存或所有租户打开场景的改善。逐轮结果保存在[性能数据](../bench-results/v081-performance.json)和同目录 `v081-recovery-*` 文件中。

## 完整回归与真实进程验证

OrbStack Ubuntu AArch64，Rust 1.90.0，Linux 7.2.12，18 个可见 CPU，约 32 GiB 客体内存；数据目录位于客体 `/var/tmp`。运行环境见 [environment](../bench-results/v081-environment.json)。

- `cargo test --locked --features failpoints -- --test-threads=1`：**94 项通过**，包含 WAL/Manifest/回收进度崩溃恢复、正文与索引原子性、快照、时态基线、租户隔离、备份恢复和复制切换。
- 全目标严格 Clippy、格式检查通过。正式服务和恢复程序以不含 failpoints 的 release 配置构建。
- 真实 v0.8.0 程序创建数据、保留策略与有效回执，停止后以 v0.8.1 打开同一目录：原回执返回相同结果，当前文档保留，策略不被重置。
- HTTP 保留示例确认：过期回执不能重复生成文档、旧发布被回收、当前发布继续可用、到期队列排空。OpenAPI 3.1 校验通过。
- 两个正常服务进程完成：检查点初始化、4,000 次文档更新、覆盖 Lookup 核对、副本 SIGKILL 后 WAL 续传、A→B 与 B→A 计划切换、旧配置重启、时态历史与回执保留，以及停止旧主后的显式故障升主。

证据：[完整测试](../bench-results/v081-final-tests.log)、[Clippy](../bench-results/v081-final-clippy.log)、[格式](../bench-results/v081-final-fmt-check.log)、[构建](../bench-results/v081-final-release.log)、[升级与 HTTP](../bench-results/v081-runtime.json)、[双进程复制](../bench-results/v081-pair-runtime.log)。

## 持续回收与读写检查

旧版和新版各运行一次 120 秒主测量窗口，顺序执行，期间没有并发构建、测试套件或其他本任务的负载。8 个活跃租户、32 个冷租户、8,000 条约 1 KiB 当前文档、每集合 3 个索引、2 个写线程、16 个读线程；全局引擎预算 512 MiB、每租户 64 MiB，保留期限 3 秒。读取线程包含 1 ms 间隔。

每写批次 20 条，持久化幂等回执。持续核对批量读取不会看到半个写批次；收尾等待回收、刷盘与合并，关闭并重开全部活跃租户，再核对正文和索引。

| 观测 | v0.8.0 | v0.8.1 |
|---|---:|---:|
| 完成文档更新 | 839,220 | 883,740 |
| 完成主键读取 | 802,652 | 802,576 |
| 写入背压次数 | 0 | 0 |
| 热点读线程各自 P95 | 23–26 µs | 20–25 µs |
| 热点读线程各自 P99 | 82–90 µs | 77–83 µs |
| 引擎记录的内存峰值 | 38,349,586 B | 37,011,708 B |
| 采样进程 VmHWM | 60,252,160 B | 61,104,128 B |
| 逻辑回收目标记录数 | 42,122 | 44,349 |
| 收尾过期队列 | 空，滞后 0 | 空，滞后 0 |
| 采样维护错误 | 0 | 0 |
| 关闭重开核对 | 8,000 条通过 | 8,000 条通过 |
| 32 个冷租户重开 P99 | 139 µs | 176 µs |

这轮负载没有观察到数据丢失、重复生成、半批可见或持续回收积压。完成工作量还包含并发创建冷租户阶段，不能直接除以 120 当作严格稳态 QPS；单次长短窗口也不能证明普遍提速。小型冷租户重开和 RSS 的观测值略有增加，未将其隐去或与多 SST 专项结果混为一谈。

## 复制追赶复测

每轮 8,192 个源事务，4 个副本读取线程，读取间隔 100 µs，回环 HTTP，最终核对源/副本文档和索引。先各运行 3 轮，发现追赶耗时波动后，补做 5 对交替运行；所有原始结果均保留。

| 每轮指标的中位数 | v0.8.0 | v0.8.1 |
|---|---:|---:|
| 首组各 3 轮：追赶时间 | 246.318 ms | 292.485 ms |
| 首组各 3 轮：Lookup P99 | 11.125 µs | 7.000 µs |
| 交替各 5 轮：追赶时间 | 223.913 ms | 230.455 ms |
| 交替各 5 轮：Lookup P95 | 4.709 µs | 4.709 µs |
| 交替各 5 轮：Lookup P99 | 9.500 µs | 10.583 µs |
| 全部各 8 轮：追赶时间 | 229.304 ms | 241.761 ms |
| 全部各 8 轮：Lookup P99 | 9.667 µs | 9.792 µs |

本轮**没有证明复制追赶提速或性能严格不下降**：汇总追赶中位数增加约 5.4%，交替复测增加约 2.9%，各轮分布有明显重叠。代码改动解决的是高磁盘占用下的复制进度问题，没有更换追赶算法；这些短测不足以判定上述差异的稳定因果。后续需要在固定设备和更长测量窗口下继续跟踪。表中是各轮 P99 的中位数，不是合并所有请求样本后的 P99。

证据：[初始测量与持续负载](../bench-results/v081-performance.json)、[交替复制复测](../bench-results/v081-replication-interleaved.json)。

## 边界与使用

这是经上述范围验证的修复，不能保证所有部署都不存在缺陷。未进行真实掉电、设备写满、独立机器网络分区、多日持续负载或本轮真实 S3 运行验证。进程 SIGKILL 和预算注入不能替代这些测试。异步复制仍可能丢失未复制提交；当前时间线仍不按业务时间裁剪；备份对象保留仍独立于在线历史回收。

建议主从都更新为 v0.8.1。调用方继续保存原操作 ID、请求内容、history 与 retry_token，不得在未知结果或过期后换新凭据盲目重试。配置仍只有租户级 `retention_seconds`，见 [保留机制](retention.md) 与 [升级契约](middleware.md)。

## 1. 管理排空失败后，已中断索引可能一直停在 BUILDING（中高）

触发顺序：后台恢复线程曾检查过一个正在进行的在线构建；随后管理员尝试 close/删除/改配额，构建响应 draining 而退出，但另一个句柄使管理排空超时。入口恢复，原引擎继续服务。

`restart_interrupted_build` 会在跳过活动构建后记录 `recovery_catalog`；构建以 BUSY 退出时仅从 `builds` 移除 generation，没有让该缓存失效。下次恢复检查发现目录序号相同就直接返回。普通文档和构建增量写入不会改变 C/J/L 目录序号，因而不能唤醒这条路径。位置：`src/tenant/indexes.rs:198–235`、`:369–394`。

**实际复现：**

- 先以可控背压重现：保留一个句柄让 close 返回 BUSY，构建也返回 BUSY；清除积压并确认普通写入仍成功后，调用恢复工作者的原方法 20 次，索引仍为 BUILDING、活动构建为零、目录序号未变，2048 条确认文档一致。
- 再启用真实后台工作者，无手工恢复调用：16,384 文档在线构建被同样的失败排空打断；观察 5052 ms、检查 96 次后，状态仍是 BUILDING，`active_builds=0`，恢复缓存与目录序号都是 66。
- 释放句柄，close 后重新打开租户，后台工作者恢复到 READY；核对 16,384 条文档的确认修订和载荷，无差异。

五秒观察本身不证明永久卡住；源码中的缓存返回条件说明，在不重开引擎且不改变目录时会持续跳过。影响包括索引迟迟不可用、BUILDING 增量持续积累；这次没有测量长期磁盘耗尽，不将其表述为已经观测到的结果。

建议在构建退出或恢复工作者跳过活动构建时正确失效恢复缓存，并保护“管理排空失败、复用原引擎”的回归。成功排空并重开引擎的测试覆盖不到此场景。

## 2. 在线缩配额与并发预留不构成原子操作（中）

`Counter::take` 修改 used，`set_limit` 先读取 used、再单独存储 limit。两条路径之间没有共同的原子协议：一次预留可能通过旧上限检查，另一个线程又接受较小上限，最终两个调用都成功。位置：`src/resources.rs:49–68`。

**实际复现：** 使用公开 Counter/Budget 接口并发执行预留与缩配额，原上限 128 MiB、新上限 64 MiB、全局预算 512 MiB。连续三轮均观察到：预留已经成功返回，used 为 **134,217,728**，limit 为 **67,108,864**；分别在 55、352、75 次预留尝试内触发。预留释放后 used 归零，未发现计数泄漏。

这是预算计费契约失效；测试没有分配同等大小的实际缓冲区，不是 RSS 超限或 OOM 的测量。全局预算仍有效。结合调用路径，已取得 HTTP 输入预算的请求可以在管理排空期间继续预留内存，因此租户 gate 不能替代 Counter 层的同步；但本次尚未在完整 HTTP 改配额请求上命中同一窄窗口，这部分影响属于源码推断。

建议使缩配额与预留使用一致的同步/原子协议，保证新配额发布后不能再有沿用旧上限的成功预留。回归不能只覆盖缩配额时已经存在的固定预留，还需覆盖并发增长。

## 3. 大量历史删除租户会耗尽生命周期容量（中，容量风险）

删除租户保留完整 Deleted 注册项；活租户上限排除了这些项，但持久注册表仍受 16 MiB 格式上限约束。位置：`src/tenant/manager/lifecycle.rs:357–369`、`src/tenant/manager.rs:423–446`、`src/storage/files.rs:23–27`。

**实际复现：** 用合法、带校验的持久注册表夹具模拟长期积累，包含 **56,870 个 Deleted 项**，文件 **16,777,152 字节**。这不是逐次执行五万多次创建/删除；之后的打开、创建、删除和重启均使用真实 Store API。

- 连续重开 Store 三次，每次创建都返回 RESOURCE_EXHAUSTED。
- 原有租户的确认修订仍可读，三次核对一致。
- 删除最后一个活租户后，再次重开，活租户为零，创建仍返回 RESOURCE_EXHAUSTED。

这里未发生元数据损坏，存储层按格式边界拒绝写入；更准确的结论是**生命周期历史容量不会随租户删除而释放**，普通重启和减少活租户均不能恢复创建能力。56,870 是本夹具字段长度下的观测值，不是固定产品上限。

建议在保留“已删 UUID 不可复用”契约的前提下，压缩或分离墓碑索引，并增加生命周期容量预检和告警；单纯放宽活租户计数不能解决历史累积。

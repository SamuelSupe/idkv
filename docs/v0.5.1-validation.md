# v0.5.1 性能与稳定性验证

验证日期：2026-11-05。本轮保持一主一从异步复制、现有 HTTP 接口和 WAL/SST 格式，优化复制追赶及从库查询，并修复资源计费和租户同步隔离问题。发行包的 Linux AArch64 二进制不启用故障注入。

## 修改与回归

| 问题 | 修改及验证 |
|---|---|
| 每个复制请求固定预留 288 MiB，使小预算节点无法初始化复制 | 输入预留 2 MiB，输出按实际编码长度计费；直接序列化结构，不再先构造整个 JSON Value。64 MiB 全局预算下初始化、增量和计划切换通过 |
| 一个待删除租户被活跃句柄占用时，中断整轮其他租户同步 | 逐租户记录目录/配额错误，跳过受影响租户，继续健康租户；释放句柄后重试删除成功 |
| 复制有积压时每页仍等待 50 ms | 本轮成功且有积压时继续下一轮；每轮各租户最多一页，追平或出错后等待配置的轮询间隔 |
| 每个原始事务独立提交一次 I/O 任务 | 校验整页后一次追加原始帧、一次 fsync；保留原始序号、事务边界和每帧校验 |
| 普通数据更新也改变从库 catalog_seq | 主从共用目录变更判定；正文更新保留元信息缓存，集合/索引/Lookup 定义更新仍使缓存失效 |
| 从库 commits、wal_bytes、document_bytes 未累计 | 与主库共用统计逻辑，回放记录原始事务数量及字节数 |
| 解码返回后预算先于页面使用结束释放 | 解码后的响应携带预算至使用结束；回放分配记录前先申请预算，源端按实际帧大小计费 |
| 取消请求可能提前释放后台任务资源 | 阻塞 HTTP 工作持有自己的并发许可；检查点安装任务持有暂存目录清理对象，避免外层取消时提前删掉仍在使用的目录 |

前两项使用同一测试在原 v0.5.0 实现上复现失败，修复后通过：[失败记录](../bench-results/v051-reproduced.log)、[复制回归](../bench-results/v051-replication-tests.log)。小预算测试同时设置租户预算 32 MiB、缓存 4 MiB、memtable 64 KiB；不意味着小预算可以处理任意 64 MiB 原子批次。

完整回归 **57 项通过，0 失败**。覆盖原有 CRUD、索引、查询、DSL、HTTP、备份、崩溃恢复和复制测试；扩展存储测试校验普通回放不改变目录版本、目录变更仍正确失效、从库提交统计、畸形页面零修改和重开恢复。日志：[完整测试](../bench-results/v051-tests.log)、[Clippy -D warnings](../bench-results/v051-clippy.log)、[格式检查](../bench-results/v051-fmt-check.log)。请求取消相关修复通过编译、所有回归及生命周期所有权检查；本轮没有专门注入检查点安装期间的异步取消。

## 复制追赶前后对比

使用同一 [replication_perf.rs](../examples/replication_perf.rs) 负载分别构建 v0.5.0 和 v0.5.1，顺序运行各三轮，每轮独立新目录。保持 50 ms 轮询、一个热点租户和一个轻租户、1 MiB memtable、8 MiB 块缓存。四个装载线程先产生 8,192 个积压事务，循环更新 1,024 个键，每个文档有 256 字符负载；存在唯一覆盖索引，追赶期间持续从库 Lookup。开始计时前已完成检查点初始化；这是增量追赶，不包含最初数据装载时间。

环境为同一 OrbStack Ubuntu AArch64 VM，18 个可见 CPU、约 31.36 GiB 内存，数据位于虚拟块设备上的 btrfs，回环网络。基准期间没有同时运行本轮编译或持续负载。它不是远程网络、独立硬件、冷缓存或大于内存的数据集测试。[环境记录](../bench-results/v051-environment.json)

| 指标，三轮中位数 | v0.5.0 | v0.5.1 |
|---|---:|---:|
| 8,192 事务追赶时间 | 1,946.20 ms | 273.45 ms |
| 追赶阶段事务/秒 | 4,209 | 29,958 |
| 该租户完成的 I/O 调度任务（含期间维护） | 8,319 | 94 |
| 轻租户更新可见延迟 | 4.99 ms | 2.55 ms |

该负载的追赶速度约 **7.12 倍**，I/O 调度任务数减少 **98.87%**。这不是客户端写入吞吐提升 7 倍，也不代表所有查询场景同幅改善。原始每轮数据和汇总：[对比汇总](../bench-results/v051-perf-summary.json)、[旧 1](../bench-results/v051-before-1.json)、[旧 2](../bench-results/v051-before-2.json)、[旧 3](../bench-results/v051-before-3.json)、[新 1](../bench-results/v051-after-1.json)、[新 2](../bench-results/v051-after-2.json)、[新 3](../bench-results/v051-after-3.json)。

明确的取舍：集中追赶期间，Lookup P99 的三轮范围从 **37–47 μs** 变为 **64–546 μs**。新版本更密集地使用 CPU、内存表及 I/O；追赶时间更短，采集到的查询样本也更少。因此本轮没有宣称读尾延迟改善或不下降。当前逐租户轮次和资源背压保留，但尚未实现以业务 P99 为反馈的动态复制限速。

采样的从库引擎预算峰值中位数约从 3.06 MiB 变为 4.94 MiB；新版本计费持续覆盖已解码页面且追赶更密集，不能据此将逻辑预算差异当成进程 RSS 增减。小请求不再固定占用 288 MiB 预算，属于资源可用性修复，未被表述为实际 RSS 降低 288 MiB。

## 实际进程、故障与兼容性

正式二进制的双进程示例通过检查点初始化、正文/索引一致性、只读边界、断线追赶、双向计划切换、重启保持持久角色、写后读等待及显式故障升主。[正式运行](../bench-results/v051-pair-release.log)

故障注入版本额外在从库合并 WAL 追加中故意截断最后一个事务负载并中止进程。重开后恢复完整事务，重取剩余日志，最后验证两个租户的文档原子批次和覆盖 Lookup。旧主持久停写、新主持久升主但尚未响应两个崩溃点也再次通过。[故障运行](../bench-results/v051-pair-faults.log)

使用旧 v0.5.0 正式二进制作为初始主库、新 v0.5.1 作为初始从库，完整运行初始化、增量、A→B/B→A 切换、重启和故障升主流程，均通过。验证了本轮格式及复制接口的双向互通；没有通过改写旧节点状态文件模拟升级。[混合版本运行](../bench-results/v051-pair-mixed.log)

普通 HTTP、DSL 和 OpenDAL fs 后端的备份/校验/恢复/保留清理回归通过；OpenAPI 3.1 规范校验通过，版本 0.5.1，44 个路径、48 个 schema。[HTTP](../bench-results/v051-native-http-smoke.json)、[DSL](../bench-results/v051-http-smoke.json)、[OpenAPI](../bench-results/v051-openapi-validation.json)

## 三分钟多租户持续负载

使用既有 [soak.rs](../examples/soak.rs) 运行 180 秒：8 个活跃租户、32 个冷租户，每活跃租户 1,000 个约 1 KiB 文档及 3 个索引，2 个写线程和 16 个读线程。写线程按 20 条原子批次循环更新，读线程执行 Get 并周期性验证 MultiGet 的批次一致性和唯一索引查询；读循环有 1 ms 间隔。全局引擎预算 512 MiB，每租户 64 MiB。

- 完成 **1,338,020 次文档更新、1,204,226 次 Get**，没有记录到读取/写入错误、维护错误或预算拒绝。这是对 8,000 个驻留文档的重复更新，不能称为百万条数据集验证。
- 热点租户的四个 Get 读线程 P99 为 **74–77 μs**；轻租户读线程为 **14–15 μs**。这些是该持续负载的嵌入式 Get 样本，不是 HTTP 或复制从库 Lookup 的延迟。
- 观察到引擎计费内存峰值 **35.41 MiB**，Linux 进程 VmHWM 采样值 **59.81 MiB**；两种计量独立记录。
- 结束后刷盘、完整合并、SST 校验通过；关闭再打开 8 个活跃租户，验证 **8,000 个文档及非唯一索引结果**。32 个冷租户均自动关闭，再次打开读取正确。

证据：[持续负载汇总](../bench-results/v051-soak-summary.json)、[完整时序及线程结果](../bench-results/v051-soak.jsonl)、[RSS 采样](../bench-results/v051-rss.json)。此测试期间并行执行了正式/混合版本 HTTP 功能验收，不能作为独占硬件的吞吐基准；它与前面的复制性能比较分开运行。

## 复现与边界

在项目目录执行，数据目录须不存在。不同版本的性能比较使用同一示例源码，每次新目录，并避免同时运行编译和其他压测：

```sh
cargo test --locked --features failpoints -- --test-threads=1
cargo clippy --locked --all-targets --features failpoints -- -D warnings
cargo fmt -- --check
cargo build --locked --release --example replication_perf --example soak
cargo run --locked --release --example replication_perf -- /var/tmp/tkv-perf-run 8192
cargo run --locked --release --example soak -- /var/tmp/tkv-soak-run 180

cargo build --locked --release --features failpoints --bin tenant-kv
python3 scripts/replication_demo.py --binary target/release/tenant-kv --root /var/tmp/tkv-fault-run --faults
cargo build --locked --release --bin tenant-kv --bin tenant-kv-restore
python3 scripts/replication_demo.py --binary target/release/tenant-kv --root /var/tmp/tkv-release-run
```

异步复制的可靠性契约不变：成功写入只保证主库本地持久化；故障升主前必须外部隔离旧主，并接受未复制事务可能丢失。尚未验证真实设备掉电、长时间网络分区、跨物理主机或机房、大于内存的复制负载和真实 AWS S3。本轮短时持续运行不能替代长期生产资格验证。

# ab7a0ec 复查、修复与性能对照（2026-11-07）

基线为 `ab7a0ecfa6077b3d3b3a030749bd2b5be9187dc8`。报告中的三项主要问题均确认并修复；另改善两处 GC 扫描行为，明确客户端连接池及 GC 状态约束。HTTP/2 被移除的说法不符合这两个历史版本的实际构建。证据保存在 [ab7a0ec-review-20261107](../bench-results/ab7a0ec-review-20261107/)。

## 核实与实现

| 反馈 | 核实与最终行为 |
|---|---|
| 空正文请求在冷准入时占执行名额 | 属实。所有请求均在取得预算、接收正文后才取得执行名额。冷预算锁等待使用独立的 `max_http_admission_requests`，默认 256；热预算查找仍用非阻塞路径。取消或超时后的阻塞准入继续持有准入和租户名额，直至任务退出，但不持执行名额。JSON 解码复用此前的预算，避免再次为预算等待 slot 锁 |
| flush 被降为 Background | 属实。TableWriter 接收 I/O 类别；flush 数据输出和最终同步使用 Durable，普通合并输出仍为 Background。合并中途插入的 flush 也使用同一 flush 路径。仍保留连续八项优先工作后让读取推进的公平规则；单个 OS I/O 不可抢占 |
| 四个租户建索引占满维护池，生命周期操作也被挡住 | 属实。增加独立的建索引池和生命周期池，各默认 4；备份、合并、校验、检查点及本地恢复继续使用维护池。建索引与维护共享每租户重任务上限 1，生命周期另有每租户上限 1。四个索引构建不再占用其他租户的备份、配额、close、删除执行名额 |
| HTTP/2 兼容性回退 | 未成立。原 axum auto builder 并未启用 HTTP/2。b206985、ab7a0ec 和本轮修复的实际二进制均不接受 h2c prior-knowledge；原版和当前锁定特性均无 http2。文档明确内置服务为 HTTP/1，未增加协议或依赖 |
| keep-alive 五秒与客户端池不匹配 | 提醒合理。内置 Rust Client 和复制客户端的池空闲回收设为四秒，短于默认服务端五秒。调低服务端期限时需相应调整调用方。没有增加非幂等请求的盲目重试，关闭竞态仍按操作 ID/条件版本处理 |
| history 后续 sweep 重复扫描旧墓碑 | 属实，属于效率问题。遇到上一次完成下界以下的旧 baseline 后，直接定位到下一 identifier，跳过已清理尾部。首次 sweep 仍逐页访问；依赖 history 不可变、ordinal 单调增加、已完成 sweep 在旧下界以下最多保留一个 baseline 的既有不变量 |
| gc_prefix 看不到同事务 expire 删除 | 原行为保守，不会错误删除。现对物理扫描已访问键叠加本事务的写/删，history 不再选中同事务已删除的知识条目。尚未进入物理视图的新键留待后续事务，未把物理分页扩大为无界事务变更合并 |
| schedule_at 的 STATE 回退可能被覆盖 | 当前清理阶段没有该调用路径，不是已发生的缺陷。在本地 State 发布处补充约束注释：以后若引入调度，必须合并 pending rewind。没有以虚构触发路径宣称修复数据问题 |

生命周期池分离解决的是准入隔离。已有嵌入式句柄或索引构建仍持有引擎时，close/配额/删除可在一秒排空后返回 BUSY；不会强制析构调用方引用。可先删除索引，使该代构建在后续检查时停止，底层 I/O 仍须返回。各池仍有全局总额，不能保证任意数量的同类任务都可同时执行。

新增配置及默认值：`max_http_admission_requests=256`、`max_http_index_requests=4`、`max_http_lifecycle_requests=4`。配置校验、[运维](operations.md)、[格式与调度](format.md)、[保留策略](retention.md)和[客户端集成](middleware.md)均同步更新。WAL/SST 格式、复制协议及确认契约未改变；CLI 生成的 OpenAPI 与仓库文件相同。

## 回归与对照

新增五项行为回归，完整 **202 项测试通过**。同五项测试放入独立的原版 ab7a0ec 源码后，全部出现预期行为失败，均非编译失败；对照没有修改生产逻辑或 Cargo 配置。

1. 两个租户各 32 个空正文 GET，在可控的 slot 锁竞争下进入冷准入后取消。旧版占满普通执行名额；修复版中第三租户仍可读出已确认修订，原租户的并发边界仍有效。这里用锁竞争稳定复现阻塞状态，不将其表述为真实大 WAL 回放耗时测量。
2. 单 I/O worker 上构造读取积压，确认 flush 的 SST 输出在排队读取之前推进，并核对已确认的 512 KiB 数据与引擎校验。旧版读取会越过 flush 输出；修复版通过。
3. 四个租户的真实 HTTP 索引请求同时阻塞在构建事务，另一个租户的备份、改配额、close、删除均成功。正在构建的租户 close 返回 BUSY，而非维护池满的 429；释放事务后四次构建完成。
4. 把物理页预算调为 8，构造旧 baseline、新 baseline 和 100 个旧墓碑；后续 history sweep 在三步内完成，保留新 baseline 并删除旧 baseline。
5. 同事务删除知识键后，物理 GC 页反映该删除，同时保留下一个有效键。

原版失败日志、输入测试原文与源文件对照分别见 `control-*.log`、`control-test-input.json` 和 `control-source-provenance.json`。Clippy（`-D warnings`）、格式检查、release 构建均通过。初轮 `initial-lib-tests.log` 保留了新增测试把响应 `_rev` 位置写错的诊断；修正测试断言后，`full-tests.log` 为最终完整结果，未修改产品契约或放宽验证。

## 同负载前后测量

在 OrbStack Ubuntu Linux aarch64 原生 Btrfs `/var/tmp` 上顺序运行原版和修复版，运行期间未并行编译。使用未修改的原资格脚本：重租户 5000×4 KiB、轻租户 200×128 B；重写每秒 40 批×20 文档，轻写每秒 20 次，以及每秒 200 get、100 lookup、50 索引查询。普通阶段 10 秒、混合阶段 45 秒、重启恢复阶段 60 秒。固定二进制与源码哈希见 [来源记录](../bench-results/ab7a0ec-review-20261107/source-provenance.json)。

| 阶段 | 轻写 P50，原版→修复 (ms) | 轻写 P95 (ms) | 轻写 P99 (ms) | 轻写吞吐 (次/秒) |
|---|---:|---:|---:|---:|
| 普通 | 5.137 → 4.527 | 8.892 → 7.894 | 10.861 → 14.145 | 19.996 → 19.893 |
| 混合 | 4.907 → 4.692 | 8.296 → 7.900 | 11.691 → 12.971 | 20.015 → 20.015 |
| 恢复 | 4.878 → 4.514 | 8.416 → 8.404 | 16.388 → 16.865 | 19.999 → 19.933 |

**本次没有取得轻租户 P99 整体改善的证据。** 混合 P99 增加约 11.0%，恢复增加约 2.9%，普通短样本增加约 30.2%。中位数及 P95 改善，吞吐接近目标，业务测量最终错误均为零；这些结果不能替代尾延迟达标。队列回归证明修正了 flush 优先级，但不能据此把真实混合负载的尾部变化全归因于该调度，更不承诺硬延迟隔离。没有为得到更好结果反复挑选测量轮次。

两版本混合阶段均有两次五项任务重叠采样、两份验证备份；恢复阶段均有七次重叠采样、三份验证备份。备份使用现有 OpenDAL fs 后端。恢复阶段业务重试中的 BUSY 为 214→217 次，全流程累计 BUSY 为 292→279 次；均按原脚本退避，不把暂时拒绝隐藏为没有背压。主从重启至可安全写入并追平为 79.3→99.4 ms，单次结果不能推导恢复时延上限。

重启前后及最终阶段逐项比对主从已确认键、修订及载荷哈希，每轮核对 31,200 个文档状态；离线恢复备份再核对 5000 个。两轮共 **72,400 次状态核对，差异为零**，GC 到期队列均排空。所有操作的 P50/P95/P99、吞吐和重试保存在 [performance-comparison.json](../bench-results/ab7a0ec-review-20261107/performance-comparison.json)，原始延迟分布也一并保留。

## 故障及协议运行验证

| 修复版场景 | 故障前已确认文档 | 恢复后缺失 | 结果未知的一批八条在重试前可见 | 解除故障后重启至安全重试 |
|---|---:|---:|---:|---:|
| 独立 256 MiB ext4 卷 ENOSPC | 2000 | 0 | 0/8 | 39.9 ms |
| 限定 WAL 路径 write EIO | 2000 | 0 | 0/8 | 31.9 ms |
| 限定 WAL 路径 fsync EIO | 2000 | 0 | 8/8 | 31.0 ms |

三种场景共保住 6000 条故障前确认文档，故障解除后重启并以原操作 ID 幂等重试，最终各 2008 文档一致。ENOSPC 覆盖真实独立卷写满；EIO 为限定 syscall 注入，不能证明真实设备写回错误及主机掉电组合的行为。

HTTP 协议探针分别向 b206985、ab7a0ec、修复版发送有效 h2c prior-knowledge 前导与 SETTINGS，三者均关闭该连接，之后 HTTP/1 健康检查仍成功。每版在探测前、探测后、重启后各核对 100 文档，共 900 个状态，差异为零。结合原/现 Cargo 特性图，确认本次不存在从 HTTP/2 回退至 HTTP/1 的实际构建兼容性变化。

测试服务均已停止，故障 loop 卷已卸载并解除映射，凭据未归档。运行和构建使用独立 Cargo target、关闭增量编译，固定运行文件不覆盖。最终测试源码、release 文件与运行日志哈希已互相核对。未做真实 S3、真实硬件掉电、50 GB 跨机房初始化或长期生产 soak，本轮结论限于上述测试与负载。本报告记录提交前的验证快照，后续交付以包含本报告的 Git 提交为准。

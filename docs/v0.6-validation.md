# v0.6 性能、稳定性与时态身份验证

日期：2026-11-05。交付版本 v0.6.0。本轮同时完成扫描/复制尾延迟优化与时态身份第一阶段。以下区分实测结果、修复证据与尚未验证的范围。

## 环境与方法

OrbStack Ubuntu，Linux AArch64，VM 显示 18 CPU、约 31.4 GiB 内存，Rust 1.90；测试数据放在 `/var/tmp` 的虚拟 Btrfs 卷。不是设计目标中的固定 8 vCPU/16 GiB 裸机 NVMe。引擎默认全局内存预算 4 GiB，具体基准覆盖配置见源码与原始 JSON。性能测试与编译、持续负载分别运行。

本轮早期编译遇到 `/tmp` tmpfs 被已有构建缓存占满。将项目构建目录移动到磁盘 `/var/tmp` 并保留原路径链接后重新验证；没有删除源数据。修复前的 v0.5.1/v0.5.2 复现与采样只用于诊断，正式对比双方均在修复后执行。

原复制基准使用 1 ms 计时器抽样，一次追赶只有约 65–99 个样本，P99 接近最大值。新基准使用独立读取线程、每轮至少 1000 个有效样本，扫描每轮 1000 次。相同增强基准同时用于 v0.5.2 基线与候选版，三轮交替顺序。旧报告的 P99 不能直接与新工作负载相减；在增强负载下也没有稳定复现 v0.5.1 到 v0.5.2 的旧回退幅度。

## 修复与机制证据

1. 长扫描原来每个数据块独立进入 I/O 队列。现在从第二块起，每工作项最多读取四个连续块，保留前缀/分区/范围边界；首块和前缀 Lookup 按需读取。低预算下回退到已加载前缀，额外预读不驱逐缓存。统计包含所有实际预读。跨分区历史版本与墓碑扫描用仅够一块的剩余预算回归，验证不漏、不重和持续推进。
2. 固定 Lookup 复用计费的 Arc 计划和快照感知的集合 UUID，避免锁内深拷贝、重复目录读取与 JSON 解码。更新定义后仍正确重新绑定；查询快照和主从提交序号语义保持不变。CPU 采样记录了原重复读取/复制开销；采样运行时间不作为性能成绩。
3. 复制应用持有一次内存表引用，并将相邻小事务合并为最多 8 条记录的插入段，较大事务保持原有最多 64 条分段，避免放大批量回放锁开销。每条记录仍保留原提交序号，WAL 原始事务帧不变，整页同步后才发布可见序号。额外插入缓冲在 WAL 写入前计费。曾试验 64 条段，但固定读取间隔测试出现更差的读取 P99，已缩小粒度并保留失败候选原始数据。
4. 修复无变更事务提前返回的持久性缺陷：并发幂等重试可以看到前一事务 staged 的收据，旧实现会在前一事务 fsync 前返回成功。现等待实际观察序号持久化，失败传播 COMMIT_UNKNOWN。确定性测试停在 WAL 已追加、尚未同步的位置，验证普通及带快照的无变更事务均不会提前确认。
5. 新增时态入口的交付前检查复现了 auto 模式混入 from 字段仍返回 200 的问题：serde 的内部标签单元变体会忽略额外字段。改为严格结构变体后，auto + 手动字段返回 400；修订令牌也严格限定为字符串，拒绝对象形式的 absent。保留失败复现日志及最终 HTTP 回归，正式 HTTP 示例同时验证非法请求不会创建时间线。

## 复制追赶与读取尾延迟

测试先在主库用四个写线程形成积压，再让从库追赶；追赶期间持续 Lookup，完成后逐条校验全部 1024 个热键及轻租户数据。不是持续主库写入吞吐或真实双机网络测试。表中为三轮中位数，单轮值和样本数全部保留。

| 负载 | 指标 | v0.5.2 | 最终 8 条插入段 |
|---|---|---:|---:|
| 8192 提交 / 4 无限速读线程 | 追赶耗时 | 182.096 ms | 222.976 ms |
| 8192 提交 / 4 无限速读线程 | Lookup P95 | 5.459 μs | 5.583 μs |
| 8192 提交 / 4 无限速读线程 | Lookup P99 | 28.208 μs | 23.334 μs |
| 8192 提交 / 4 无限速读线程 | 实际读取速率 | 975643.133 次/s | 1218091.922 次/s |
| 16384 提交 / 16 读线程 / 10000 次/s 到达 | 追赶耗时 | 361.844 ms | 372.339 ms |
| 16384 提交 / 16 读线程 / 10000 次/s 到达 | Lookup P95 | 8.958 μs | 9.083 μs |
| 16384 提交 / 16 读线程 / 10000 次/s 到达 | Lookup P99 | 28.542 μs | 24.709 μs |
| 16384 提交 / 16 读线程 / 10000 次/s 到达 | 实际读取速率 | 9960.089 次/s | 9972.095 次/s |

早期采用逐次 sleep 的受控负载会累积 VM 定时器漂移，已改用共享单调时钟及到达序号；固定速率三轮实际读取约 9947–9981 次/s。表中 Lookup 延迟是接口执行时间，不含基准生成器的定时等待。无限速模式的读取总量随读取速度及追赶窗口变化。短追赶、随机租户 UUID 调度次序及虚拟化调度都会影响耗时和轻租户延迟；不根据三次短测试宣称严格尾延迟保证。原始数据包括较慢候选，未通过减少持久化、延迟确认或取消读取来提高成绩。

无限速读压下 Lookup P99 中位数降低约 17.3%，但总追赶耗时增加约 22.4%。固定 10000 次/s 到达时 P99 降低约 13.4%，追赶耗时增加约 2.9%。本轮改善读取尾延迟，不能宣称复制总体吞吐也提升；追赶时间仍受调度和读负载竞争影响。

最后补入“大事务沿用原有分段”的保护后，重新通过完整 70 项测试、严格静态检查、正式/故障双进程、混合普通集合复制和 HTTP/备份恢复；并额外复测交付二进制：16384 提交、约 9946 次/s 读取，追赶 321.45 ms、Lookup P99 20.08 μs（3197 样本）。这是单轮一致性确认，不替换上表三轮统计。

## 时态第一阶段

已实现受管集合、UTC 微秒区间、自动/手动模式、显式修订、原子 bind/rebind/unbind/replace_identifier、永久知识 UUID、幂等收据、实体属性合并、基础解析、HTTP 鉴权与 OpenAPI。历史按标识及知识 ordinal 定位一份完整时间线，最新查询直接读取当前时间线；每次仍需解码整条时间线。

## 正确性与运行验证

- OrbStack 完整测试 **70 项通过**；严格 Clippy（all-targets、failpoints、-D warnings）、格式检查、正式 release 构建通过。
- 时态回归覆盖：半开边界、未来计划、空档、同义 no-op、原子替换、16 并发同操作重试、并发修订冲突、随机修正对照参考实现、属性更新不解绑、重复标识拒绝、展开批次/片段上限整体回滚、跨租户知识拒绝、恢复后 UUID 不复用。
- 时态故障注入覆盖 WAL 撕裂头/载荷、追加、同步、SST 同步、Manifest 发布、合并同步。新旧知识、时间线和收据全成或全败；旧历史保留。主从测试覆盖检查点、增量、落后版本错误、切换后幂等重试和反向追赶。
- 独立 Linux 正式双进程、故障版双进程及 v0.5.2 主库 → v0.6.0 从库的普通集合复制验证通过。混合版本不用于时态写入；启用前两端必须升级。
- 正式 HTTP 服务通过原生 API、DSL、时态身份、OpenDAL FS 备份/校验/恢复及 OpenAPI 3.1 校验；另以 JSON Schema 验证五份真实 HTTP/Rust 身份响应。该轮没有连接真实云 S3。
- 持续负载运行 180 秒：1436120 次更新、1275819 次读取，8 活跃租户、32 冷租户、2 写线程、16 读线程、3 索引。无记录的维护/租户错误；结果、唯一索引、批次原子性、重开恢复按程序断言验证。观测 VmHWM 61.0 MiB。

进程退出和软件故障注入不能代替真实掉电、设备缓存持久性与磁盘故障；180 秒负载不能代替长期 soak。此轮未重新跑百万/千万条或大于内存三倍的数据集。时态历史和收据暂不 GC，依赖租户磁盘配额背压。

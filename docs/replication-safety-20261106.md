# 复制安全复查与修复（2026-11-06）

此文保留 31b575f 的验证时点。后续确认持续短读仍可能饿死安装、逐页冷重开代价较高，且只重试旧 inode 的 fsync 不能充分覆盖写回错误。当前实现和新的验证见 [读流量与 WAL 恢复修复](read-drain-recovery-20261106.md)，下文“回放后同步”的旧实现已由新 inode 重建替代。

以 31851b6ea490125ad8d9c6b9c561fca9bf731492 为基点复核。两条严重问题及三个较轻实现问题均属实，已修复。WAL 完整帧 CRC 错误继续拒绝恢复。版本仍为 0.10.1，持久格式和复制协议 3 不变，部署应以构建哈希区分。

## 不确定提交与计划切换分叉

COMMIT_UNKNOWN 时 committed=c 不能证明磁盘上没有完整 c+1。旧版关闭路径缓存 c，冷日志空页和切换位置比较又信任此缓存，确实可能把 c 作为安全切换边界。旧主稍后回放出旧 c+1，与新主写入的不同 c+1 并存，而纯序号比较不能发现。

修复集中在位置可信边界：

- 位置读取在 writer 锁下检查隔离状态；在线 COMMIT_UNKNOWN 返回错误，不能生成计划切换凭据，也不把此租户当成已追平。
- 手动关闭、空闲关闭只缓存健康引擎的位置。隔离引擎缓存置空，后续位置及日志请求必须重开并回放真实 WAL；恢复失败继续隔离。
- 完整 WAL 重放后也执行 fsync，再发布恢复位置；不能把仍只在页缓存中的未知尾帧当成已恢复持久位置。持续同步故障会使恢复和 fence 失败，修复故障并关闭失败实例后才能重试。
- 冷日志检查临时打开的引擎，使用既有运行身份和活动标记决定是否关闭，不误关并发复用的实例，也不因初始化前后探测留下冷引擎。

真实进程对照使用同一 [switchover-uncertain.py](../bench-results/replication-safety-20261106/switchover-uncertain.py)：先确认 100 条文档并复制，限定测试根目录注入 WAL fsync EIO，使一个含 8 条文档的完整原子批次返回 COMMIT_UNKNOWN；移除故障、关闭租户，在它重新打开前发起计划切换，新主再确认一条文档，最后比较两端全文、_rev 和位置。两个服务根和凭证均为独立测试实例。

| 结果 | 31851b6 | 修复后 |
|---|---:|---:|
| 两端报告的位置 | 均为 8 | 均为 9 |
| 旧主/新主当前文档数 | 108 / 101 | 109 / 109 |
| 旧主/新主保留不确定批次文档数 | 8 / 0 | 8 / 8 |
| 两端全文及版本哈希 | 不同 | 相同 |
| 旧主缺少升主后已确认文档数 | 1 | 0 |

旧版不仅存在结果未知记录的分歧，还会缺少新主后来确认的数据。修复后先恢复并复制完整位置，再升主写下一序号；所有已确认数据均保留。原始结果：[修复前](../bench-results/replication-safety-20261106/switch/before/result.json)、[修复后](../bench-results/replication-safety-20261106/switch/after/result.json)。单元回归另外直接构造“完整追加、同步未确认、writer 隔离”的状态，验证在线 fence 拒绝、关闭后日志不能返回旧位置空页、恢复后的 fence 包含完整尾帧。

修复后演练还在移除 EIO 前先关闭租户并尝试 fence，要求返回 IO_ERROR 或 COMMIT_UNKNOWN；故障修复后才重新打开并完成计划切换。这覆盖了“完整帧能够读回，但 fsync 仍失败”时不能公布可信恢复位置的边界。

## 活动句柄导致反复初始化

旧版在整份下载和验证后才发现本地不能关闭，随即释放源导出并删除本地下载；100 ms 后又从源重新复制。修复后：

- 下载前检查本地可关闭性，避免已知不能安装时要求源复制整库；失败按租户从 100 ms 指数退避至最多 30 s，成功后重置。
- 下载、同步、完整验证后保留副本，BUSY 时每 100 ms 重试安装，不重新下载。安装期间探测仍检查取消和持久来源，角色变化或日志缺口等失败才结束本次尝试。
- 已验证的本地检查点可以先交还源导出槽位，源端仅保留所需 WAL；每 30 s 用该持久位置探测日志。其他租户可以取得源槽位。after 不表示在线引擎已追平，实际位置仍是安装后的引擎位置。
- 状态接口增加 initializing、waiting_for_readers；sync_once 返回 Ok 仍只是完成一轮调度，不是追平承诺。

回归通过真实 HTTP 和检查点文件验证两个阶段：已有句柄时不向源请求快照且有退避；下载过程中新增句柄时保留同一任务及下载，只等待安装。等待期间另一个租户能完成初始化，释放句柄后原租户完成安装，全文和 _rev 一致。源快照请求次数及实际启动次数均不因安装等待重复增加。

发布竞态 BUSY 时仍可能重新复制本地 staging，但会复用远端下载。最多两个在途任务包含等待安装的任务；两者都被长期引用阻塞时仍需释放句柄。等待期间日志超过窗口会重新初始化，这是资源边界，不保证无限保留旧副本。

## 其余问题

| 问题 | 核实与处理 |
|---|---|
| 准备 panic 留下 generating | 属实。RAII guard 在展开时清掉本次占位并把已知路径加入清理队列；catch_unwind 回归后可再次创建导出并清理。进程 abort/OOM 退出仍由启动清理处理。 |
| 缺失保留 WAL 使 flush 永久失败 | 属实。仅对已刷盘保留历史的 NotFound 移除引用，复用一次采样的文件长度做回收，失效旧导出租约以免重装同一旧检查点。回归删除该文件后继续写入、刷盘、重开，原已确认数据仍在 SST 中。其他 I/O 错误继续失败；活跃 WAL/SST 缺失不按可选历史处理。 |
| 恢复期间配额被覆盖 | 属实。复制配额更新检查 restoring，准备期间返回 BUSY，后续目录同步再应用。回归验证准备期间不能修改，结束后能应用最新配额。 |
| WAL 完整尾帧 CRC 失败拒绝打开 | 保留原设计和既有回归。当前格式不能安全区分未确认尾部损坏和最后一个已确认帧损坏，不能盲目截断。 |

未引入跨帧哈希链。它需要新的持久历史锚点及协议/迁移设计；本轮通过拒绝不确定切换位置并强制恢复消除已复现路径，保留现有 generation、epoch、seq 和帧 CRC 校验，不能将此修复描述为所有同序不同内容历史的通用检测。

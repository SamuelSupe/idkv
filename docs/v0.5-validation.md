# v0.5 主从复制与切换验证

验证日期：2026-11-05。交付源码、Linux AArch64 服务/恢复工具、OpenAPI 3.1、配置和双进程示例。发行二进制不启用 `failpoints`。

本版实现一主一从异步复制，提供手动计划切换及显式故障升主。没有半同步、自动选举、自动隔离主机或自动修改业务入口；不能据此宣称已具备零数据损失的自动高可用。

## 实际环境

- OrbStack Ubuntu，AArch64，Linux `7.2.12-orbstack`，glibc 2.42。
- VM 可见 18 个 CPU、约 31.36 GiB 内存；数据目录在 `/var/tmp`，底层为 OrbStack 虚拟块设备上的 btrfs。两节点为同一 Linux 环境中的独立进程、独立目录，使用回环网络。
- Rust/Cargo 1.90.0。双节点示例每进程全局预算 4 GiB、默认每租户 512 MiB；示例将 memtable 调为 256 KiB、块缓存 8 MiB，便于触发刷盘，非峰值性能配置。
- 宿主仍承载其他任务；正式双节点示例与单机 HTTP 回归同时运行。没有声称独占 NVMe、跨物理设备故障隔离或等同原方案的 8 vCPU/16 GiB 性能环境。

原始环境：[v05-environment.json](../bench-results/v05-environment.json)。

## 自动化回归

完整测试 **55 项通过，0 失败**。包含原有 CRUD、索引、查询、DSL、HTTP、OpenDAL 备份、恢复和稳定性测试，以及 7 项复制集成测试和 1 项新增存储回放测试。原始日志：[v05-tests-final.log](../bench-results/v05-tests-final.log)。

新增验证保护以下行为：

| 场景 | 实际检查 |
|---|---|
| 原子增量 | 正文、索引、覆盖字段及删除一起到达；双向计划切换后继续写入与复制 |
| 并发切换 | 写线程与停写屏障竞争，所有已经成功确认的写入都能在接任节点读取 |
| 日志过期 | 限制保留窗口并反复刷盘/合并，落后节点安装检查点；租户删除也同步 |
| 权限与升主 | 复制凭证拒绝普通业务及强制操作；伪造停写 ID 无法升主；故障升主要求明确源身份和确认 |
| 持久角色 | 重开及过时初始配置不清除 fenced；调整保留配置不会恢复写权限 |
| 冷租户与读令牌 | 同步轮询不重新打开无变化的冷租户；等待正确历史/序号，拒绝错误历史；切换使旧游标失效 |
| 单租户损坏 | 源端损坏租户被报告为不可用，已有从库副本不被误删，健康租户仍能复制 |
| 回放边界 | 同页后续帧损坏时不先应用前面的帧；重复位置拒绝；重开后保留已应用位置和只读约束 |

`cargo fmt --check`、所有 target 的 Clippy `-D warnings` 均通过。日志：[格式](../bench-results/v05-fmt.log)、[Clippy](../bench-results/v05-clippy-final.log)。正式构建：[v05-release-final.log](../bench-results/v05-release-final.log)。

## 真实服务进程验证

[replication_demo.py](../scripts/replication_demo.py) 启动两个实际 HTTP 服务，每边独立 Store。两个租户各有 100 个约 1 KiB 负载文档、唯一覆盖索引和固定 Lookup；持续阶段完成 4000 次文档更新，整个脚本发出 48 个百条原子批次。

正式二进制运行通过了：检查点初始化、租户隔离、从库只读、增量及覆盖索引一致性、从库 SIGKILL 后重开追赶、A→B 计划切换、写后读等待、两边以旧配置重启后保持真实角色、B→A 切回、明确停止旧主后的故障升主与继续写入。

这里的 SIGKILL 在从库已追平后执行，随后主库继续写入，再重启从库验证恢复和追赶；没有将它描述成在每一条回放指令中间随机终止。最后的故障升主也在双方追平并停止旧主后执行，没有测量故障丢失量。

另一次 `failpoints` 构建的双进程运行额外验证：

1. 旧主持久化 fenced 后立即中止进程。重启仍拒绝业务写入，重试原切换成功。
2. 新主持久化升主结果、尚未返回响应时中止进程。旧主保持 fenced；新主重启保持 primary；重试完成旧主跟随，无需撤销停写状态。

证据：[正式双进程结果](../bench-results/v05-pair-release-final.log)、[两个切换故障点结果](../bench-results/v05-pair-fault-final.log)、[故障测试构建](../bench-results/v05-release-faults.log)。脚本退出会停止服务并删除其临时凭证。

正式运行的 48 个百条写批次 HTTP 延迟样本：P50 14.94 ms、P99 114.93 ms；单次已基本追平的计划切换耗时 15.65 ms。故障版运行对应为 9.80 ms、98.41 ms、8.98 ms。这些是回环功能测试中的少量样本，**不是吞吐基准、切换 SLA 或开启复制前后的性能对比**，不能外推百万/千万条或远程网络表现。

## 复现

在项目目录执行；数据目录必须不存在：

```sh
cargo test --locked --features failpoints -- --test-threads=1
cargo clippy --locked --all-targets --features failpoints -- -D warnings
cargo fmt -- --check

cargo build --locked --release --features failpoints --bin tenant-kv
python3 scripts/replication_demo.py --binary target/release/tenant-kv --root /var/tmp/tkv-fault-check --faults

cargo build --locked --release --bin tenant-kv --bin tenant-kv-restore
python3 scripts/replication_demo.py --binary target/release/tenant-kv --root /var/tmp/tkv-release-check
```

本次命令均在 OrbStack Ubuntu 中执行。复现正式二进制前应按最后一条构建命令去掉 `failpoints`。

## 尚未验证或实现

尚未进行独立主机掉电、真实设备持久化/损坏、跨机房网络分区、远程 HTTPS 代理部署、多日运行、大于内存的数据集复制或复制开销的系统性能对比。没有提供外部仲裁器，因此网络隔离时无法自动证明旧主已停止。

异步写成功仅代表主库本地持久化；故障升主可能丢失尚未复制的成功事务。必须先外部隔离旧主，旧主回归从新空目录重建。计划切换要求全部租户追平；单个不可用租户会阻止整体切换。具体运行约束、检查点空间和日志窗口见 [replication.md](replication.md)。

## 两个新回归

### 导出槽位及 WAL 租约

旧实现把一个导出检查点、固定位置的 WAL 租约和目标进程内存中的 transfers 表绑定。目标安装后重启会忘记 release ID；有效日志请求持续续租旧位置，其他租户一直 BUSY，旧检查点副本和 WAL 无法正常回收。原先 125 项测试没有覆盖“源还活着、目标遗忘传输状态”的行为。

修复后，源端先验证并生成日志页，再根据请求中的已持久化 after 推进租约。满足检查点位置的有效请求在导出状态锁可用时交还槽位并删除副本目录，锁忙则由后续请求推进，避免阻塞健康租户。追赶只保留独立 WAL 租约，不能根据尚未被目标确认的返回页尾提前回收。目标启动后即使已在源头位置，也探测一次空日志页，源端不再依赖目标记住 release ID。空页双方均可使用经过身份和状态检查的已知位置，避免空闲轮询反复打开冷引擎。

租约总时长最多 1 小时，传输/追赶活动续期最多 5 分钟。刷盘回收允许租约将保留 WAL 暂时扩展到正常窗口的两倍，超过则使该租户的租约失效、继续正常回收。失效句柄不能重新注册租约；分块 SNAPSHOT_EXPIRED、日志 LOG_GONE 会触发重新初始化。后台清理过期导出。规则及容量边界见 [复制文档](replication.md)。

真实黑盒对比使用相同脚本、各自全新 Store、1 MiB 日志窗口：源保持运行，SIGKILL 目标进程，在已复制的位置创建源检查点，继续写入，再用原数据目录启动新的目标进程。随后另一个租户请求导出，并持续覆盖 100 条 4 KiB 文档、刷盘/合并和追赶。

### 管理响应重新打开租户

旧版在 HTTP 路由前及生成历史响应头时调用 Store::tenant，确实会使 close、配额更新和 restore 刚关闭的实例再次打开，也影响只想查看关闭实例状态的请求。

历史头改为读取内部注册表及复制状态，复用与 TenantHandle 相同的 token 编码，不打开引擎。回归覆盖 close 后读取状态、更新配额及真实备份恢复，均保持 open=false；原先用户 history 字段的正文及头部边界测试继续通过。

证据：[旧版失败测试](../bench-results/review-followup-20261106/http-before.log)、[初步修复测试](../bench-results/review-followup-20261106/targeted-after.log)、[最终完整测试](../bench-results/review-followup-20261106/validation.log)。

## 较轻问题的处理

| 项目 | 核实与处理 |
|---|---|
| flush 与 compaction 共用维护锁 | 属实，保留串行发布约束。前台尝试刷盘不再长时间等待，但合并期间刷盘仍受阻，积压可导致快速背压；未拆锁，不宣称解决后台并发容量或硬延迟隔离。已在运维文档明确。 |
| 一致性等待取得 writer 锁 | 已修复，独立进度 Mutex/Condvar。回归持有 writer 锁不释放，20 ms 读取预算仍须在释放写锁前返回 DEADLINE_EXCEEDED。 |
| 在线索引背压等待过长 | 已修复无单次上限的等待。在线构建每次事务准入最多等待 5 秒，闭包执行前及取得写锁后检查期限；重启恢复继续按构建快照期限和停止标记等待。回归验证超时前没有执行事务闭包、维护推进后只执行一次。此期限不限制整次扫描或已进入的系统 I/O。 |
| 多主体共享游标总额 | 属实，保持既有容量策略。默认两个主体各 64 个游标会占满 128 总额，第三个主体分页被拒绝，点读仍有预留名额；API 文档明确不保证分页公平。 |
| 冷位置读取误关并发复用的引擎 | 已修复。只有本次读取确实打开了引擎、运行身份未变且活动时间未变时才尝试关闭。回归覆盖其他请求复用和关闭后重开，不误关新实例。 |

# 第四轮稳定性审查（2026-11-07）

审查对象为当前工作区：`81c46c6` 加上上一轮尚未提交的修复。源码及既有回归测试与第三轮最终验证指纹一致；原生 Linux 服务二进制 SHA-256 为 `f193543e4595867be1305a8967d9e879574e120b2ffdc453aaed32789a6fc18b`。本轮没有修改产品代码，仅新增审查脚本、证据和本文。

## 1. 中高优先级：小磁盘配额租户的合并无法推进，写入持续被拒绝

**已用真实 HTTP 服务复现三次。** 初始配置：全局内存 128 MiB、租户内存 64 MiB、租户磁盘 16 MiB、memtable 256 KiB、cache 0、target_sst 4 MiB、level_base 64 MiB、l0_trigger 4、l0_stop 12。没有磁盘写满或 I/O 故障注入；原生文件系统有约 266 GiB 可用空间。

先写入 1000 条随机 4 KiB 文档，再打乱顺序更新同一批键。三个运行中分别确认 508、419、374 次更新后，写入开始返回 `RESOURCE_EXHAUSTED: L0 backlog: retry after compaction`。此时没有活动快照；连续 30 次重试全部失败，删除现有文档同样失败，中止并重启服务后仍不能写入。后台持续报 `tenant disk quota/headroom exhausted`，L0 停在 12 个文件。

| 运行 | 实际租户目录占用 | 占原配额 | 提高配额后实测的新 SST 输出 | 原目录加新输出 |
|---|---:|---:|---:|---:|
| 首次 | 6,362,035 B | 37.92% | 4,210,427 B | 10,572,462 B |
| 重复 | 5,986,739 B | 35.68% | 4,210,409 B | 10,197,148 B |
| 带 ACK 日志复核 | 5,798,641 B | 34.56% | 4,210,331 B | 10,008,972 B |

仅将磁盘配额从 16 MiB 提到 64 MiB，保持数据、负载、内存及层级参数不变，合并即恢复，后续写入成功。表中输出大小是提高配额后的实测对照；原目录加输出及 64 KiB 元数据余量仍低于原 16 MiB 配额，未直接采样原配额下的合并峰值。

**原因**：[合并选取](../src/storage/engine/maintenance.rs#L392)会将 L0 键范围覆盖到的目标层文件全部加入任务，缺少按租户配额限制的输入范围；[空间准入](../src/storage/engine/maintenance.rs#L440)又要求额外预留 `3 × 所选 SST 总大小 + 65536`。首个运行选中 30 个 SST、总计 6,352,280 B，仅额外预留就达 19,122,376 B，已经超过整个 16 MiB 配额，维护无法通过准入。达到 l0_stop 后，[写入协调器](../src/storage/engine/write.rs#L73)在执行事务前拒绝普通写入和删除，任务选择及空间需求便不能自行改变。重试和重启都不会消除这组持久化文件。

文档已经提示保守预留可能提前背压。本轮确认的是：小磁盘租户与较大的层级/输出参数组合，可以在不足 40% 占用时进入需要运维干预的持续写入停顿。这不是对默认 100 GiB 配额下触发比例的验证，不能外推该比例。

**建议**：按租户容量限制每次合并的键区间和输出规模，避免宽范围 L0 任务一次覆盖过多目标层文件，并维持实际输出的磁盘计费。持续维护失败需要明确告警，不能只让调用方按普通临时背压重试。

证据：[主复现](../bench-results/deep-audit4-20261107/compaction-result.json)、[重复复现](../bench-results/deep-audit4-20261107/compaction-repeat-result.json)、[ACK 复核运行](../bench-results/deep-audit4-20261107/compaction-journal-result.json)、[有效 Manifest](../bench-results/deep-audit4-20261107/compaction-manifest.json)、[准入计算](../bench-results/deep-audit4-20261107/compaction-calculation.json)。另有 2000 条文档的初步运行复现同类停顿，主要容量结论采用上述三次 1000 条运行。

## 2. 中优先级：fs 备份清理遗留空目录，积累后列表和 prune 都无法工作

**真实清理加加速目录夹具，重复确认两次。** 使用受支持的 fs 备份后端，创建两份实际备份，再执行 `prune(keep_last=1)`。任务正常完成、报告删除一份，但其 UUID 快照目录仍然存在且为空。

[prune](../src/backup/repository.rs#L170)只删除 `COMPLETED` 和 `manifest.json`；[列表](../src/backup/repository.rs#L90)对每个目录先累计 visited，超过 4096 立即失败，之后才判断该目录有无有效完成备份。历史空目录因此一直占用列表预算。

将真实清理产生的空目录形态加速扩充到总共 4097 个 UUID 目录、仅保留一份有效完成备份后：

- 列表返回 `RESOURCE_EXHAUSTED: remote backup listing limit`。
- 新的 prune 任务同样失败，因为它首先调用同一个 summaries；它无法自行清掉导致超限的历史。
- 仅删除已经核实为空的目录，列表恢复，保留备份的完整文件校验成功。

本轮没有执行 4097 个完整备份周期。两次正常备份和一次真实 prune 确认残留来源，目录夹具验证累积后的失效边界。持续保留最近少量备份的正常清理流程也会不断增加历史目录；在通过 forget 回收本地终态任务、每 5 分钟创建一次备份的安排下，4097 次创建约对应 14 天。这里的周期换算不是长期运行实测。

**影响**：有效备份仍保留，但无法列举，常规清理也无法继续，远端存储会继续积累。已知 UUID 的直接校验路径仍可使用；没有观察到现存完成备份被删除或损坏。该缺陷已确认于 fs 后端，本轮未测试 S3 的长期目录行为。

**建议**：清理已剪除快照的 UUID 目录，为旧残留提供有界回收，并将有效备份数量约束与垃圾扫描进度分开处理。

证据：[首次运行](../bench-results/deep-audit4-20261107/backups-result.json)、[重复运行](../bench-results/deep-audit4-20261107/backups-repeat-result.json)。

## 验证范围与复现

全部运行使用 OrbStack Ubuntu Linux aarch64 和原生 `/var/tmp` Btrfs。脚本仅管理自己创建的目录、租户及进程，结束时停止进程并删除测试凭证。合并复现三次均核对全部 1000 条最新已确认状态；带日志运行额外保存逐次 ACK 和最终读取的 SHA-256/修订号，独立重算一致，差异为 0。

从仓库目录运行，root 必须是尚不存在的新目录：

```sh
python3 -B bench-results/deep-audit4-20261107/probes.py --case compaction --documents 1000 --root /var/tmp/idkv-audit-compaction-new --binary /path/to/tenant-kv
python3 -B bench-results/deep-audit4-20261107/probes.py --case backups --root /var/tmp/idkv-audit-backups-new --binary /path/to/tenant-kv
python3 -B bench-results/deep-audit4-20261107/verify-evidence.py
```

原始输出、ACK 日志、读取指纹及数据文件均位于 [deep-audit4-20261107](../bench-results/deep-audit4-20261107/)。本轮另核查了角色屏障、生命周期发布、关闭/恢复、I/O 工作池、游标及保留回收的相关边界，没有将未复现推测或已说明的限制列为新缺陷。本轮未重新运行全量测试或长期生产资格负载，也未验证 macOS、真实硬件掉电及真实内核写回错误。

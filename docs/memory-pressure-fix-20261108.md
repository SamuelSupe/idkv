# 全局内存压力下写入停滞修复（2026-11-08）

修复 [极端场景审查](extreme-audit-20261108.md) 中确认的 P1：多个租户的 memtable 都低于各自阈值时，全局预算先耗尽，自动维护不触发刷盘，手动刷盘也申请不到工作内存。基线为 `2969a142de632936219bd0bd96984fe1a724ad52`。

## 实现

- Store 在既有全局上限内保护少量刷盘容量，大小为 `min(global / 8, 4 * (max_document_bytes + block_bytes) + 2 MiB)`；默认约 6.06 MiB。普通预算不使用该部分，实际分配仍共用原来的全局及租户计数器，没有绕过硬上限。
- 当计费内存达到普通容量约 7/8 时，非空 memtable 即使低于本租户阈值也进入刷盘；正在合并的任务也检查这一条件。
- 只有一个压力刷盘能取得保护容量，竞争时不阻塞等待；正常低压力刷盘仍可并行。容量用于 SST 编码、文件打开和版本发布；SST 后续读取及缓存恢复普通预算，不能继承回收权限。BUSY 重试不扫描清理尚未生成的 SST，也不重复增加合并的磁盘预留。
- 复制接收和回放的单页预检改用扣除保护容量后的上限。确实放不下的日志页转入检查点恢复，避免仍按配置总额判断而无限重试。

正常负载仍按原 memtable 阈值刷盘。该修复不使所有请求永不限流：资源紧张时仍可能返回 RESOURCE_EXHAUSTED/BUSY；写入已完成但响应内存不足时，既有 RESPONSE_UNAVAILABLE 语义保持有效，必须用原操作 ID 和 history 安全重试。长期快照、无法容纳的超大记录和持续磁盘故障仍有各自限制。保护容量未实际使用时不计入 `memory_bytes` 已分配量。

## 原场景前后验证

OrbStack Ubuntu AArch64，数据位于 `/var/tmp` 的原生 Btrfs。原 HTTP 脚本、64 MiB 全局、64 MiB 租户、16 MiB memtable、零缓存和 8 个负载租户加 1 个轻租户保持不变，没有通过降低阈值规避问题。

| 项目 | 旧版本 | 修复版第一次原脚本复测 |
| --- | ---: | ---: |
| 初次背压后持续尝试写入 | 20.00 秒 | 20.13 秒 |
| 此期间成功 / 失败 | 0 / 1,692 | 1,170 / 0 |
| 手动 checkpoint | 8/8 内存不足 | 8/8 成功 |
| 关闭重开及随后强杀重启的数据核对 | 1,486 条最终状态一致 | 2,199 条最终状态一致 |

修复版在前面的装载阶段曾出现 8 次短暂内存拒绝，随后自行恢复；上述持续写入发生在手动 checkpoint 和关闭租户之前。两个版本的最终文档数量不同，是脚本在压力后能够完成的写入不同，不能把它们作为同一批数据的吞吐比。

第二次不带操作 ID 的原脚本在一个写入完成后收到 RESPONSE_UNAVAILABLE，因其仅接受 RESOURCE_EXHAUSTED 的断言而停止。这轮不计作完整压力演练通过。之后使用原备份配置重开该库，核对已写入确认日志的 **1,603 条文档**，内容与修订号全部一致；结果未知的那次写入未计为已确认。

进一步使用 [带固定操作 ID 的 HTTP 探针](../bench-results/memory-pressure-fix-20261108/http-progress.py)，每次拒绝或响应不可用都在 5 秒期限内用相同请求退避重试，保持原内存配置，并在每次大文档写入后插入一次轻租户写入：

- 完成 **2,500 次 32 KiB 文档写入和 2,500 次轻租户写入**，共 5,000 次最终确认。
- 141 次 RESOURCE_EXHAUSTED、7 次 RESPONSE_UNAVAILABLE 均恢复，未出现永久停滞。没有重试 COMMIT_UNKNOWN。
- 负载/轻租户写入 P99 分别为 28.097 / 29.326 ms，最长为 185.608 / 612.086 ms，包含重试等待。
- 轻租户重复更新同一键，最终共有 **2,501 条文档状态**；在线读取和重启后核对全部一致。验证逐租户读取并关闭，故该探针的强杀发生在这些租户已关闭之后；真正未关闭实例的崩溃恢复另由恢复测试和混合负载覆盖。

这轮与回归套件共用 VM，延迟只是当次观察，不是隔离的版本性能基准或 SLA。

## 回归验证

最终源码执行 `cargo test --locked --features failpoints --lib --tests -- --test-threads=1`，**219 项全部通过**：90 项库测试、129 项集成测试。

新增及扩展的行为边界：

1. 9 个租户句柄一直保持打开，完成 1,500 次大文档写入和 1,500 次轻租户写入，不依靠空闲关闭；逐条核对当前文档及重开后的数据。在独立旧源码上运行同一个测试，第 1,003 次负载写入因全局内存不足、重试仍无法推进而失败。
2. 人为占满普通全局预算，低于 memtable 阈值的已确认数据仍能刷盘；之后继续占满普通容量，SST 读取必须被正常拒绝，释放压力后数据完整，证明回收权限未泄漏给读取。
3. 回收预算独占、全局硬上限、租户配额、缩容、释放计费保持一致。
4. 64 MiB 全局预算、16 个覆盖索引下，448 KiB 文档仍可增量同步，512 KiB 和 768 KiB 文档转检查点并追平，核对内容及已确认修订号。512 KiB 边界曾暴露复制使用旧总额预检的问题，修复后通过。

运维和持久化说明已更新：[内存与背压](operations.md)、[复制](replication.md)、[存储格式说明](format.md)。没有修改 WAL/SST 格式或新增配置项。

## 混合负载与故障恢复

最终发布二进制还运行了原有 `qualification.py`：5,000 条负载文档、200 条轻租户文档，20 秒基线、70 秒同时写入/合并/复制/备份/GC、25 秒双节点强杀重启后的恢复负载。混合和恢复阶段分别有 5/3 个采样区间同时观察到后台任务进展，5 次在线备份完成校验，GC 回收 4,696 条记录。主从重启前后及最终各 5,200 条当前文档全部一致，最终备份离线恢复的 5,000 条负载文档也一致。轻租户写入 P99 为 12.326 / 15.998 / 30.550 ms（基线/混合/恢复），各类前台操作没有最终失败；这些是当次负载下的观测，不构成延迟 SLA。

重新执行真实 ext4 满盘、WAL append EIO、WAL fsync EIO 三种故障。每例故障前 2,000 条已确认文档全部保留；8 条结果未知的写入在安全重试前分别可见 0/0/8 条，用原操作 ID 重试后各 2,008 条全部一致。EIO 使用限定测试目录的系统调用注入，不代表真实设备写回或断电行为。

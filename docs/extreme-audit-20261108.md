审查对象：`2969a142de632936219bd0bd96984fe1a724ad52`。本轮确认 **1 个 P1 可用性问题**，没有确认新的 P0 或已确认数据丢失。覆盖当前存储、资源预算、HTTP、复制和生命周期路径，不仅检查上一提交的差异。审查阶段只新增复现脚本和审查证据，未修改生产实现。

## P1：多个租户未达到各自刷盘阈值，就能耗尽全局内存并阻断写入

### 实际复现

通过发布二进制的普通 HTTP API 操作，无外部内存预留、长期快照、缓存占用或故障注入。配置被服务正常接受：全局内存 64 MiB、每租户 64 MiB、memtable 16 MiB、cache 0。创建 8 个负载租户和 1 个轻租户，轮流向负载租户写入 32 KiB 文档。

第一阶段成功确认 1,012 条文档（含轻租户的 1 条）。此时全局计费内存为 **66,748,584 / 67,108,864 字节**，各负载租户仅约 7.93–8.00 MiB，全部低于 16 MiB 阈值，且 `flush_bytes=0`、`snapshots=0`、`maintenance_error=null`。继续写少量 128 B 文档消耗余量后，轻租户也收到 `RESOURCE_EXHAUSTED: global memory budget exhausted`。

| 检查 | 第一次独立运行 | 第二次独立运行 |
| --- | ---: | ---: |
| 继续轮流尝试小写入的观察时间 | 6.02 秒 | 20.00 秒 |
| 失败请求 | 522 | 1,692 |
| 成功请求 | 0 | 0 |
| 手动 checkpoint | 8/8 返回全局内存不足 | 8/8 返回全局内存不足 |
| `/health` | ok | ok |
| 手动关闭租户 | 9/9 成功 | 9/9 成功 |
| 关闭重开后逐条核对 | 1,486 条一致 | 1,486 条一致 |
| SIGKILL 重启后逐条核对 | 1,486 条一致 | 1,486 条一致 |

对照只把 memtable 阈值改成 **1 MiB**：相同的 2,500 次负载写入全部成功；加轻租户共 2,501 条，关闭重开和 SIGKILL 重启后全部一致。

这是全局写入停止推进和跨租户干扰，不是物理数据丢失。6/20 秒是实测观察窗口，不能表述为已测试永久无法恢复。默认空闲回收为 300 秒；本轮没有等待该期限，也不能把空闲回收当作有持续请求或嵌入式长期句柄时的回收保证。

### 源码依据与修复方向

- [maintenance.rs](../src/storage/engine/maintenance.rs) 的 `needs_flush()`（3–7 行）只检查本租户冻结表或 memtable 阈值；`maintain()`（17–19 行）没有全局内存高水位触发。
- [write.rs](../src/storage/engine/write.rs) 的事务提交（143–146 行）继续申请同一预算。全局预算耗尽后，小写入也不能把某个租户推到自动刷盘阈值。
- [cache.rs](../src/storage/cache.rs) 的 `reserve()` 只尝试释放本引擎缓存；本场景 cache 为 0，没有可释放缓存。
- [sst/writer.rs](../src/storage/sst/writer.rs) 的 `TableWriter::new()`（37 行）还需预留 1 MiB 输出内存，后续编码也需工作内存。没有独立保障回收进度的预算。实测手动 checkpoint 返回内存不足；故障后的 8 个负载租户各有两份 WAL，符合已轮转但尚未成功生成 SST 的路径。没有把具体报错指令位置当作运行时栈跟踪结论。

建议在共享内存接近高水位时，提前调度占用较大的可刷盘租户，并为受限数量的刷盘任务保留有界工作内存；前台背压应早于回收工作内存耗尽。仅在彻底耗尽后强制调用 `flush()` 不足以解决。需保护的回归行为是：多个租户均低于各自阈值、总预算吃紧时仍能释放内存，轻租户在有界时间内恢复小写入。

降低 memtable 阈值是本次对照证实的缓解方式，不是所有文档大小、租户数量及快照占用下的通用修复。默认 4 GiB/大量租户的同类风险来自源码推断，本轮实际复现使用 64 MiB 缩放配置。

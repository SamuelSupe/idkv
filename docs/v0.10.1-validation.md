# v0.10.1 客户端路由与后台维护优化验证

本版本后续的并行负载、真实 ENOSPC、WAL I/O 错误与重启检查单独记录在[生产资格验证](production-qualification.md)，故障升主流程见[恢复演练](recovery-drill.md)。以下优化对比的环境和数字保留原测量口径。

验证日期：2026-11-06。本轮完成读取路由缓存、并发发现合并、排队读取取消，以及磁盘计费扫描移出写锁。Query JSON、DSL、WAL/SST、注册表和复制协议保持不变。项目在 GitHub 使用名称 `idkv`，现有 Rust 包、导入及命令名保持兼容。

## 实现与正确性边界

- 同一 Client 及其 clone 共享一秒路由缓存，同时发生的冷读取共用一次发现；没有独立刷新线程或无界路由表。
- 缓存中的角色、history、applied_seq 仅用于选择节点。原始最低位置继续发送给服务端，数据响应继续确认读取控制能力。缓存显示从库落后时优先主库；即使缓存中两边都落后，也不能据此拒绝可满足请求的主库。
- 可重试节点错误清除旧缓存；旧请求不能清除其他请求已刷新的缓存。每个配置节点最多执行一次数据请求；最低历史冲突、预算、取消、权限及续页错误仍直接返回。写入不复用读取路由授权，所有 SDK 游标仍绑定签发节点。
- SST 正文、索引块和扫描预取任务在排队等待期间检查读预算。已经取消、超时或被放弃的任务在出队时跳过 I/O；多块预取在块间检查。写任务没有这种放弃行为，调用方不再等待也必须执行。
- 维护锁固定活跃 WAL 身份和文件发布；目录扫描不持有写锁。扫描后用短写锁取得当前 WAL 实际长度并发布总量，因此不漏掉期间的 WAL 增长。旧快照释放造成的过期 SST 消失允许跳过，已引用文件仍由原打开、校验和恢复路径验证。
- 保留磁盘校准频率、空间预留及提交/Manifest 发布顺序。后台仍优先刷盘；本轮没有新增优先级调度器、改变合并策略或实现多段有序合并与索引在线替换。

详细使用约定见 [读取控制](read-controls.md)、[资源预算](operations.md) 和 [指标](telemetry.md)。`scheduler.cancelled_jobs` 是详细 JSON 指标，目前未汇总为 Prometheus 指标。

## 前后对比方法

旧版为修改前保存的 v0.10.0 源码，新版为 v0.10.1，使用独立 Cargo target 构建 release。客户端基准源码在两边相同。两轮执行顺序分别为旧→新、新→旧，期间不并行运行构建或其他基准。

环境为 OrbStack Linux AArch64、Rust 1.90、18 个可见 CPU、约 31.4 GiB 内存。数据在 `/tmp` tmpfs，实际经过文件读取、WAL、SST 和工作队列，但不是 NVMe 或物理设备持久化测试。详细配置、源码指纹和全部指标见 [环境](../bench-results/v0101-environment.json) 与 [汇总 JSON](../bench-results/v0101-comparison.json)。

表格使用两次独立运行指标的中位数；P99 是两次 P99 的中位数，不是合并样本后的分位数，也不构成置信区间。

### HTTP 客户端

真实本机主从 HTTP 服务，读取已同步的小文档，16 个客户端并发，预热一次。无延迟用例每轮 160,000 次读取；慢发现用例每轮 8,000 次，仅给主库 `/context` 人工增加 25 ms，不给数据路径增加延迟。

| 指标 | v0.10.0 | v0.10.1 |
|---|---:|---:|
| 无注入延迟：P50 | 0.573 ms | 0.198 ms |
| 无注入延迟：P95 | 0.848 ms | 0.313 ms |
| 无注入延迟：P99 | 1.084 ms | 0.399 ms |
| 无注入延迟：读取吞吐 | 26,950/s | 78,266/s |
| 无注入延迟：发现请求数/轮 | 320,000 | 4 |
| 主库发现延迟 25 ms：热读取 P99 | 33.161 ms | 0.618 ms |
| 主库发现延迟 25 ms：发现请求数/轮 | 16,000 | 0 |
| 主库发现延迟 25 ms：首次冷读取 | 27.857 ms | 28.168 ms |

根因是旧客户端每次读取都等待两个节点的发现请求。复用短时缓存删除了这部分重复网络与服务端处理，并将并发刷新合并。无注入延迟的 P99 降低约 63%，吞吐约为原来的 2.90 倍。首次冷发现仍需探测节点，缓存不能消除冷请求的慢节点等待。无延迟新版测量持续约两秒，实际经过缓存刷新；带延迟的新版热测量短于一秒，收益主要体现已有缓存命中。

证据：[无延迟旧 1](../bench-results/v0101-client-zero-before-1.jsonl)、[新 1](../bench-results/v0101-client-zero-after-1.jsonl)、[旧 2](../bench-results/v0101-client-zero-before-2.jsonl)、[新 2](../bench-results/v0101-client-zero-after-2.jsonl)；[慢发现旧 1](../bench-results/v0101-client-delay-before-1.jsonl)、[新 1](../bench-results/v0101-client-delay-after-1.jsonl)、[旧 2](../bench-results/v0101-client-delay-before-2.jsonl)、[新 2](../bench-results/v0101-client-delay-after-2.jsonl)。

### 扫描与后台维护

相同的 80,000 条种子数据，每条含 4 KiB 难压缩内容，合计 312.5 MiB payload；引擎租户内存预算 64 MiB，缓存 8 MiB。每轮独立复制种子目录，四种读取并发执行 20 秒，同时约每秒更新 1,000 条文档，最终刷盘、合并并完整校验。

| 指标 | v0.10.0 | v0.10.1 |
|---|---:|---:|
| 主键尾部范围 P99 | 1.298 ms | 1.305 ms |
| 唯一索引范围 P99 | 0.573 ms | 0.584 ms |
| 非唯一索引 IN P99 | 0.386 ms | 0.396 ms |
| 256 输入 Lookup P99 | 1.771 ms | 1.820 ms |
| 主键范围吞吐 | 1,565/s | 1,581/s |
| 唯一索引范围吞吐 | 4,450/s | 4,425/s |
| 索引 IN 吞吐 | 9,115/s | 9,051/s |
| Lookup 吞吐 | 877/s | 874/s |
| 写锁累计等待 | 2.279 ms | 0.392 ms |
| 每轮成功更新/背压拒绝 | 20,020 / 0 | 20,020 / 0 |
| 最终引擎计费内存 | 8.14 MiB | 8.12 MiB |
| 估算写放大 | 8.392 | 8.480 |

写锁累计等待降低约 83%，是目录扫描移出写锁的直接观测结果；绝对值仅为毫秒量级，不能将此比例当作提交延迟的改善比例。读取吞吐变化约 −0.7% 至 +1.0%，P99 增加约 0.6% 至 2.8%。本轮没有证明普通扫描尾延迟改善，新增排队预算检查存在开销，不声称全面零回退。

最后一次查询的读块/扫描量在两版一致：主键范围 26/100、唯一范围 2/100、IN 2/4、Lookup 10/512；后三者正文回读均为 0。写放大按 `(WAL + flush + compaction write) / document bytes` 计算，含最终合并。

证据：[旧 1](../bench-results/v0101-mixed-before-1.jsonl)、[新 1](../bench-results/v0101-mixed-after-1.jsonl)、[旧 2](../bench-results/v0101-mixed-before-2.jsonl)、[新 2](../bench-results/v0101-mixed-after-2.jsonl)。

### 复制追赶

真实主从积压 65,536 笔事务，四个读线程按合计 4,000 次/s 发起从库 Lookup，另有轻量租户并发追赶。每轮校验主从最终全部 1,024 个键一致。早期 16,384 笔试跑因不足 1,000 个尾延迟样本被基准拒绝，未纳入结果。

| 指标 | v0.10.0 | v0.10.1 |
|---|---:|---:|
| 追赶耗时 | 280.459 ms | 269.640 ms |
| 并发 Lookup P50 / P95 | 4.271 / 31.750 μs | 4.917 / 16.749 μs |
| 并发 Lookup P99 | 107.563 μs | 83.917 μs |
| 轻量租户追平时间 | 4.261 ms | 2.916 ms |
| 从库 I/O 任务数 | 1,523 | 1,403.5 |
| 从库峰值计费内存 | 7.34 MiB | 7.77 MiB |

四次有效运行分别采样 1,061、1,139、1,011、1,179 次 Lookup。新版 P99 的单轮范围为 66–102 μs，旧版为 96–119 μs；第一轮新版略慢，第二轮更快。因此这里只报告小样本局部测量，不能认定普遍的复制尾延迟收益。当前复制仍为异步，故障升主的数据损失边界不变。

证据：[旧 1](../bench-results/v0101-replication-before-1.jsonl)、[新 1](../bench-results/v0101-replication-after-1.jsonl)、[旧 2](../bench-results/v0101-replication-before-2.jsonl)、[新 2](../bench-results/v0101-replication-after-2.jsonl)。

## 复现与限制

```sh
cargo build --locked --release --example client_perf --example range_perf --example replication_perf
target/release/examples/client_perf /tmp/idkv-client-run 10000 16 0
target/release/examples/client_perf /tmp/idkv-slow-discovery-run 500 16 25
target/release/examples/range_perf /tmp/idkv-seed seed 80000 1
cp -a /tmp/idkv-seed /tmp/idkv-mixed-run
target/release/examples/range_perf /tmp/idkv-mixed-run mixed 80000 20
target/release/examples/replication_perf /tmp/idkv-replica-run 65536 4 1000
```

每次使用新目录，旧新版本使用独立构建目录和相同参数。更快设备若采样不足，基准会失败，需继续增加积压或调整两版相同的到达率。

取消是协作式机制，不能中断已进入的系统 I/O；部分元信息读取仍在调用边界检查。被取消的读取占据队列和预留内存直到出队，队列上限仍为 4,096。没有对百万/千万数据、NVMe 冷缓存、真实掉电、多日运行或真实云 S3 重新资格测试。数据量大于引擎预算，不等于超过主机物理内存。本轮不创建 GitHub Release。

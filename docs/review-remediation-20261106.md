# 2026-11-06 报告核实与修复

此文保留 75e2938 验证时点的结果。后续复查确认该提交新引入了导出租约和 HTTP 管理响应两个回归，当前修复及新的验证结果见 [复查修复报告](review-followup-20261106.md)；下文的旧租约描述及旧构建指纹不代表当前实现。

按用户附件逐项追踪调用链，区分可修复缺陷、性能限制与必须保留的数据安全契约。本轮验证使用当时尚未提交的工作区，包含此前备份进度优化及演练材料；以下结果对应该验证时点的构建，后续 GitHub 提交不改变其指纹或测量边界。软件版本仍为 0.10.1，部署时应以构建哈希区分，并同时更新主从两端。

## 高优先级

| 原编号 | 核实结果及处理 |
|---|---|
| 1 读队列拒绝导致写入器隔离 | 共享调度器饱和时风险属实；未声称默认单次 HTTP MultiGet 就能达到 4096。4096 水位只拒绝新读任务，持久化任务仍入队。WAL 追加区分入队前失败与执行后失败；前者退还磁盘预留，不污染写入器，后者继续 COMMIT_UNKNOWN 隔离。新增饱和队列下另一租户连续写入回归。读负载仍可能增加共享设备等待，不承诺硬延迟隔离。 |
| 2 用户 history 污染响应头 | 属实。删除从任意 JSON 结果推断历史的逻辑，只使用 Store/Tenant 内部历史，并以可失败的 HeaderValue 转换防御。测试非法换行/Unicode 与伪造值，覆盖 Get、MultiGet、DSL，响应正文仍保留用户字段。 |
| 3 游标耗尽全部快照 | 属实。游标总额降为 max_snapshots/2，同一主体为 max_snapshots/4（至少 1），默认 128/64。HTTP 绑定稳定 subject；嵌入式使用共同的默认主体。max_snapshots=1 时不保留游标。验证两主体达到各自上限、总额达到上限后，其他主体点读仍可用；释放后可重新分页。 |
| 4 初始化和租户错误拖住复制 | 属实。初始化/LOG_GONE 重建改为最多两个独立任务，不持 cycle 锁。租户错误单独退避，健康租户继续有界多轮追赶；显式 sync_once 仍报告该轮错误。检查点从生成开始固定 WAL，传输与追赶续租，追至日志页确认的源位置后释放。生成期间不因耗时超过五分钟丢失日志；转为传输后无活动五分钟过期。仍只有一个源导出，其他初始化受 BUSY 限流。 |
| 5 写锁覆盖同步和 Manifest I/O | 属实，优化主要路径。组提交释放写锁执行 fsync，只确认开始同步前捕获的序号；后来暂存的数据另行同步。维护锁串行化 Manifest 变更，刷盘/合并的最终发布不占写锁。WAL 轮转期间创建日志及发布映射仍互斥，未声称完全消除写锁内 I/O，也没有把本轮修复当作新吞吐基准。 |
| 6 递归删除占注册表锁 | 属实。锁内完成 journal、rename 与最终注册发布，并固定当时可回收的路径；锁外递归删除，清理出错仍保留原有租户隔离。新增权限故障回归验证发布已经完成、清理失败后仍不能继续写，重开后恢复正确备份。恢复同样处理旧目录。不能简单用过时的注册表副本扫描未来出现的目录，否则可能误删并发恢复文件。 |
| 7 长复制持有复制屏障 | 属实。恢复复制、完整验证移出屏障，最终发布才重新取得权限并检查源/角色；删除旧目录也在屏障之外。安装前发生升主或源变化会拒绝旧传输发布。 |
| 8 重启索引重建耗尽维护池 | 属实。独立单线程工作者承担重建，不占刷盘/合并池；分批扫描与回放检查停止标记。停止时保留 BUILDING 供下次恢复，不把正常停止误记为构建失败。单个不可中断系统 I/O 仍受操作系统约束。运行回归另发现构建已发布 BUILDING 后遇到 L0 背压、错误回写也被背压拒绝的情况；后续构建批次改为在调用事务闭包之前有界等待，释放写锁和复制屏障，仍检查构建快照期限及停止。普通写入保持立即背压，已执行事务不自动重放。 |

## 中优先级

| 原问题 | 结论与处理 |
|---|---|
| 已删除租户占 16384 上限 | 已修复，统计未删除注册。用 16384 个持久删除注册验证仍可新建并写入。墓碑继续保留以防 UUID 复用，整体重写及 16 MiB 元数据格式上限仍是容量边界，未通过删除身份记录掩盖。 |
| 完整 WAL 帧 CRC 错误无法打开 | 行为属实，保留拒绝恢复。当前格式无法区分未确认尾部损坏与已确认最后一帧损坏。盲目截断会丢已确认数据；原有回归明确覆盖 ACK 后翻转最后一字节必须报 CORRUPTION。只截断不完整尾帧。 |
| 预留失败清空块缓存 | 已修复。逐帧按需释放，预留成功即停止。回归验证只需一帧空间时其他三帧仍可读。若确实需要全部可释放空间，仍可能全部淘汰。 |
| 前台 flush 排在整个 compaction 后 | 已修复前台等待路径。flush_if_needed 尝试维护锁，忙则交还后台；超过缓冲/配额上限返回可重试背压。显式管理 flush/compact 仍可等待完成。 |
| 内存表逐个扫描热点版本 | 已修复。按快照序号二分选每个 key 的可见版本，再移动到下一 key，保留 tombstone 与旧快照语义；快照之后新增但不可见的 key 仍计一次扫描，另有回归保护预算边界。扩展已有范围/读预算回归，区分内存跳过历史与实际扫描条目。 |
| 超时重试占满复制许可 | 已修复重复请求排队路径。源正在生成导出时，其他 snapshot 请求用 try_lock 立即返回 BUSY；原请求即使断线，既有阻塞工作者仍完成可复用导出。没有实测 100 GB、超过 30 秒的实际导出。 |
| Tokio 线程做文件 I/O | 已修复长阶段。初始化文件、哈希、同步、验证、清理放在有界阻塞传输工作者；绑定源、目录同步、引擎打开、角色持久发布同样交给阻塞池。 |
| fence 累积打开所有冷租户 | 已修复保留路径。读取冷租户位置后尝试立即关闭新打开的实例，不积累整节点打开文件。活动句柄使关闭 BUSY 时仍保留；没有执行 16384 个真实大租户的 FD 压测。 |
| 慢租户打开阻塞维护协调器 | 已修复，协调器及维护入口尝试 slot 锁，跳过忙租户。打开仍在该租户 slot 内串行化，以避免两个 Engine 操作同一目录。 |
| 每 100 ms 扫 catalog | 已修复无变化时的重复扫描。独立重建工作者按目录提交序号缓存检查结果；业务文档写入不触发此扫描。 |
| 时钟锚点永不刷新 | 修复正常校时累计漂移：成功采样刷新，失败不刷新。大跳变继续 CLOCK_SKEW，需校正时钟，必要时重开租户；未自动把未知墙钟当成可信业务时间。新增渐进漂移与跳变拒绝回归。 |
| 索引构建长快照占空间 | 属实，是在线构建一致性约束。保留构建截止时间、内存/磁盘配额及背压；提前丢弃快照会漏建索引。运维文档说明容量与超时，不以缩短默认期限冒充消除成本。 |
| SDK 每次写串行发现 | 写入路径属实，读取此前已有缓存。write_batch 复用同一秒级共享路由缓存，失败时失效；显式获取写上下文仍实时探测。稳定操作 ID 与历史条件决定是否允许自动重试，原请求不会换 ID。新增 clone 间顺序写只发现一次及复制数据核对。 |

## 低优先级

- **磁盘预留后 pin 失败**：属实。先取得快照再预留磁盘，入队前追加拒绝另有退还；回归验证反复失败不增加磁盘用量。
- **2 ms 轮询**：改用提交条件变量与有界定时等待，提交唤醒复用现有通知。同步库接口仍阻塞调用者线程；周期性醒来用于检查取消、角色与历史变化，未声称释放了所有 HTTP 等待许可。
- **MultiGet 与冻结内存表锁**：分区尾部检查只遍历该分区的输入索引，去掉 K×P 重复循环。冻结表为旧只读实例，其读锁不阻塞新活动内存表写入，不据此做无必要的锁重构。
- **优雅停机**：SIGTERM/SIGINT 先公开 503 就绪状态并保持监听 2 秒，再停止接收并最多排空 HTTP 请求 30 秒，超时非零终止。新增真实服务进程信号测试，确认 503 可观察且正常退出。不能用 HTTP 排空期限替代进程管理器对永久 I/O 挂起的最终期限。
- **非索引排序每页重扫**：属实，是有界 top-K 与固定快照分页的当前执行策略。保留扫描/时间预算，文档要求高频分页配置排序索引；没有把内存保存完整结果集作为无成本修复。

## 验证

在 OrbStack Ubuntu Linux AArch64 / Rust 1.90、普通用户 livesite 下，完整 125 项测试通过，包括真实 SIGTERM、慢初始化隔离、WAL 保留、权限故障与进程崩溃恢复。格式检查、全目标 Clippy -D warnings、发布构建通过，见 [validation.log](../bench-results/review-remediation-20261106/validation.log)。中间的 validation-before-index-admission.log 保留了权限字面量的首次 Clippy 拒绝以及改成八进制后通过的记录；这一修正不改变运行行为。此前测试/Clippy 记录也保留：旧扫描预算断言随二分语义修订，测试模块位置修正；后续发现的不可见 key 计费及清理失败隔离都补充回归后重新运行完整测试。

最终 Linux 发布二进制 SHA-256：`537a50f11dfcb90e40a5a0b2781470f024a2e9e6f98fc74c5bddf366ba611c03`。负载、三项磁盘故障、HTTP 对照使用同一构建。保留的修复前二进制为此前备份进度优化后的构建 `87448b98…c62ea`，并非最初 Git 提交。

### HTTP 黑盒对照

同一脚本、分别建立的新 Store：修复前 Get/MultiGet 被 `forged-token` 覆盖历史头，换行/Unicode 文档触发 500；修复后均为 200，历史头与内部 context 一致，正文数据原样保留。将 max_snapshots 明确设为 8，旧版保留 8 个未消费游标后点读 429；新版同一主体保留 2 个后拒绝新游标，点读仍 200。见 [原始结果](../bench-results/review-remediation-20261106/http/result.json) 与 [复现脚本](../bench-results/review-remediation-20261106/http-regression.py)。

### 并发、重启与备份恢复

沿用 qualification.py 的 20000 条主租户（4 KiB 正文）与 200 条轻租户，30 秒基线、120 秒五类任务并行、30 秒重启恢复负载。共 10845 个已确认批次、165154 次文档写操作；每个 key 按最高已确认版本重建模型，核对源与副本的完整正文和原始 _rev。重启前后 20200 条当前文档哈希一致，最终主从一致，独立 Store 恢复的 20000 条主租户文档与检查点模型一致，全部 acknowledged_mismatches=0。见 [负载结果](../bench-results/review-remediation-20261106/load/result.json)。

并行阶段 4 次备份完成 create/verify/prune；实测 13 个采样区间同时推进刷盘、合并、复制、备份和 GC，恢复阶段另有 5 个。杀进程时处于 checkpointing 的备份，重启后同一任务持久状态为 completed。重启至可写且副本追平为 89.85 ms，只代表本机自动流程。恢复阶段完整备份循环计数为 0，不计为额外成功循环；最终另完成备份校验与导入。GC 排空时 next_expiration_ms=null，lag=0，回收 7388 条记录。业务请求无错误；另有 556 次管理任务 BUSY 重试，不将它们算作业务失败，也不将它们隐藏为所有 HTTP 都成功。

### 存储故障

使用独立 256 MiB ext4 loop 卷制造真实 ENOSPC；WAL 写入/同步 EIO 由限定路径的 LD_PRELOAD 拦截实际系统调用。每项先确认 2000 条文档，再触发故障：均返回 COMMIT_UNKNOWN，后续写入被隔离。重启后已确认文档各缺失 0；未知批次分别可见 0/8、0/8、8/8，沿用原操作 ID 与历史重试，均收敛到 2008 条且无重复。重启到安全重试分别 35.16、30.94、35.68 ms。见 [故障结果](../bench-results/review-remediation-20261106/faults/result.json)。这不模拟设备掉电或控制器谎报持久化。

### 复算与边界

[validate-evidence.py](../bench-results/review-remediation-20261106/validate-evidence.py) 从压缩回执/延迟/采样重新计算批次、文档操作数、P99 及五类任务重叠，核对源/副本/备份哈希、故障结果、恢复任务与源码指纹；[summary.json](../bench-results/review-remediation-20261106/summary.json) 保存通过结果。采样、回执、原始日志、源码指纹与已跟踪文件相对验证基线（base-commit.txt）的 diff 在同一证据目录；diff 包含此前尚未提交的备份优化，不能当成本轮独立提交；新增脚本/文档以实际工作区文件和指纹为准。中间构建的失败与通过记录均保留，最终以本段 SHA 和 summary 为准。

没有执行 100 GB 恢复、16384 个真实大租户、跨机房、真实 S3、多日稳态或物理断电。本轮确认并修复正确性/隔离问题，不解除注册表大小、在线索引快照空间、非索引分页成本、共享磁盘尾延迟或异步复制 RPO 的边界。

# 后台备份进度与写入尾延迟优化

本轮在 v0.10.1 工作树上优化备份任务进度更新；软件包版本、HTTP、复制协议和持久化编码不变。未创建 Git 标签或远程发布。此前完整资格验证的历史数字保留在[生产资格报告](production-qualification.md)，本页单独记录归因与前后对比。

## 实测结果与数据核对

2026-11-06 完成旧版→优化版→旧版回测三组完整负载，每组前台负载 14 分钟，共 **42 分钟、2,085,103 次已确认文档写操作**。三组主从当前数据、重启前后数据、最终备份恢复均通过成功回执模型核对，已确认业务数据缺失和不一致均为 0。

优化版轻租户 P99 比两轮旧版低 **36.47%–42.04%**，P99.9 低约 **39.20%–67.19%**；主租户批次 P99 低 24.07%–28.28%。主租户实际更新速率高约 0.81%–1.86%，仍是固定目标附近的闭环完成速率，不是最大吞吐能力。三组完成相同数量的并行备份循环，GC 最终排空，没有通过减少后台工作换取该结果。

**最大停顿没有稳定消除。** 优化版与旧版回测都出现约 700 ms 的轻租户写入，仍受共享存储及必要同步的影响。本轮改善集中在常用尾部分位数，不构成租户 IOPS、带宽或最坏延迟的硬隔离承诺。

基线中还没有备份进度更新，依然存在明显差异，因此不能把所有端到端差异都归因于该修改。旧版回测的并行尾延迟再次高于优化版，和独立的同步调用减少证据方向一致；但这里只是一组 A→B→A 顺序测试，百分比是本次观察值，不是置信区间。

恢复阶段的更深尾部也不是全面改善：优化版主租户 P99.9 为 **176.492 ms**，高于两轮旧版的 139.424–150.347 ms；优化版轻租户 P99.9 为 188.918 ms，位于旧版 175.853–265.145 ms 区间内。120 秒复测的极尾样本较少，本轮没有证明恢复阶段所有尾部指标均无回退。

### 业务数据与备份恢复

- 三组各自核对 20,200 条主从当前文档、原回执 `_rev`、完整分页、MultiGet、覆盖 Lookup 和引擎完整性。写操作包含合法覆盖，模型按回执重放每个主键最后一次已确认状态。
- 三组在备份 checkpointing 阶段终止双节点，重启前后业务数据指纹一致，原中断任务恢复为 completed。恢复至业务写入成功且副本追平分别为 77.110、71.250、114.406 ms；这些单次值不用于宣称恢复性能加速。
- 三组最终备份各恢复 20,000 条主租户文档到新 Store，并按相应 checkpoint sequence 核对。
- 另外分别恢复三份持续写入期间生成的备份：每份 20,000 条文档全部与检查点模型一致。这些主键在检查点后均已再次成功更新，因此验证的是过去的业务状态与修订号，不仅是文档总数。
- 任务管理中的 BUSY 按原单租户串行契约有界重试并记录，不将其误报为业务写入失败。源码中的 WAL 提交确认、检查点和远端完成标记的持久化顺序保持原契约。

原始记录在 [bench-results/tail-latency-20261106](../bench-results/tail-latency-20261106/)：[三组对比](../bench-results/tail-latency-20261106/comparison.json)、[源码与二进制指纹](../bench-results/tail-latency-20261106/source-provenance.json)、[代码补丁](../bench-results/tail-latency-20261106/source.patch)。每组保留全部延迟样本、状态采样、压缩成功台账、阶段汇总、备份结果、并行备份恢复校验和服务日志；`compare.py` 从原始延迟重新核对分位数，`analyze.py` 重算资源/吞吐摘要。

## 定位证据

历史并行负载中，轻租户出现接近一秒的写入，但对应 5 秒窗口的累计 I/O 排队时间仅为毫秒量级，不能直接归因为队列排队。用相同负载运行旧版，并对指定演练目录内的 write/pwrite64/fsync/fdatasync 系统调用记录耗时后，观察到轻租户的 WAL 同步占据主要请求时间。例如：

| 诊断运行中的轻租户写请求 | WAL fsync 系统调用 |
|---:|---:|
| 155.727 ms | 150.917 ms |
| 131.627 ms | 127.036 ms |
| 117.938 ms | 114.456 ms |

这些调用已经开始在 I/O worker 内执行；简单提高队列优先级不能中断已进入内核的同步。重租户 SST、WAL、备份对象和任务元信息也在同一 Btrfs 虚拟磁盘上同步，存在跨租户的存储竞争。系统调用墙钟耗时不单独证明设备、文件系统或 CPU 调度各自占比；这里不把它扩展为某个内核锁的确定诊断。

进一步追踪代码发现：旧版对上传、校验和恢复中的每个文件都调用持久化 `update`，即使只改变 processed_files/uploaded_bytes/reused_bytes，也原子改写任务 JSON 并同步文件与父目录。任务恢复实际依赖已持久化的阶段、检查点 manifest、内容校验和与远端完成标记，进度在重启时本来就重置。

## 聚焦修改

- 增加仅修改进度计数和 updated_ms 的内存更新路径；三个逐文件调用点使用这一条路径。
- 任务入队、阶段切换、检查点清单、远端完成标记和终态仍使用原持久化顺序；终态持久化时包含完整进度。
- 继续使用原 WAL 同步、提交确认、I/O 调度与备份限速。没有引入调度器、优先级配置或新依赖。

实时进度通过现有 HTTP/Rust API 可见；内部任务 JSON 中的计数在阶段或终态保存。该内部文件不是实时监控接口。失败与重启后的计数重置规则保持不变。

## 独立同步调用核对

对同样的 2,000 条种子文档执行一次创建和一次完整校验，两版各产生 12 个备份文件。只统计该运行 control/backup-jobs 下的元信息同步调用：旧版 62 次，优化版 14 次，减少 48 次（77.4%）。差额正好对应两个阶段各 12 个文件、每次进度更新的文件和目录同步。

这项检查验证被消除的同步开销，不是生产 P99 的加速倍数；WAL、SST、备份数据和完成标记的同步未计入这个数值。

## 正确性与回归

完整 `cargo test --locked --offline --features failpoints -- --test-threads=1` 的 111 项测试通过。扩展已有备份中断用例：在对象已经上传、内存进度已更新但终态尚未发布时中止进程；重启后从持久检查点继续，复用已有对象，完成完整 verify。该回归保护“丢失进度不能丢失续传依据，也不能误报完整备份”的实际边界。

格式检查、全目标 Clippy `-D warnings` 与 release 构建通过。源码修改仅涉及备份进度路径和上述回归，历史演练与资格验证文件继续保留。

## 前后对比方法

保留旧版服务与恢复工具的独立副本；优化版使用相同 Rust 1.90、Cargo.lock 和 release 参数构建。正式对比串行执行旧版→优化版→旧版回测，不并行构建、测试或运行其他压力。加入回测是因为无备份基线也有明显波动，不能把所有前后差异都归因于修改。两版都运行原 `scripts/qualification.py` 的默认负载：20,000 条 4 KiB 文档、200 条轻租户文档，120 秒基线、600 秒并行、双节点重启、120 秒恢复后复测，以及最终 GC 排空和备份恢复。

全局/租户计费内存分别为 512/128 MiB，缓存 8 MiB、memtable 2 MiB、4 个 I/O worker；后台同时运行合并、异步主从复制、20 秒历史保留、每 5 秒发布和 16 MiB/s fs 备份。主租户目标 800 条更新/秒，轻租户 20 条/秒；从库 Get/20 输入 Lookup/索引查询目标分别为 200/100/50 次/秒。闭环负载完成速度会影响实际备份循环数与成功请求数，两者都需报告。

两版分别用成功回执台账重放当前主键状态，逐条核对主从、重启前后、最终备份恢复的正文与原修订号，并检查索引、Lookup、完整分页和引擎完整性。正式百分比不使用带系统调用记录器的诊断运行。

本轮为共享 OrbStack Linux VM、Btrfs 虚拟磁盘与回环网络，OS 缓存未清空。单次顺序对比不能代表置信区间、裸机存储性能或租户 P99 硬 SLA。

# 主从复制与切换（v0.5）

本版本实现传统单源、异步主从复制，默认部署一主一从。主库独立完成 WAL 持久化后确认写入，从库拉取有序原子批次并落盘回放。数据复制不是多数派提交，不自动选主。

已实现：检查点初始化、WAL 增量、重连续传、日志过期后的检查点重建、租户目录/配额/删除同步、从库只读、计划切换、显式故障升主、写后读等待和复制状态。半同步、自动故障转移、多源复制、级联复制及多从拓扑编排尚未实现。当前网络服务只配置一个对端，切换面向这对节点。

## 快速运行一主一从

最短的完整例子会生成自己的凭证、启动两个进程、创建两个租户、写入和校验索引、来回切换、验证重启及故障升主，然后停止两个进程。目录必须不存在：

```sh
cargo build --locked --release --bin tenant-kv
python3 scripts/replication_demo.py --binary target/release/tenant-kv --root /var/tmp/tenant-kv-pair-demo
```

脚本最后会执行一次明确的故障升主；它先停止旧主，并在结束时关闭两边。若之后继续使用演示数据，应从最终主库重新初始化另一节点，不能直接启动故障前的旧主。结果和服务日志保存在指定目录，临时 token 和权限文件在退出时删除。

长期运行使用 [主库配置](../examples/replication-primary.json) 和 [从库配置](../examples/replication-replica.json)。为这对节点生成新的 `cluster` UUID，两边填相同值。`peer_url` 分别指向另一节点；`role` 仅决定首次初始化角色。

```sh
openssl rand -hex 32 > admin-token.txt
openssl rand -hex 32 > peer-token.txt
chmod 600 admin-token.txt peer-token.txt
cat admin-token.txt | target/release/tenant-kv token-hash
cat peer-token.txt | target/release/tenant-kv token-hash
```

将两个输出填入两边的 `auth.json`：

```json
{
  "tokens": [
    {"sha256":"管理员 token 的 SHA-256","subject":"operator","tenant":null,"role":"admin"},
    {"sha256":"复制 token 的 SHA-256","subject":"replica-peer","tenant":null,"role":"replication"}
  ]
}
```

复制凭证仅允许读取复制状态、日志、检查点及验证已有切换凭据的升主操作，不能执行普通业务 API、停写、强制升主或发起切换。两边需要相同的业务租户授权策略；应用权限文件及 S3 凭证不会通过业务日志复制。

在两个终端分别启动：

```sh
target/release/tenant-kv serve --root /var/tmp/tkv-primary --auth auth.json --replication-config examples/replication-primary.json --listen 127.0.0.1:8080
```

```sh
target/release/tenant-kv serve --root /var/tmp/tkv-replica --auth auth.json --replication-config examples/replication-replica.json --listen 127.0.0.1:8081
```

从库初始化要求空 Store。已有单机库可以作为主库启用复制。建议两边使用相同引擎配置和版本，并预留检查点暂存空间。远端 `peer_url` 必须使用 HTTPS；回环地址允许 HTTP。TLS 由服务前的代理终止，客户端验证服务端证书，Bearer 复制凭证认证对端请求；当前没有内置双向 TLS 配置。

## 写入、读取与可靠性边界

- 客户端成功只保证当前主库本地 WAL 持久化。异步复制未传出的成功写入可能在主机/磁盘丢失后丢失。
- 从库对业务写入返回 `READ_ONLY`，包括 HTTP、DSL、现有 `TenantHandle` 和经其取得的 `Engine::transact`。刷盘、合并及受验证的复制回放可以继续。
- 源日志包含正文和索引的同一原子批次，从库不重新执行 DSL、不生成业务 UUID、不自主重启索引构建。索引构建和逻辑 GC 由主库产生日志。
- v0.8.1 的复制回放使用维护磁盘门槛，可以占用前台写入预留的 20% 空间，以便在高占用时继续应用删除和回收进度。租户总配额、内存和 L0 背压仍然生效；这不保证实际设备写满时还能追赶。
- 从库查询使用本地已应用快照，允许延迟。每批 MultiGet/Lookup 使用一个快照。
- 升主/重新跟随后复制历史 epoch 改变，旧分页游标和写后读令牌失效。故障升主可能发生数据回退，调用方还必须丢弃旧 CAS 版本、重新读取；`_rev` 数字本身不是跨数据历史的事务标识。
- 原有未知提交结果语义保留。普通写入已有同 WAL 提交的 operation_id 回执；启用租户保留后，还必须保存首次提交的 retry_token。超时不能视为未执行，回执过期也不能自动换 token 重做。

复制使用 `(cluster, epoch, tenant UUID, database generation, sequence)` 确认日志身份及顺序，不使用文件路径作为租户授权。正常重连从本地恢复出的已提交序号继续；文件/偏移只是加速定位的游标，缺失、重复、越界和校验失败不能静默跳过。重复发送已经应用的整页会返回位置冲突，客户端重新读取本地位置，不再次应用。

v0.7 写回执的 history/rev 可直接作为后续读请求的 `X-TKV-Min-History`、`X-TKV-Min-Seq`，等待和读取跨历史时失败。旧的复制等待接口仍接受节点状态的 epoch UUID，不接受新的完整 X-TKV-History 字符串：

```text
POST /v1/tenants/{tenant}/replication/wait
{"epoch":"节点状态中的 epoch UUID","seq":123,"timeout_ms":5000}
```

达到位置后返回 `{"applied_seq":123}` 或更大值。最多等待 5 秒；未追平返回 `REPLICA_LAG`，历史不同返回 `REPLICATION_CONFLICT`。此操作需要该租户 read 权限。它提供写后读，不承诺全局最新；等待成功后仍应处理节点切换或查询错误。Rust 使用 `TenantHandle::wait_replication`。

## 计划切换

向当前主库发送全局管理员请求：

```sh
curl --fail-with-body -H "Authorization: Bearer $(cat admin-token.txt)" -H 'Content-Type: application/json' -d '{}' http://127.0.0.1:8080/v1/replication/switchover
```

流程为：检查接任节点角色和来源 → 等待已经进入写入协调器的操作完成 → 持久化旧主 `fenced` 状态和所有租户最终位置 → 从库验证旧主的持久停写凭据并追平 → 持久化新主角色和新 epoch → 旧主验证接任记录后转为从库。

v0.5.2 在首次停写前要求对端为同集群的另一从节点，绑定当前主库的 node/epoch，或为尚未绑定的空从库；对端报告不可用租户时拒绝切换。配置错误会在停写前返回 `REPLICATION_CONFLICT`，原主仍可写。本地有尚未恢复的删除/恢复 journal 时，不将这些租户当作已删除并生成不完整的最终位置，而是返回 `UNAVAILABLE`。预检查不能消除之后的网络故障和状态变化；一旦持久停写，仍遵循下述重试契约。

停写凭据绑定集群、旧主节点/epoch、指定接任节点及租户位置。复制凭证不能伪造升主请求中的完整凭据：HTTP 升主接口只接受凭据 ID，并向配置的旧主重新获取和核验。

该流程支持原请求重试。若网络中断、追赶超时或进程崩溃，旧主可能保持 `fenced`，此时业务写入明确拒绝。修复连接、恢复相关进程后重新提交同一旧主上的 `/switchover`，不应通过修改启动配置重新放开旧主。

完成后更新应用写入口。数据库不自动修改 DNS、负载均衡或客户端地址。需要切回时，在当前主库调用相同接口。

也可以分步执行以下管理员操作，适合接入自己的运维系统：

| 接口 | 请求与含义 |
|---|---|
| `GET /v1/replication/status` | 节点角色、对端历史、租户位置、不可用租户、最后复制错误 |
| `POST /v1/replication/fence` | `{"target":"目标 node UUID"}`；持久停写并返回凭据 |
| `POST /v1/replication/promote` | `{"fence":"凭据 UUID"}`；向旧主验证并追平后升主 |
| `POST /v1/replication/follow` | `{}`；原主验证其指定接任者后跟随 |

单次升主追赶循环上限约 120 秒；状态读取、追赶及最终升主遇到 REPLICA_LAG、BUSY、REPLICATION_UNAVAILABLE、RESOURCE_EXHAUSTED 或 DEADLINE_EXCEEDED 时，在该窗口内等待 50 ms 后重试完整验证。身份/协议冲突、数据损坏和不确定持久化结果不会按瞬时错误重试。普通对端响应头等待上限为 30 秒，节点间 promote 响应头为 150 秒；响应体使用独立的 30 秒停滞超时，外围代理也可能先超时；这些都不是失败即回滚。观察双方持久状态并重试。

## 故障升主

首先在外部真正隔离旧主：停止其服务/主机，或封禁全部业务写入通道及可能重新启动它的管理程序。仅更换 DNS 或入口地址不能做到这一点。本引擎没有远程关机或租约仲裁能力。

然后读取候选从库的状态，复制其中的 `node.source`，向候选从库提交：

```text
POST /v1/replication/force-promote
{
  "source":{"node":"旧主 node UUID","epoch":"旧主 epoch"},
  "old_primary_fenced":true,
  "accept_data_loss":true
}
```

这两个布尔值是管理员对实际操作和风险的明确声明，系统无法据此验证旧机器已经关机。故障升主创建新历史，可能缺少旧主已确认但未复制的事务。旧主不能自动回归：保留其文件用于核对，在新的空目录从新主重建副本。不要把双方额外事务自动合并。

完整的隔离证据、旧节点新目录重建、丢失写入核对及实际恢复计时，见[故障恢复演练与操作流程](recovery-drill.md)。脚本分别验证已追平与暂停复制的场景，不将已追平场景的零丢失结果当作异步复制的 RPO 保证。

## 资源、初始化与运维

默认轮询 50 ms；v0.5.1 在仍有积压且本轮成功时直接继续下一轮，追平或源节点级错误后才等待轮询间隔。租户级错误只对该租户按 100 ms 至 30 s 指数退避，健康租户有积压时继续推进。每租户每轮最多拉取 256 个批次或约 1 MiB，所有租户轮到一次后再处理下一页；v0.6.1 在一次目录刷新后最多继续 8 轮，轮次边界检查已用时间，达到 10 ms 就结束该轮；后台复用最多 100 ms 的状态响应，同一响应只做一次成功的目录协调。单个请求或一整轮本身仍可能超过 10 ms，该值不是请求耗时上限。每个日志页仍独立验证源 epoch 和租户存储代次，并使用该页报告的最新源位置；单个较大原子批次仍受 64 MiB WAL 格式及预算限制。传输使用有界 JSON/base64 页面，尚未实现原生二进制长连接流水线。接收和回放按页顺序执行，当前没有独立无限接收队列。一次源日志请求最多固定 128 个文件描述符，头校验和读取在释放写锁后执行。v0.6.1 对当前 WAL 文件复用最多 64 KiB 的顺序读取缓冲，缓冲计入租户及全局预算；必需帧或输出编码需要内存时释放预读缓冲并从准确位置续读。读取严格限制在请求固定的文件前缀，逐帧校验仍然执行。

回放先验证整页，再合并为一次 WAL 追加和一次同步；每个原始事务仍保留自己的帧、序号及校验和。崩溃时可以恢复该页中的完整事务前缀，再请求其余部分，不将整页误作跨事务原子提交。普通文档变化不使从库的集合/索引元信息缓存失效；集合、索引和 Lookup 定义变化仍使缓存失效。从库回放也累计 commits、wal_bytes 和 document_bytes。v0.6.1 将已经暂存的记录直接移入内存表，免去记录的第二次键复制及值引用计数增加，保留新键与旧键的一次树查找；小事务仍以最多 8 条记录分段插入，大事务仍以最多 64 条分段，提交发布继续等待 WAL 同步。

本地崩溃恢复允许丢弃最后一个 WAL 中 WAL-SYNC 水位之外的坏魔数、帧头/载荷 CRC 失败或不完整帧及其后缀；即使同一页更晚的事务帧完整，也不会越过损坏位置回放。网络接收与日志导出的帧校验继续严格拒绝损坏，不使用这条恢复容错规则。WAL-SYNC 并非逐提交水位，设备损坏与撕裂写的区分限制见 [格式与恢复](format.md)。

复制 HTTP 的小请求预留 2 MiB 输入空间；响应按实际编码长度预留，发送期间保留输出计费。收到的页面在回放完成前保留解码预算，源端按实际帧大小预留，避免用整个 WAL 文件大小估算小页。回放仅为原始解码字节和暂存记录预留租户内存，避免重复按 base64 体积计费。整页先验证，未追加 WAL 前因租户现有内存占用不足时先刷盘并重试一次；单页本身超过租户预算或刷盘后仍无法容纳时，使用有界检查点初始化恢复，不无限重试同一页。接收缓冲按实际容量计费，扩容时覆盖新旧缓冲同时存在的峰值；JSON 树预算与原始输入只各计一次。若接收、解析或回放的单页工作集本身超过扣除刷盘保护容量后的普通全局预算，也转检查点初始化；不能用配置总额代替实际准入上限，否则会反复拒绝同一日志页；全局瞬时压力、磁盘或 L0 背压仍按资源错误处理，不将未知提交自动重放。检查点也需要暂存空间和校验内存，资源始终不足仍可能无法初始化，应监测 reinitializations、last_error 和初始化退避。64 MiB 全局预算下的小数据初始化、增量和切换已通过测试，不意味着该预算能处理所有 64 MiB 原子帧。

`log_retention_bytes` 默认每租户 256 MiB，可配 1 MiB–1 TiB，修改配置后重启服务生效，不改变持久角色；只限制已经刷盘的保留 WAL，活跃/未完成刷盘 WAL 仍受原有磁盘配额和背压约束。保留日志计入租户磁盘占用。刷盘发布新 Manifest 后才能删除淘汰日志；落后从库遇到 `LOG_GONE` 会重新安装检查点。

缺失租户及 LOG_GONE 初始化在独立的有界传输任务执行，最多两个在途（包含等待安装的任务），不持有复制 cycle 锁；健康租户可继续增量复制。下载前及验证后的安装阶段分别取得租户安装闸门，阻止新 tenant() 及旧句柄上的新普通请求继续进入，已有请求可收尾。持续重叠的短读因此能够排空；等待超过 1 秒时撤销该引擎快照并释放缓存游标，后续续页返回 CURSOR_EXPIRED。每次排空等待最多 10 秒，超时释放闸门恢复旧数据读取；已校验副本保留 30 秒后重试一次安装，再次超时才释放初始化名额并退避，下载前排空超时则直接退避；已经进入的系统 I/O 和原子发布不受此等待期限中断。关闭闸门会唤醒 wait_context/wait_replication 并返回 BUSY。闸门不覆盖整个网络下载，异常、取消和成功均由 RAII 释放。失败按租户指数退避，从 100 ms 增至最多 30 s，成功后重置。源端只在导出状态锁内预留一个生成占位，打开租户、生成检查点和计算 SHA-256 均在锁外执行；完成或失败后交还占位，panic 展开也由 RAII 保护释放。生成期间重复快照请求立即返回 BUSY，其他租户的日志进度和租约续期仍可推进。文件写入、校验、同步及角色发布运行于阻塞工作者。

检查点在 `replication-work/` 暂存，包含业务数据，不放入 `control/`。源节点最多保留一个正在传输的导出检查点；传输使用 1 MiB 分块和文件 SHA-256。导入验证文件白名单、身份、校验和、序号和 SST 后才发布。目标需要一份新增检查点的可用暂存空间及额外余量，已有在线目录在切换完成前仍占用空间；源端检查点上限为租户磁盘配额，源端也执行物理空闲空间检查。

检查点校验使用源端公布且通过兼容性检查的租户实际配额；节点默认租户配额不限制已经调大配额的复制租户。已有租户重建时，临时校验与在线实例共用租户计费器，节点全局预算始终生效。离线灾备 import 仍按目标节点的默认租户配额导入，不采用源端配额。

检查点生成期间固定 WAL。目标下载、同步并完整验证副本后，即可提交匹配租户、generation、epoch 且 after 不低于检查点位置的日志请求，源端在短锁内交还导出槽位并将副本目录加入后台清理队列，追赶只保留独立 WAL 租约。after 此时可以对应尚未发布、但已持久化并验证的本地检查点，不代表在线引擎已追平。安装遇到活动句柄时保留下载目录，在每次 10 秒排空窗口内每 100 ms 重试安装，两次窗口之间开放读服务 30 秒；等待期间每 30 s 用该持久位置探测源日志，不重新请求整份检查点；角色/来源变化、取消或 LOG_GONE 等失败会退出并按退避重试。已验证的私有 import 目录通过同文件系统 rename 移交到 staging，不再复制第二份完整检查点；空间检查需要一份新增检查点及 maintenance_reserve_free_bytes，旧在线目录占用仍保留到发布和清理。恢复期间配额变更返回 BUSY，避免覆盖准备阶段捕获的配额；无变化的目录同步仍可继续。

源端租约下界随 after 单调推进，不提前推进到本次返回日志的末尾。目标进程重启后会探测各租户的已应用位置，即使已追平也发送一次空日志请求；源端交还槽位不依赖目标内存中的快照 ID。追平后释放 WAL 租约。等待安装期间仍受日志字节窗口约束；日志已不足时必须重新下载，不能无限保证旧副本可用。长期保留的嵌入式 TenantHandle、直接取得的 Engine/Snapshot 引用仍需由调用方释放；不能安全强制析构调用方持有的 Arc。正常短请求的连续到达不再延长安装等待；底层不可返回的 I/O 仍不保证固定排空期限。

检查点生成及活跃传输没有固定总时长上限，低写入大租户不会仅因生成或传输超过一小时而失效。准备工作完成后，传输和追赶租约每次有效活动续期 5 分钟，空闲过期的租约不能复活。刷盘回收时，包括准备阶段在内，租约的保留上限在创建时取 `max(2 * log_retention_bytes, min(当时租户已计费用量, 租户磁盘配额 / 4))`，给大检查点与其规模匹配的窗口。超过单个租约上限时只撤销阻止回收的该租约，不清空其他进度较新的租约；失效句柄不能续期复活。此上限不包含活跃/未完成刷盘的 WAL，租户磁盘总配额和原有背压仍生效。失效分块返回 SNAPSHOT_EXPIRED，日志缺口返回 LOG_GONE，目标重新初始化。需按检查点大小、传输耗时和写入速率配置足够日志窗口；窗口不足可能反复初始化，不能保证持续落后副本最终追平。

Service::start 启动的后台循环定期清理失效、交还或失败导出。目录递归删除及目录同步在导出锁外执行，不计入日志请求；清理失败保留路径、记录错误并在后续轮次重试，已生成的日志页仍成功返回。进程启动也会清理遗留目录。服务命令自动启动该循环，嵌入式使用 Service 时也应启动它。健康的活跃导出和追赶租约会阻止源引擎关闭，关闭/删除可能返回 BUSY。租约只持有独立的保留状态，不引用引擎；检查、续期和释放不会取得引擎所有权或执行其析构 I/O。源 WAL 出错时，在同一把保留状态锁下标记恢复并撤销全部旧租约，业务恢复不依赖对端下载完成、release 或后台目录清理。检查点复制每个 256 KiB 块、哈希每个 1 MiB 块检查故障，取消失效准备；复制完成后先释放在线句柄再计算哈希。取消在块边界协作执行，不能中断已进入的系统 I/O；外部持有的句柄仍须释放。

重开后的引擎不继承旧下载或追赶租约，旧会话的进度请求不能恢复原保留窗口。下载分块会收到 SNAPSHOT_EXPIRED，导出被回收后也可能是 NOT_FOUND。已交还检查点、只追赶日志的副本仍可继续读取正常保留窗口内的 WAL；所需历史被回收后返回 LOG_GONE，才重新初始化。失效导出由后台回收，副本按既有过期/失败流程重试。已完成的检查点文件仍有一致的持久位置，但复制导出必须同时具备有效 WAL 租约，不能只因文件完整而继续传输。网络中断后可能重新复制检查点，不承诺分片断点续传。

`/v1/replication/status` 的 initialization_attempts、initialization_failures、reinitializations 分别记录本服务实例启动以来实际启动的初始化尝试、已收集的失败以及由 LOG_GONE 触发的重建尝试；正在进行或被并发上限拒绝的重复调度不增加计数。Prometheus 同时提供 `tkv_replication_*_total` 三个计数器。反复重建的告警建议见 [遥测文档](telemetry.md)。

状态中的 initializing 列出在途租户 UUID，waiting_for_readers 列出下载前排空或已保留检查点、等待安装的租户。租户状态中的 installing 表示安装闸门正在阻止新请求。initialization_errors 按租户 UUID 保存最近一次初始化失败原因（包括 reader drain 超时），成功后清除；不会因下一轮同步无错误而丢失。安装发布位置时在同一 slot 锁内释放闸门，位置已可见时新的读取即可进入。sync_once 成功只表示这一轮处理完成，初始化任务可能仍在后台；判断追平须核对实际租户位置，不能仅以 Ok 或初始化计数不增长为准。

COMMIT_UNKNOWN 的在线引擎不能提供切换依据，fence 拒绝创建安全切换凭据。关闭时不缓存旧 committed 序号；后续打开校验实际 WAL。健康关闭保存的 WAL-SYNC 水位匹配 WAL 身份和完整长度时可复用；其余 WAL 须以普通写入重建新 inode、同步文件和目录之后才能确认位置。只有重建遇到 ENOSPC 时可降为只读，读取只暴露 SST 及 WAL-SYNC 覆盖的连续持久前缀；未被水位覆盖的回放帧在空间恢复前不可见。该租户列入 unavailable，日志导出、位置确认和计划切换均拒绝，不能公布只读回放位置为 durable。释放空间后 close/reopen 完成恢复。隔离引擎旧引用释放后自动关闭，不依赖空闲计时；打开 IO_ERROR 缓存 1 秒，之后重试。CORRUPTION 与 UNAVAILABLE 保持隔离。

未发生变化的租户只报告已知位置，不因轮询反复打开冷引擎。冷日志读取若仍有后续页会保留打开的引擎，后续页复用它；由冷导出打开的引擎在多页追赶中复用，追平或读取失败后尝试关闭；原本已打开的实例不会因此关闭。并发请求、句柄或 WAL 租约仍引用它时保留，交给默认 300 秒的空闲回收。源端单个租户损坏会显示在 `unavailable`，其已有从库数据保留，健康租户仍可复制。v0.5.1 中一个租户因活动句柄等原因无法删除或更新配额时，会记录错误并跳过该租户，仍同步其他健康租户；只有显式 sync_once 调用返回该轮租户错误，后台循环不会因此将健康租户限制为每个轮询间隔一页。移除租户时清理其复制定位缓存。计划切换要求整个候选节点的全部租户完整追平，不能忽略不可用租户。

v0.5.2 将尚未恢复的租户生命周期 journal 同样列入 `unavailable`，不会通过目录缺失向从库宣布已经删除。重启按持久状态解决后，才继续普通目录同步和计划切换。

在复制启用期间，普通备份保持可用；业务 restore/import 会明确拒绝，避免悄悄回退源历史。恢复到新 Store 后再初始化新的复制关系。S3 备份/清理仍只配置一个执行者，角色切换不自动迁移备份执行权。

节点身份、角色和切换凭据持久化于 `control/replication.json`。启用复制后根注册表升级到 v2，v0.4 的 `Store` 会拒绝打开该根目录；WAL/SST 业务格式仍为 v1。不能删除复制状态文件或降级注册表来取消只读状态。初始化期间的中断以只读状态打开，重新提供复制配置完成初始化。

本版本属于可验证的复制基础版本。实际运行范围见 [v0.5 验证报告](v0.5-validation.md)，它不包含真实设备掉电、跨机房故障、长时间网络分区及生产自动切换资格。

v0.5.1 的性能对比、新增回归和运行范围见 [v0.5.1 验证报告](v0.5.1-validation.md)。可使用示例脚本的 `--replica-binary` 指定另一版本的节点，验证先升级从库、切换、切回的互通流程；升级前仍须备份。

v0.5.2 的切换预检查、生命周期故障回归及混合版本运行见 [v0.5.2 验证报告](v0.5.2-validation.md)。

## 时态身份与升级

v0.6 的身份有效时间、永久知识 UUID、时间线及幂等收据通过同一 WAL 批次复制；从库不重新生成时间。查询指定知识 UUID 尚未到达本从库时返回 `KNOWLEDGE_UNAVAILABLE`。切换后原请求重试可复用已经复制的原收据；异步故障升主可能丢失未复制的收据，不能保证跨数据回退恰好一次。

启用身份 API 前应将主从全部升级到 v0.6.0 或更高版本，含时态数据的目录不支持旧版本写入或降级服务。物理复制格式兼容不等于旧节点实现了受管集合保护。普通集合的混合版本验证范围见 [v0.6 验证报告](v0.6-validation.md)。

v0.6.1 的缓冲边界、故障回归和滚动升级验证见 [本轮优化报告](v0.6.1-validation.md)。示例可附加 `--identity` 验证身份历史及切换后幂等收据，要求双方均支持 v0.6 身份 API。

## v0.8 回收复制

统一保留策略、重试凭据、截止时间与回收任务都是租户 WAL 数据。主库执行逻辑回收，从库只按顺序回放并依据自身有效快照整理物理版本。恢复不重置已固定期限。最新业务状态始终保留，详见 [统一保留](retention.md)。

复制导出使用 maintenance_reserve_free_bytes（默认 64 MiB）检查物理空闲空间，复制期间持续核对；分块 open/pread 在导出锁外进行。后台追赶最多每 100 ms 刷新一次全量状态，同一份状态只协调一次无错误目录，页请求继续校验实时源位置和 epoch。日志应用与检查点初始化分别保存退避状态，成功日志页只清日志退避。普通日志的 BUSY、RESOURCE_EXHAUSTED、DEADLINE_EXCEEDED 从 100 ms 指数退避，最多 1 秒；其他日志错误及状态请求失败最多 30 秒。检查点初始化仍保持独立的 100 ms 至 30 秒退避，避免重复全量复制。

计划切换先在全节点写屏障外恢复冷租户位置，再在屏障内只核对缓存与在线位置；短暂锁竞争在整个目录共享的 100 ms 预算内重试；预算耗尽或新目录变化仍返回 BUSY，调用方重试操作，避免屏障内整库回放。升主仍最多等待 120 秒，节点间 promote 请求超时为 150 秒，超时后旧主仍保持持久 fence；重试完成切换，不自动解除隔离。

小预算兼容性：刷盘保护容量缩小了可供单个复制页面使用的普通预算。这是容量取舍，可能使过去直接增量回放的边界负载改走检查点；例如 64 MiB 全局、40 MiB 租户、16 个覆盖索引时，512 KiB **文档**的展开日志工作集会触发此回退（不是 512 KiB 日志页本身超限）。增量或检查点完成后都必须核对同一已确认位置和文档内容；必要时提高全局预算并观察重新初始化指标。

复制回放在 write_buffer_full 时先尝试非阻塞维护刷盘。若已下载页面因解码内存不足必须强制刷盘，会保留该页，在 100 ms 窗口内以 2 ms 间隔重试刷盘许可的 BUSY，而不立即重新下载；窗口耗尽后才交回原有逐租户退避。该窗口只限制 BUSY 重试，不取消已开始的文件 I/O。其他错误原样返回，尤其 COMMIT_UNKNOWN 不在此处重放。

### 请求与凭证边界（2026-11-08）

复制请求连接超时仍为 3 秒；响应头等待 30 秒（promote 为 150 秒），响应体按每次接收的 30 秒停滞期限计时。持续推进的大日志页可以超过 30 秒，总体大小仍受 MAX_WIRE_BYTES 及内存预算限制。非 JSON 错误页、认证错误和未知远端错误码统一归为 REPLICATION_UNAVAILABLE；只有复制协议明确支持的控制错误保留原码。

`token_file` 必须是无符号链接的普通文件，权限不允许 group/other（通常 chmod 600）；读取最多 514 字节，实际 token 为 16..512 字节。每个请求在阻塞工作线程上重新读取，原子替换文件即可轮换出站凭证，无需重启复制服务。接收端 auth 配置仍在启动时加载，应先部署可同时接受新旧 token 的配置，再轮换出站文件。

在从未完成过对应切换的从库上调用 switchover 返回 CONFLICT；已完成的旧主仍可凭后继节点的匹配 parent fence 幂等重试。

检查点下载完成后的安装排空每次最多 10 秒。首次超时打开闸门恢复读服务，保留已校验副本并续期 WAL pin，30 秒后只重试安装。第二次排空仍超时则释放副本和初始化名额，记录 DEADLINE_EXCEEDED 并按租户退避；后续重新下载仍先检查句柄能否排空。这样保留下载的重试路径可达，也不会让两个永久句柄无限占满初始化名额。waiting_for_readers 与 initialization_errors 可定位租户。持续写入超出 WAL 保留能力、源身份变化、取消或服务重启仍可能使暂存副本失效。

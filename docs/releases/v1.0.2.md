# idkv 1.0.2

**Released November 10, 2026.** This patch hardens WAL recovery and improves isolation for replication and remote backups.

## Changes

- Recovery reports `CORRUPTION` for an incomplete WAL header or payload and preserves the original file. The affected tenant stays out of planned switchover. Rebuild a damaged replica from the authoritative primary. Explicit offline WAL repair changes the history and replication epoch.
- Replica catch-up can process two tenants concurrently. Each tenant applies one page at a time in order, with up to eight pages per cycle.
- The data server can start when the configured remote backup manager fails to initialize. Remote backup routes return HTTP 503, and `tkv_backup_startup_degraded` reports the degraded state. Repair the backup state or configuration and restart to enable it.
- Binary logs, JSON logs and checkpoint file chunks share a send budget capped at one quarter of foreground memory. In-flight allocations also count against global memory. Temporary saturation returns `RESOURCE_EXHAUSTED`. An oversized log page returns `REPLICA_SNAPSHOT_REQUIRED` so the replica can request a checkpoint.

## Upgrade from 1.0.0 or 1.0.1

Registry 6, replication protocol 4 and WAL/SST format 1 are unchanged. Verify a backup and upgrade the server and both offline tools together on each node. A 1.0.0 peer uses JSON log pages. Check tenant errors, replication lag and backup readiness after each restart.

## Validation

- OrbStack Ubuntu ARM64 passed 302 locked source tests with failpoints enabled. The million-row qualification was ignored. Clippy and formatting checks passed.
- The failpoint demo verified acknowledged data through replica restart, rejected switchover after a torn WAL, rebuilt the replica and completed planned switches in both directions. It also exercised crashes during fencing and promotion.
- Both production builds passed CLI, HTTP, DSL, temporal identity, retention, filesystem-backed backup and restore, offline import and archived WAL repair smoke tests. Both generated the same OpenAPI document as the release asset.
- The production replication demo passed with an ARM64 and an x86_64 1.0.2 peer. Separate runs paired x86_64 1.0.2 with the published ARM64 binaries for 1.0.0 and 1.0.1. Each loopback run exercised checkpoint catch-up, 4,000 updates, replica restart, planned switches in both directions and explicit emergency promotion.
- Both builds used Rust 1.99.1 and the release lockfile. ARM64 was built and tested natively on OrbStack Ubuntu using GCC 15.2 and musl 1.2.5. x86_64 was built in the pinned release container and tested under emulation on the ARM64 host.

# idkv 1.0.0

**Released November 9, 2026.** The first stable release brings document storage, indexed batch lookup, versioned datasets and temporal identity into one embedded Rust engine and HTTP service.

## Highlights

- **A native tenant-scoped storage engine:** independent tenant WAL, directory lock, sequence, indexes and cache; LSM/SST storage, MVCC snapshots, checksummed recovery and compaction.
- **Documents and datasets:** conditional writes with history-aware retries, atomic Put/Delete/Check batches, same-snapshot read_batch, compound/unique/covering indexes, ordered batch lookup and immutable published versions.
- **Temporal identity:** business-time bindings and durable knowledge versions, batch resolve_many, subject identifier reverse lookup and paged change history. DSL resolve/resolvemany/ids/history share native semantics.
- **Operations:** asynchronous primary/replica replication, fencing and explicit failover, local and S3/fs backup, persistent backup jobs, offline import and archived WAL prefix repair.
- **Bounded work:** tenant/global resource budgets, separate HTTP execution pools, fair I/O task queues, Prometheus metrics and optional OTLP traces/logs.

The final maintenance changes reuse SST cursors throughout subject migration/link GC batches and let history GC advance through up to 64 physical records with a 10ms cooperative budget. Durable progress, atomic limit checks and historical predecessor baselines are preserved.

## Compatibility and upgrade

| Contract | Version |
|---|---:|
| Application / Rust package | 1.0.0 |
| Rust compiler | 1.99.1 |
| HTTP route prefix / DSL grammar | /v1 / v1 |
| Root registry | 6 |
| Replication protocol | 4 |
| WAL / SST | 1 / 1 |

Back up and verify recovery before upgrading. Stop writes and both peers; replace servers and offline tools together, then start primary/replica and check role, failures, catch-up and subject migration progress. Older roots require writable metadata space and are durably upgraded before writes are served. Old binaries cannot reopen the upgraded root; rollback requires the pre-upgrade backup.

Identity audit/link/pointer/TTL records count toward expanded atomic limits. At the default 1000-record limit, typical same-subject new bindings fit 199 items without retention or 110 with retention; real byte/document/memory limits may bind sooner. Review existing batches and coordinate limit changes across peers.

## Validation evidence

The 1.0 source regression suite passed **294 tests** on OrbStack Ubuntu ARM64, including failpoint-enabled recovery tests. The million-row qualification used two independent datasets: eight tenants sharing one million history rows under normal scheduling, and one tenant holding a million rows under an accelerated maintenance driver.

Four SIGKILL/restart continuations exercised migration and GC progress. After restart, **91,675 complete client-ledger acknowledgements** matched stored values; reverse/forward queries and retained history/link counts agreed. That report distinguishes default scheduling from accelerated driving, describes the fixture shape, and retains measured tail-latency limitations: [scale validation](https://github.com/SamuelSupe/idkv/blob/v1.0.0/docs/subject-maintenance-scale-validation-20261109.md).

The exact production executables were built from the Rust 1.99.1 image pinned in the release Dockerfile, using the default thin-LTO release profile, generic CPUs and static CRT. No failpoints were enabled in either distribution.

| Distribution gate | ARM64 | x86_64 |
|---|---|---|
| ELF architecture, static loading, all three --version/--help | Passed | Passed |
| Generated OpenAPI equals the committed 1.0 contract | Passed | Passed |
| HTTP CRUD/CAS, indexes, lookup, integrity and local restore | Passed | Passed |
| Remote fs create/reuse/verify/restore/prune | Passed | Passed |
| DSL, identity, retention, subject paging and batch resolution | Passed | Passed |
| Offline import, archived WAL repair and preserved document | Passed | Passed |

ARM64 execution used OrbStack Ubuntu on ARM64. x86_64 executables ran through x86 emulation on that Linux host, not native x86 hardware. A mixed ARM64-primary/x86_64-replica pair passed checkpoint initialization, **4,000 document updates**, replica SIGKILL/restart, planned switchover in both directions, history/receipt checks and explicit emergency promotion after stopping the old primary. Both nodes reported 1.0.0.

The pair ran over loopback in one OS. It demonstrates cross-architecture protocol execution, not independent hardware failure behavior or a production throughput benchmark. Remote backup validation used fs; a live S3 provider and real device power-loss/EIO were not newly tested for this release. Historical fault drills retain their dated scopes.

## Operating limits

- Write success means **local durable WAL**, not replica acknowledgement. Asynchronous emergency promotion can lose unreplicated acknowledged data; externally fence the old primary first.
- No automatic election, quorum, cross-tenant transaction/query, SQL, join, aggregation, full-text or CIDR query layer.
- Quotas and bounded scheduling are not a physical I/O or latency SLA. In the scale test, light-tenant write p99 remained higher during GC.
- Queries, atomic expansion, pagination and snapshots have explicit budgets and expiry. A lost response/COMMIT_UNKNOWN is not evidence that a write did not happen.
- Legacy reverse indexes backfill incrementally. ids may return INDEX_NOT_READY; historical audit events that were never stored are not synthesized.
- Offline WAL repair requires explicit data-loss acceptance, preserves the original database archive and changes history/epoch, requiring replica rebuild.
- Static binaries and emulated x86 execution do not constitute validation on every Linux kernel, filesystem, device or native x86 CPU.

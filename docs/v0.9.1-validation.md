# v0.9.1 查询、批量范围读取与稳定性验证

验证日期：2026-11-05 至 2026-11-06；OrbStack Ubuntu Linux AArch64。本次完成 KV 查询路径与后台整理优化，接口、DSL 语法、租户物理隔离、保留语义及复制协议保持不变。没有增加业务 Schema、CDC、业务授权或审计模块。

## 实现内容

1. 主键字符串范围使用物理键边界直接定位，正确处理包含/排除边界、NUL、Unicode、相矛盾条件和快照续页。可用的二级索引仍优先，避免宽主键范围抢占选择性更好的索引。
2. 二级索引连续前缀支持 eq/in 组合，去重后有界展开；完整唯一键集合走 MultiGet，未覆盖的正文也批量读取。多段结果使用有界 Top-K。
3. 稀疏唯一索引支持安全的范围和 IN 查询：必须能证明所有索引字段存在且非 null。无法证明的条件继续使用完整读取路径。
4. 非唯一 Lookup 与多段索引查询复用文件游标、索引分区和已解压块，直接跳过范围之间的数据。扫描不重复建立整套合并状态；旧版本、墓碑、快照租约、输入顺序和匹配上限保持原契约。
5. 整理积压时，每轮最多执行 4 次整理，累计执行达到 20 ms 后不再启动下一次；每次先检查刷盘需求。单次正在执行的合并仍不可抢占，因此这不是严格的 20 ms 任务耗时上限。没有积压时沿用一次检查，避免提高空闲整理频率。
6. 保留唯一点查的专用 Get 路径，省去无关主键范围、单值笛卡尔积、唯一点键上下界等临时分配。

范围展开最多 256 段、前缀键总长最多 1 MiB；超出后缩短索引前缀或回退到预算约束下的扫描，不截断结果。不同 read_batch Query 尚未融合成一次存储扫描。完整使用边界见 [API](api.md) 和 [组合读取](kv-capabilities.md)。

## 读性能对比

使用同一初始数据和相同基准逻辑：80,000 条文档，每条包含 4 KiB 确定性、低压缩率载荷，3 个索引；目录约 322 MiB。每租户引擎内存预算 64 MiB、块缓存 8 MiB、内存表 2 MiB，全局预算 128 MiB。数据位于 Linux Btrfs 虚拟磁盘 `/var/tmp`，不是 tmpfs。

下表为旧版与最终版本各两轮 P99 的中位数，单位 ms；原始数据保留 P50/P95/P99、吞吐、文件/块计数及资源数据。每个模式至少 100 次调用，快速模式至少运行 1 秒。此前还完成旧/新/新/旧的交错复测，扫描与读块收益一致。该结果代表这些具体查询，不代表全部查询的统一加速倍数。

| 原生 API 场景 | 优化前 P99 | 最终 P99 | 单次物理扫描条目：前 → 后 |
|---|---:|---:|---:|
| 主键尾部范围，返回 100 条 | 345.139 | 0.546 | 80,000 → 100 |
| 唯一索引范围，覆盖返回 100 条 | 349.085 | 0.179 | 80,000 → 100 |
| 二级索引 IN，返回 4 条 | 316.245 | 0.093 | 80,000 → 4 |
| 256 个非唯一 Lookup 输入，每个 2 条 | 9.704 | 1.542 | 512 → 512 |
| read_batch 内 8 个主键范围，各返回 10 条 | 2,463.048 | 1.366 | 640,000 → 80 |

Lookup 的输入相邻且落在少量块中，实际读块从约 260 降到 10，候选文件访问从 256 次降到 1 次；收益主要来自同批复用，而非少返回数据。分散键未必有同等收益。

为使旧版的 8 次全扫描能完成，此基准将累计扫描预算设置为 800,000，查询时间 120 秒、快照租约 180 秒；这些不是新的默认值。普通对比保留 OS 文件缓存，不称为物理冷盘测试。基准使用共享虚拟机，不以微秒级差异证明生产 SLA。

## 发现并处理的性能回退

只完成读取优化时，自由运行的 4 路查询显著增加了吞吐，但写入从约 774 条/秒下降到 687 条/秒。补充固定速率对照后，写入仍从约 802 降到 668 条/秒，因此不能只用“查询更多”解释。

后台原来每轮只推进一次合并/文件晋级，再等待 100 ms 调度。多个键空间产生小 SST 时，这个调度节奏限制了积压处理速度。增加有界连续整理后，同样的固定读取速率下写入达到约 943 条/秒；自由运行查询时达到约 963 条/秒。两种负载各运行 120 秒，结束后刷盘、合并及完整性检查通过。

| 120 秒混合负载 | v0.9.0 | 最终整理策略 |
|---|---:|---:|
| 固定查询速率：成功文档更新/秒 | 801.8 | 942.9 |
| 固定查询速率：Lookup P99，ms | 31.875 | 3.134 |
| 自由运行 4 路查询：成功文档更新/秒 | 774.0 | 963.4 |
| 自由运行 4 路查询：Lookup P99，ms | 33.506 | 2.317 |

固定负载是每秒各 1 次主键范围、唯一范围、IN 查询，以及每秒 50 次 256 输入 Lookup；写入目标为每秒 1,000 条。自由运行模式保持 4 个查询线程闭环提交。

**代价与限制：**目标写入速率仍未完全达到，出现背压时基准等待并重试。固定负载中，SST 写放大 `(flush_bytes + compaction_write_bytes) / document_bytes` 从约 4.25 增至 5.25；统计包括结束时的强制合并。采样到的进程文件句柄峰值从约 490 增至 641；结束合并后，两边均为 86 个 SST。此策略提高积压推进速度，需要更多后台写 I/O，不能描述成所有指标同时改善。

点读保护对照中，还发现新规划逻辑给唯一点查增加了不必要的小分配；移除后，唯一点查 P99 为 2.1045 → 2.104 µs，1,000 键唯一 Lookup 为 1.046 → 1.057 ms，未索引扫描为 7.070 → 7.103 ms。完整结果保留微小波动，不宣称这些未优化路径有性能提升。

## 超内存与多租户验证

- 在 Linux cgroup 中把进程及文件缓存总量限制为 **96 MiB**、禁用该组交换；使用 `posix_fadvise(DONTNEED)` 对已关闭的基准文件做最佳努力缓存清理。完整读取约 322 MiB 数据，共 80 页，每页 1,000 条，逐条校验全部业务字段。内存达到限制并触发回收，`oom=0`、`oom_kill=0`，全部数据正确。该测试超过内存上限三倍，但不能清空设备内部缓存。
- 8 个活跃租户、16 路读取、2 路写入，3 秒历史保留，运行 60 秒；32 个冷租户完成打开、关闭与重开。批次原子性检查通过，8 个租户重开后校验 8,000 条文档。引擎计费内存峰值约 34.8 MiB，低于该测试 512 MiB 全局预算，租户状态无维护错误。
- 混合负载的 RSS、句柄、I/O 排队、写锁等待和读写字节在原始日志中保留；它们包含基准程序自身的统计缓冲，不能等同于引擎专用内存。

## 正确性与交付验证

- 完整 failpoints 回归 **105 项通过**；最后一次等值规划分配优化后，额外重跑全部 **22 项引擎集成测试**通过。覆盖 WAL/恢复、合并、快照、复制切换、发布、幂等回执、历史回收和租户隔离。
- 新增 4 个有行为意义的回归：编码边界及主键范围快照；混合类型、稀疏复合索引、IN 展开上限与全扫描对照；非唯一批量 Lookup 顺序/缺失/上限/迁移删除；跨 SST 块版本链、墓碑与累计扫描预算。
- 最终代码通过 `cargo clippy --all-targets --features failpoints -- -D warnings`、格式检查及 release 构建。
- 实际启动最终 HTTP 服务，验证三个新查询路径、批量 Lookup、原生 HTTP、DSL、时态身份、统一保留、发布分页、备份恢复及重启。OpenAPI 3.1 校验通过：62 个路径、83 个组件 schema；实际响应通过 JSON Schema 校验。
- 真实 v0.9.0 程序可打开最终版本生成的数据，读取发布元信息/正文并保持冻结集合不可写，再切回新版本继续读取。本项不是完整降级资格认证。
- 更新 Linux AArch64 服务、恢复工具、OpenAPI 和校验文件；没有远程部署或发布 Git 标签。

## 复现与未验证范围

使用 [range_perf](../examples/range_perf.rs) 和已有 [read_perf](../examples/read_perf.rs)。旧、新源码分别使用独立构建目录；同一份基准逻辑链接各自内核，使用同一初始目录的独立副本执行混合写入。对照版本通过扫描计数和构建来源核实，无效编译缓存样本未纳入结论。

```sh
CARGO_TARGET_DIR=/var/tmp/tkv-v091-build cargo build --locked --release --example range_perf
/var/tmp/tkv-v091-build/release/examples/range_perf /var/tmp/tkv-data seed 80000
/var/tmp/tkv-v091-build/release/examples/range_perf /var/tmp/tkv-data read 80000 1
# mixed / mixed_paced 会修改数据，应使用 seed 目录的独立副本。
/var/tmp/tkv-v091-build/release/examples/range_perf /var/tmp/tkv-copy mixed_paced 80000 120
```

本轮未完成百万/千万条、10–100 GB、多日运行、16 并发下的正式性能资格验证，也未测真实掉电、物理设备冷缓存、真实云 S3 或 HTTP 性能。复制仍为异步主从，故障升主的既有 RPO 边界不变。多段 IN 尚无跨段有序归并；不同 Query 尚无跨请求 I/O 融合。当前结果支持上述实现与测试场景，不能据此承诺所有业务负载的生产 SLA。

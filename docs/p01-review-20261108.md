## P1：复制导出租约阻止 WAL 故障后的自动恢复

触发条件是租户正在向副本导出检查点，此时该租户的 WAL fsync 返回一次错误。即使随后存储 I/O 已恢复，租户仍无法重新打开引擎，读写请求继续返回 `COMMIT_UNKNOWN`，管理员 close 返回 BUSY，计划主从切换也失败。大检查点或慢链路会把这段不可用时间延长到传输结束或租约释放，恢复没有独立于复制传输的期限。

源码链路：

- [LogRetention](../src/storage/engine.rs#L37) 持有 `Arc<Engine>`；`valid()` / `renew()` 只检查 pin 和过期时间，没有检查 `recovery_required`。
- [tenant_with_open_marker](../src/tenant/manager.rs#L489) 检测到恢复标记后，必须先 close 旧引擎。`close_slot` 要求引擎引用计数为 1；[后台恢复](../src/tenant/manager.rs#L744) 也有同一条件，因此都被导出租约挡住。
- [snapshot chunk](../src/replication/snapshot.rs#L165) 会继续续租，[expire](../src/replication/snapshot.rs#L230) 仍认为导出有效。5 分钟是可续的空闲期限，不是故障恢复期限。

### 实际复现与对照

在 OrbStack Ubuntu Linux aarch64 / 原生 Btrfs 上启动真实 HTTP 服务，使用当前版本 release 二进制。每次使用独立数据根和凭证；通过仓库已有 shim，仅对本轮根目录内的 WAL 注入 fsync EIO，收到 `COMMIT_UNKNOWN` 后立即撤销注入。

| 场景 | 撤销 EIO 后的结果 | 解除导出依赖后的结果 |
| --- | --- | --- |
| 同样生成检查点，但在注入前释放导出 | 首次写入约 7.79 ms 成功，无后续错误 | close 成功 |
| 保持导出并持续请求分块 | 6.05 秒观察窗内 111 次写入全部 `COMMIT_UNKNOWN`，close 为 BUSY | release 后约 7.90 ms 写入成功 |
| 正常副本初始化，经测试代理暂停目标租户的分块响应 | 6.04 秒观察窗内 112 次写入全部失败，计划切换返回 `COMMIT_UNKNOWN` | 恢复传输后约 445 ms 写入成功 |
| 独立重复正常初始化，并追加进程强杀重启验证 | 6.02 秒观察窗内 112 次写入全部失败，计划切换同样失败 | 恢复传输后约 459 ms 写入成功 |

6 秒是主动设置的观察窗口，不是系统的超时上限。毫秒值为本轮单次样本，不代表 P99。自动初始化场景没有手工创建或释放导出，走的是现有副本下载、探测日志和失败释放流程；代理仅暂停目标租户的一次分块响应，未修改服务实现。

两个正常复制场景中，健康对照租户仍能写入，计划切换失败后旧主仍保持 primary。故障租户 100 条文档、对照租户 10 条文档在两端按 ACK 账本核对，键、修订、载荷、索引查询、multi_get、lookup 和存储 check 均通过。最后一个场景对两端执行 SIGKILL，再启动服务后重新核对同样的已确认数据，差异为零。未知结果的写入更新既有键；恢复后用成功写入覆盖该键，再按成功回执核对，未把未知结果记成确认成功。

该问题按 P1 判定：一次可恢复的局部 I/O 错误，被正常复制任务延长为业务租户持续不可用，并阻塞整个节点的计划主从切换。本轮没有复现已确认数据丢失或静默分叉。

### 修复方向

应让 WAL 恢复能够撤销相关导出：租约有效性和续期感知引擎故障，及时取消并释放旧引擎引用；正在准备检查点的拷贝、哈希阶段也要能结束。副本沿现有过期/失败路径重试。不能只清空 pin 表而保留持有引擎的导出对象，也不能直接绕过 close 的引用计数检查。

需要新增的回归边界是：保留活动导出，制造一次 WAL 同步失败并恢复 I/O，在不依赖下载完成或手工 release 的有界时间内恢复业务写入，再验证复制与重启后的 ACK 数据。本轮尚未实现修复。

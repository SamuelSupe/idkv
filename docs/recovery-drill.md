# 故障恢复演练与操作流程

适用版本：v0.10.1，异步一主一从。故障升主可能丢失已确认但未复制的写入；备份恢复只回到所选检查点。本文分别记录这两种数据回退，不将它们相加当作一次故障的损失。

## 2026-11-06 实测结果

执行时间：新加坡时间 11:17:51–11:18:36。引擎源码为 `87d9a1a`，release 构建，未开启 failpoints；本轮增加演练脚本和文档，没有修改引擎实现。环境为 OrbStack Ubuntu Linux AArch64，数据和 fs 备份仓库位于 `/var/tmp` 的 Btrfs 虚拟磁盘，非 tmpfs。memtable 2 MiB、块缓存 8 MiB，其余引擎选项沿用默认值。

两个场景均完整通过：主进程丢失、外部隔离、故障升主、旧节点新目录重建、完成并校验备份、两个在线副本停止后导入新 Store、恢复服务读写与重启。数值均为各一次实际运行，不是重复采样分位数或 SLA。

lagged 场景的最早一笔丢失批次在故障注入前 93.469 ms 已获得成功响应；这直接证明很短的复制暂停也可能丢失已确认写入。两份备份在灾难恢复起点的元信息年龄分别为 8,787.571 ms、8,232.624 ms；恢复明确回退到检查点，未包含之后写入的 1,000 条。备份中还包含重建后的 100 条增量及独立 probes 集合，表中的文档数量只计 assets。

每次关键恢复均比较全部正文和原成功回执的 `_rev`，遍历全部分页以检测额外/重复文档，校验唯一覆盖 Lookup 与缺失键，并执行引擎完整性检查。新副本拒绝业务写入，且收到新主重建后追加的数据；旧主分叉目录始终离线，没有将其中的尾部写入自动合并回新历史。两个恢复库重启后仍保留检查点数据，检查点后的写入仍不存在。

最终运行中，caught-up 没有准入重试；lagged 记录一次 `BUSY` 重试，两个场景都没有 `RESOURCE_EXHAUSTED` 重试。较早的大数据预演遇到过 L0 背压，脚本已按现有明确拒绝契约做有界重试。这些是运维流程需要处理的状态，未修改引擎错误语义。

本轮是同一 Linux VM 内的进程级演练；fs 仓库也在同一虚拟磁盘。没有模拟独立主机/整盘丢失、真实掉电、网络分区、真实云 S3、生产 TLS/入口切换或人工响应耗时。上述速度不能用于承诺生产 RTO；已追平时零丢失也不能用于承诺异步复制的最大 RPO。

## 可重复执行的独立演练

在 OrbStack Linux 内、项目根目录执行。数据根目录必须尚不存在，并位于虚拟磁盘，不能使用 `/tmp` tmpfs。脚本只管理自己创建的进程、凭证和数据目录。

```sh
CARGO_TARGET_DIR=/var/tmp/idkv-drill-build cargo build --locked --release --bin tenant-kv --bin tenant-kv-restore
python3 -B scripts/recovery_drill.py \
  --binary /var/tmp/idkv-drill-build/release/tenant-kv \
  --restore-binary /var/tmp/idkv-drill-build/release/tenant-kv-restore \
  --root /var/tmp/idkv-recovery-drill-new
```

默认分别执行 `caught-up` 和 `lagged` 两个独立场景。每个场景装载 20,000 条种子文档，每条有 4 KiB 确定性高熵 base64 payload；再提交 1,000 条故障前尾部文档，每批 100 条。每个成功响应的主键、修订号、history 与操作 ID 写入独立的 `acknowledgements.jsonl`。

1. 启动主从、完成初始化，校验种子文档、唯一覆盖索引及 Lookup。
2. `caught-up` 等待全部尾部写入复制；`lagged` 先 SIGSTOP 暂停从库，再让主库确认尾部写入。
3. SIGKILL 主进程，等待退出，确认旧监听端口已关闭，将原数据目录移至隔离目录。演练没有自动重启服务的监督程序；这些条件共同构成本次进程级外部隔离证据。
4. 恢复候选从库运行。先验证缺少隔离或接受数据损失声明时升主被拒绝，再提交故障升主。确认写就绪、业务读取和一次持久写入后记录恢复耗时；随后逐条核对成功写入。
5. 修改旧节点的首次角色配置为 replica，使用新空目录从新主重建。确认位置追平、业务数据一致、拒绝业务写入；新主再写 100 条，验证新副本收到增量。
6. 新主创建 fs 仓库检查点，等待任务 `completed`，运行完整 verify。之后再确认 1,000 条写入，让备份明确落后于在线数据。
7. 停止并隔离两个在线副本，只使用备份，通过 `tenant-kv-restore` 导入新 Store。启动独立服务，验证读写就绪、全部检查点文档及索引、检查点后文档不存在；重启后再次校验。

默认参数可以用 `--documents`、`--tail-documents`、`--payload-bytes` 调整。大数据写入、建索引可能因 L0 积压返回 `RESOURCE_EXHAUSTED`；紧接已完成备份提交下一个操作可能短暂返回 `BUSY`。脚本仅对这两类明确拒绝做有界重试，记录次数；写入重用原操作 ID 与 history，网络失败或未知提交结果会终止演练，不作为“未提交”继续执行。

退出时脚本关闭自己的所有节点、删除 token 与 auth 文件，保留隔离数据和日志供核对。结果中的 `passed` 要求两个场景及全部校验均完成；失败场景会留下自己的 `result.json`。不会自动重新启动被隔离的旧数据目录。

## 实际故障操作顺序

### 1. 确定故障范围并保存证据

记录故障发现时间、最后成功写入回执、客户端未知结果、候选从库状态、租户 applied sequence 与复制错误。调用候选节点的 `GET /v1/replication/status`，保存完整 JSON，确认它属于预期集群及来源。

停止向故障写入口发新请求。能访问旧主时，计划切换优先使用原有 `/switchover`；旧主无法参与时才进入故障升主流程。不能把请求超时解释为事务未提交。

### 2. 在外部隔离旧主

停止旧主服务与自动拉起它的 systemd/container/调度器；必要时关闭主机、撤销存储访问或封禁所有业务写入通道。核对旧进程已退出或基础设施隔离已生效，并保存操作时间与证据。只修改 DNS/负载均衡不足以证明旧主不能写入。

本次演练使用 SIGKILL、等待退出、端口关闭检查与原目录隔离；生产环境需要对应主机、编排和网络层面的证据。故障升主请求中的布尔值只声明管理员已经完成隔离，数据库不会远程验证它。

### 3. 从候选副本升主并恢复业务

从候选状态复制 `node.source`，构造 `promote.json`。不要填候选自己的 node 或 epoch。

```json
{
  "source": {"node": "旧主 node UUID", "epoch": "旧主 epoch UUID"},
  "old_primary_fenced": true,
  "accept_data_loss": true
}
```

确认外部隔离与数据损失决策后，以全局管理员调用候选节点：

```sh
curl --fail-with-body -H "Authorization: Bearer $ADMIN_TOKEN" \
  -H 'Content-Type: application/json' --data-binary @promote.json \
  "$CANDIDATE/v1/replication/force-promote"
```

核对返回角色与新 epoch，检查 `/ready/write`，执行实际业务读取和一次可安全去重的写入，再更新应用入口。客户端必须处理历史变化、失效游标和旧 CAS 条件；对已丢失回执的旧操作，不得自动换 history/token 重放。

使用应用成功回执台账与新主数据逐项对照，分别记录已确认但缺失的操作、文档及未确定结果。sequence 差用于定位日志进度，不能直接当作文档丢失条数。保留旧主文件供取证，不自动合并分叉写入。

### 4. 将旧主重建为副本

保持原目录离线并归档。为旧节点选择新空根目录；配置相同 cluster、`role: replica`，peer 指向新主，并恢复业务和复制凭证。已有根目录中的持久角色不会被启动配置覆盖，不能通过改配置或删除复制状态文件把旧数据直接变成副本。

启动后确认新节点身份、来源和只读角色；等待全部健康租户与新主位置一致，再核对文档、索引与 Lookup。向新主写入新批次并确认副本收到，才算恢复了复制保护。恢复读流量时仍遵守最低读取位置规则。

### 5. 从检查点进行灾难恢复

需要从备份恢复时，先停止目标租户/节点流量，选定最后一个完整、校验通过的备份，记录其 checkpoint sequence、时间、文件数与字节数。启用复制的 Store 不允许普通 restore/import，应使用新 Store。

```sh
tenant-kv-restore /var/lib/idkv-restored backup-config.json "$TENANT_UUID" "$BACKUP_UUID"
```

导入完成后，单独恢复 auth、配置与备份凭证；这些不属于业务备份。启动服务，校验业务数据、索引、Lookup 和新历史，验证实际读写，再切换业务入口。需要主从保护时，将恢复库初始化为主库，并在另一个新空目录重建副本。

本次演练恢复到独立服务，验证了重启后的持久数据；没有把恢复完成等同于恢复后的主从拓扑已经建立。远端仓库创建/清理执行权也必须明确交接，不能让旧控制器重新同时操作相同租户前缀。

## 耗时与数据损失口径

| 字段 | 实际计时或计数边界 |
|---|---|
| failure_to_read_write_ready | 发出旧主 SIGKILL 前开始，至新主写就绪、业务读取和探针写入后读回均成功；包含脚本隔离与升主步骤 |
| force_promote_request | 已完成外部隔离后，故障升主 HTTP 请求耗时 |
| replica_rebuild_to_caught_up | 在新空目录启动旧节点，至全部租户追平且节点可读；完整逐条校验另行执行 |
| backup_import | 两个在线副本都已停止后开始，包含目录隔离和离线导入，至恢复工具成功退出 |
| backup_recovery_to_read_write_ready | 同一灾难恢复起点，至恢复服务实际读写探针成功 |
| backup_recovery_through_full_validation | 同一起点，至全部文档、缺失键、索引 Lookup、分页和完整性校验完成 |
| failover_loss | 故障前获得成功响应、但升主后缺失的文档和原子批次；包含缺失键清单 |
| backup_loss | 本次在线新历史中已确认、但检查点不包含的写入；与上一次故障升主的损失分开计算 |
| missing_payload_bytes | 缺失文档的 payload 字节，不包含字段、索引、WAL、压缩等开销 |

`lost_ack_window_ms` 为最早一笔已确认但丢失的批次响应至注入故障的时间；`checkpoint_age_at_disaster_ms` 为备份元信息时间至停止全部在线副本的时间。二者都是本次观察窗口，不能推导异步复制的最大 RPO。

自动化耗时不包含人工发现、审批、云平台隔离、DNS/LB 传播或客户端重试退避。副本一直在运行，升主耗时也不包含候选节点冷启动。本地文件缓存没有清空，恢复时间只对应本轮数据、虚拟磁盘和 fs 仓库。

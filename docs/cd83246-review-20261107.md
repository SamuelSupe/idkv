## 1. 管理排空无法中断在线索引构建

原版在线 `create_index` 的 stop 为 None，只在后台恢复构建时检查停止信号。扫描、增量应用及写入背压等待均未检查 engine 的 draining 状态。因此，虽然 HTTP 执行池已分离，构建仍可持有句柄与快照，使 close、删除或改配额的一秒排空超时。

现在线与恢复构建共用排空检查，覆盖进入构建、快照扫描、增量处理及写入等待。发现 draining 后返回 BUSY，释放构建自身的引用；错误处理不会再等待另一笔事务将其写成 FAILED。已登记的 BUILDING 保留，租户重新打开后由原有恢复工作者使用新 generation 重建，旧 generation 交给原有 GC 清理。尚未登记 BUILDING 的请求直接退出。

回归停止自动维护，以 2048 条已确认文档和小 memtable 构造真实 L0 积压，让在线构建停在背压等待中。修复版分别完成 close、同配额更新和删除，构建返回 BUSY；close/改配额后确认状态仍为 BUILDING、error 为空，再重开 Store 并等待自动恢复为 READY。核对 **4096 个文档状态和 4096 个索引查询结果**的主键、确认修订与 1 KiB 载荷，全部一致。删除场景核对租户不可再打开，不把明确删除当作数据丢失。

同一回归加入独立原版 cd83246 后，在第一个 close 场景因 `tenant handles did not drain within one second` 失败。原版未继续运行后两个场景；源码确认三种操作共用同一排空函数，修复版测试覆盖三者。

另用 I/O 屏障在 BUILDING 发布期间开始排空，验证没有 L0 背压时也会协作中断、保留 BUILDING/error 为空，并核对一条已确认数据。这防止把“FAILED 发布恰好被背压拒绝”误当作正确保留状态。原版在该场景继续构建到 READY，未按排空中断，出现预期行为失败。

这是协作中断，不是强制结束线程。已经开始的文件 I/O、事务锁等待仍须返回；嵌入式调用方在构建退出后长期保留的 TenantHandle 也必须自行释放。普通读快照不被作废，长期引用仍可能合法地导致 BUSY。原有“失败排空保留快照、释放节点许可”的回归继续通过。

## 2. 全局锁竞争被误送入冷准入池

原版 `try_http_input_budget` 对 registry/slots 目录锁竞争、租户 slot 锁竞争和缺少 slot 都返回 None。目录锁短暂竞争也会尝试取得冷准入名额，满池时直接拒绝正常租户。

现区分两种等待：全局目录锁竞争内部返回 BUSY，HTTP 异步任务每隔一毫秒重试，不持执行或冷准入名额，也不创建阻塞工作。重试沿用预算准备与正文的共同期限，默认最多五秒，读取控制可收紧。租户 slot 忙或尚未创建时仍进入原有有界阻塞准入；真正的满池仍返回 429，取消后的阻塞任务继续持有名额到退出。

回归把冷准入总额缩小为 1，用一个取消后仍卡在 slot 锁上的请求占满它。第二个真正的冷请求仍被拒绝；正常租户分别遇到 registry 和 slots 锁竞争后，都能在锁释放后读出已确认修订。另将读取期限收紧到 20 ms，在目录锁仍持有时验证等待按 DEADLINE_EXCEEDED 退出。这里稳定覆盖的是同一容量边界，不把缩小总额的回归表述为实测了默认配置下八个租户、256 个阻塞线程。

同一回归放入原版，正常租户在满池加目录锁竞争时被拒，出现预期行为失败。对照先加入两个测试函数，后追加正常可写状态的第三项回归；生产源码、Cargo 文件和依赖均未调整。

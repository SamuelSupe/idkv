# 性能与稳定性 — v0.4.0，2026-11-05

本轮以已交付 v0.3.0 为基线，处理持续更新后的版本链开销、非索引排序的解码成本，以及并发分页和结果限额的稳定性边界。持久格式仍为 v1，已有 DSL、租户隔离和 OpenDAL 备份接口保持可用。

## 已复现并修复的缺陷

| 问题 | v0.3 复现 | v0.4 行为 |
|---|---|---|
| 并发消费同一 cursor | 8 个请求均成功返回下一页并产生各自的续页 token | 结果准备后在同一锁内消费并发布；只有 1 个成功，其余 CURSOR_EXPIRED |
| MultiGet 漏算响应字节 | 一个接近 1 MiB 的文档加 64 个未命中项，数组超过 1 MiB 上限仍成功 | 将 null、逗号和括号一并计入；超限返回 RESOURCE_EXHAUSTED |

回归测试对旧代码确实失败，修复后通过。旧版失败日志的长文档内容在交付摘录中省略，未更改失败结论。游标的指纹/租户/快照校验继续执行；执行失败或响应超限不会提前消费可重试的 token。

## 性能改动

- **内存历史版本**：从每次头插改为按提交序号追加；旧快照点读和倒序扫描使用二分定位。消除热点键的整链搬移与扫描时反复从链头遍历；刷盘仍输出降序版本，恢复协议不变。
- **SST 可见版本读取**：块内同时定位逻辑键和快照序号；找到第一个可见版本（包括墓碑）后停止，不继续加载更旧块。MultiGet 已找到可见版本时不重复扫描跨分区历史。
- **事务点读**：检查旧文档和唯一性时使用同一单键快路；写批次长度通过计数序列化计算，省去一次仅用于测长的缓冲分配。
- **刷盘期间的读延迟**：WAL 创建和 Manifest 同步期间保持视图共享可读，仅在内存表交换时取得排他锁；写入协调锁仍保护轮转，持久化顺序没有变化。该调整是在 5 分钟负载暴露热点读尾延迟后加入，并单独复测。
- **排序与完整文档 Top-K**：排序字段路径预编译，直接读取二进制标量；完整文档仅在进入最终页后解码。窄字段投影仍保留紧凑候选，避免无谓引用大正文。候选、输出和截止时间继续受预算约束。

## 自动化与实际接口验证

OrbStack Linux 上 **47 项测试通过**：19 引擎、8 备份、7 DSL、3 HTTP、5 故障恢复、4 新稳定性回归及 1 SST 单元测试。新增检查包括历史版本/墓碑在刷盘、合并及重开后可见性一致；SST 跨分区 Get/MultiGet 一致，最新点读不加载整条历史；缺失/null/布尔/整数/浮点/Unicode 字符串的双向排序与参考实现一致，完整文档分页无遗漏。

Clippy 全目标/failpoints `-D warnings`、格式检查通过。另实际启动发布版 HTTP 服务，运行 DSL 示例及 JSON API 工作流，包含覆盖 Lookup、分页、条件写入、本地备份恢复，以及 OpenDAL fs 仓库的创建、增量复用、校验、恢复、保留清理和任务清理。OpenAPI 3.1 校验通过，版本 0.4.0，33 个路径、30 个 schema。

运行日志与接口结果保存在 `bench-results/v04-*`。本轮未连接真实 AWS；S3 模拟器历史证据仍在 [v0.2 报告](backup-validation.md)，不能作为本轮重新执行的结果。

## 基准环境与对比方法

- OrbStack Linux AArch64，Rust/Cargo 1.90.0，release 构建，CPU 亲和性限制为 0–7。VM 可见 18 CPU、约 31 GiB 内存；本轮未设置 cgroup 内存上限。
- 数据位于 Linux `/var/tmp` Btrfs 虚拟磁盘。OS 页缓存预热，没有冷盘缓存驱逐；未验证宿主磁盘型号或裸机持久化语义。
- 从 v0.3.0 归档源码加入与新版完全相同的 `examples/deep_perf.rs`，独立构建旧版二进制。新旧交替各运行 3 轮，表格取各轮 P50/P95/P99/吞吐的中位数；倍数按 P50 计算。
- deep_perf 每轮使用新库，10,000 个文档，包含 1 KiB 可压缩 payload、24 个附加字符串字段与主键/score；排序字段没有索引，取最大的 100 行。使用默认 16 KiB SST 块，内存表上限 64 MiB，基准查询超时设为 30 秒。
- 另对一个内部键保留 8,000 个提交版本：先测内存快照扫描完整版本链，再刷盘测 SST 最新版本点读。每模式预热 3 次，计时 2 秒或最多 100,000 次调用。数据装载和 8,000 次持久提交不计入查询延迟，但计入进程资源使用。
- 使用原来的 read_perf 再做 3 轮常规读路径回归：10,000 条、512 字节 payload、一个唯一覆盖索引，输入与 v0.3 报告一致。每模式 2 秒或最多 200,000 次调用；Get 与唯一查询可能提前达到次数上限。
- 压力测试与性能对比顺序执行，不同时争用测试 CPU。本文是嵌入式调用测量，HTTP 仅验证功能，未声称 HTTP 具有相同延迟。

## 5 分钟主测试与 2 分钟锁优化复测

复用并扩充 `examples/soak.rs`：8 个活跃租户，每个 1,000 条约 1 KiB payload 的文档，3 个索引；2 个热点租户持续以 20 文档批次更新，16 个读取线程持续访问，另外创建 32 个冷租户并检查空闲关闭和重新打开。

读取线程验证主键、IP、score 和 payload；周期性 MultiGet 固定 20 行必须看到同一个批次版本，唯一索引查询必须返回正确文档。每 5 秒保存租户状态，持续采样引擎预算；结束后刷盘、完全合并和校验 SST，再关闭并重开 8 个租户，核对 8,000 个文档及非唯一索引与全量正文结果一致。

先完成 300 秒持续负载及重开核对。随后发现刷盘轮转在文件同步期间占用视图排他锁，缩短锁范围后，针对最终代码在新库重复完整流程 120 秒，并重新执行 47 项测试、HTTP/备份示例及全部 3 轮性能对比。两个时长的运行分别记录，不合并成一段连续测试。

总引擎预算 512 MiB、每租户 64 MiB、块缓存 8 MiB、内存表 1 MiB。该测试使用可压缩 payload；读线程每次循环暂停 1 ms，延迟样本最多保留每线程前 200,000 次 Get，包含返回值校验时间。它用于持续负载下的隔离、正确性和资源进度验证，不是最大吞吐竞赛。

最终代码的 120 秒完整复测成功：**1,095,060 次文档更新、896,641 次 Get**；周期性的批量快照/索引校验另计，不包含在 Get 次数内。峰值引擎计费内存 **34.0 MiB / 512 MiB**，进程峰值 RSS **56.5 MiB**（Linux wait4，含基准样本数组）。24 次租户状态采样未见维护错误。

32 个冷租户均观察到空闲关闭；重开 P99 137 µs。8 个活跃租户全部重开验证通过，核对 8,000 个文档及非唯一索引结果。结束后的完整合并让所有租户 L0 清空；运行期间的分层文件数、内存和调度进度保留在原始 JSONL 中。

| 租户 | 更新数 | Get 数 | Get+校验 P99 µs | 写背压次数 | I/O 完成任务 | 写放大 |
|---|---:|---:|---:|---:|---:|---:|
| active-0 | 547,820 | 113,412 | 105 | 0 | 213,262 | 1.58× |
| active-1 | 547,240 | 114,999 | 105 | 0 | 213,245 | 1.58× |
| active-2 | 0 | 111,609 | 17 | 0 | 1,550 | 1.56× |
| active-3 | 0 | 111,313 | 16 | 0 | 1,550 | 1.56× |
| active-4 | 0 | 111,362 | 16 | 0 | 1,552 | 1.56× |
| active-5 | 0 | 111,853 | 16 | 0 | 1,546 | 1.56× |
| active-6 | 0 | 110,967 | 16 | 0 | 1,546 | 1.56× |
| active-7 | 0 | 111,126 | 17 | 0 | 1,545 | 1.56× |

写放大按 `(WAL + flush + compaction_write) / document_bytes` 估算，包含装载及末尾完全合并；使用可压缩 payload，不代表其他数据分布。每租户写锁累计等待、I/O 排队、合并字节与读背压见 [压力测试汇总](../bench-results/v04-soak-summary.json)，完整进度见 [v04-soak.jsonl](../bench-results/v04-soak.jsonl)。

刷盘视图锁调整前后的压力观察（配置相同、时长不同；P99 取各组读取线程中的最大值）：

| 阶段 | 时长 | 更新数 | Get 数 | 热点 Get+校验 P99 µs | 轻量 Get+校验 P99 µs |
|---|---:|---:|---:|---:|---:|
| 调整前 | 300 s | 2,762,020 | 2,211,168 | 5,032 | 13 |

首次 300 秒负载及 SST 检查完成后，验证程序在关闭阶段遇到后台维护持有引用的 BUSY，未完成重开核对；没有把该次运行计为通过。验证程序补充最长 5 秒的有界重试后，从新库重跑 300 秒整套流程并成功。之后缩短刷盘视图锁，对最终代码另外完成 120 秒复测；上面的逐租户表格来自最终阶段，首次退出摘要另存。

## 复现命令

以下在 Linux/OrbStack 内执行；数据库目录须为本次测试独占的新目录：

```sh
cargo test --locked --features failpoints -- --test-threads=1
cargo clippy --locked --all-targets --features failpoints -- -D warnings
cargo fmt -- --check
cargo build --locked --release --bin tenant-kv --bin tenant-kv-restore --example deep_perf --example read_perf --example soak
taskset -c 0-7 target/release/examples/deep_perf /var/tmp/tkv-deep-new
taskset -c 0-7 target/release/examples/soak /var/tmp/tkv-soak-new 300
```

前后对比需要将相同 deep_perf.rs 放入 v0.3.0 归档源码，只添加基准文件、不更改旧引擎，并使用独立 target 目录构建。每轮新建数据库，新旧交替各 3 次。read_perf 使用相同行数/内容的已关闭库，deep_perf/soak 使用全新目录，避免混入旧数据。

HTTP 服务启动方法见 [README](../README.md)，启用 OpenDAL fs 后可执行：

```sh
python3 scripts/dsl_smoke.py http://127.0.0.1:8080 token.txt
python3 scripts/http_smoke.py http://127.0.0.1:8080 token.txt --remote-backups
```

## 结论边界

五分钟持续负载及三轮微基准通过，不等于数天运行或全部生产资格验证。百万/千万条、数据超过内存、冷盘读取、真实 S3/网络故障、设备掉电、磁盘硬故障及其他 CPU 架构本轮未重新执行。读锁分项等待没有独立指标，报告只记录已有写锁与 I/O 调度统计。原百万/千万条结果仍为 [v0.1 历史基线](validation.md)。macOS 原生编译仍未执行：宿主 Xcode 许可未接受，没有修改许可状态。

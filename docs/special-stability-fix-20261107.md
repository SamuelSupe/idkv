# 特殊稳定性场景修复与复测（2026-11-07）

本轮修复两项并发缺陷，并优化历史注册项容量；保留此前未提交的 HTTP/索引排空修复。原始发现见[特殊场景审查](special-stability-audit-20261107.md)，新证据见 [special-stability-fix-20261107](../bench-results/special-stability-fix-20261107/)。

后续[边界审查](special-stability2-20261107.md)已将健康 v4 根的格式升级推迟到必要的注册表发布，并修正能力接口的版本报告。下文“打开即升级”及测量描述保留为本轮当时版本的记录，当前行为以新报告与运维文档为准。

## 修复行为

**失败排空后的索引恢复。** 构建退出时在 builds 锁内移除 generation 并使恢复缓存失效；恢复检查在同一把锁内确认所见活动 generation 仍存在，才发布缓存，避免晚到的检查覆盖失效标记。目录序号比固定快照新时不缓存检查结果。活动构建仍可使用缓存，未改成每轮全量扫描目录。

未修改的原自动后台探针，在同样的 16,384 文档场景中，由原先五秒仍为 BUILDING，变为管理排空失败后 **2309 ms 内在原引擎恢复 READY**。共检查 45 次，没有手工调用恢复方法；在强制重开之前已 READY，随后核对确认修订和载荷，差异为零。

**并发缩配额。** Counter 使用读写锁协调预留和限额发布：预留共享读锁，更新独占写锁，used 的检查与 limit 的存储不可被新预留穿插；释放仍用原子递减，不等待配额更新。没有撤销已有预留，使用量超过新上限时继续拒绝缩容。

原 128 MiB→64 MiB 探针代码不变，连续三轮各三秒：12,703,873、13,220,733、13,044,005 次预留尝试，均无超额，最终 used 为零；原版三轮均触发超额。这里验证的是预算计费，不将尝试次数表述为实际分配了同等大小内存，也没有宣称完成整个 HTTP 改配额窄窗口的端到端复现。

**历史删除记录容量。** 根注册表升级为 **v5**，Deleted 项持久化为紧凑行，省去重复字段名和重复 UUID；保留名称、generation、history、内存/磁盘配额，因此历史状态接口与已删 UUID 禁止复用契约不变。读取时检查重复 UUID，旧格式在打开时原子迁移。

与原复现一致的旧 v4 持久夹具含 56,870 个 Deleted 项、16,777,152 字节；迁移并完成后续创建/删除后，文件为 **8,645,372 字节，约减少 48.5%**。连续三次重启均成功创建、确认文档可读、历史状态完整，旧 UUID 导入被拒；删除全部活租户后再重开，仍可创建。

16 MiB 格式上限继续保留，历史身份并未删除，**不承诺无限租户周转容量**。这部分是有界容量优化。新增注册表字节数、容量上限和 Deleted 数量指标；在创建/导入建立或移动目录前，以及删除/恢复/配额发布状态前预检容量。新 v5 格式再次达到边界的回归确认：创建返回 RESOURCE_EXHAUSTED，持久文件逐字不变、无暂存目录、内存注册表仍只有原活租户，确认数据及重启均正常。

## 版本与兼容性

打开 v1–v4 根会持久迁移到 v5，需要可写空间；升级后旧程序无法打开。服务和离线恢复工具应一起更新，升级前保留停机备份。WAL、SST、复制协议及 HTTP 租户状态结构均未改变。

实际旧版二进制尝试打开 v5 根时以 registry version 错误退出，拒绝前后注册表哈希相同；新版可读历史 Deleted 状态，Prometheus 三项容量指标正确。再用新版重开，100 条文档前后共 200 次状态核对一致。该测试验证旧读者拒绝和新版重开，不将它当作完整降级迁移能力。

相关文档：[格式](format.md)、[运维](operations.md)、[指标](telemetry.md)、[中间件](middleware.md)。建议结合注册表占用比和租户周转率告警；仅减少活租户数量不能清除身份历史。

## 测试与运行验证

新增四项行为回归：并发预留/缩配额、自动后台线程恢复、接近满额的 v4 历史迁移及 UUID 保护、新格式容量拒绝无副作用。完整 **209 项测试通过**，Clippy（all-targets、failpoints、`-D warnings`）、格式检查和最终 release 构建均通过。

全部后端运行使用 OrbStack Ubuntu Linux aarch64，Cargo target 和测试 TMPDIR 都是原生 Btrfs。原探针副本有独立 target，关闭增量编译；仅追加测试，没有为复现修改生产逻辑。验证源码、构建及运行二进制哈希分别固定在 `validated-source.json`、`probe-source.json`、`binaries.log` 和来源记录中。

## 相同负载前后比较

使用未修改的原脚本：重租户 5000×4 KiB、轻租户 200×128 B；重写 40 批/秒×20 文档、轻写 20 次/秒，get 200、lookup 100、索引查询 50 次/秒。普通、混合及重启恢复分别为 10、45、60 秒。对照是上一轮已固定的审查二进制，修复版另存固定文件，运行时没有覆盖二进制或并行编译。

|---|---:|---:|---:|---:|
| 普通 | 4.808 → 4.927 | 8.309 → 7.920 | 9.666 → 11.044 | 20.079 → 20.084 |
| 混合 | 5.194 → 4.813 | 10.049 → 7.532 | 21.015 → 12.767 | 19.996 → 20.019 |
| 恢复 | 4.913 → 4.603 | 9.936 → 7.667 | 32.437 → 11.989 | 19.964 → 20.000 |

混合/恢复样本的尾延迟下降，普通短样本 P99 上升约 14.3%；不能称为全面性能改善，也不能把单次前后差异全部归因于本轮锁修改。没有为得到有利结果反复挑选轮次。各操作原始分位数、吞吐和样本保存在 [performance-comparison.json](../bench-results/special-stability-fix-20261107/performance-comparison.json)。

混合阶段有两次五项任务重叠采样、两份验证备份；恢复阶段有七次重叠采样、三份验证备份。主从在重启前后及最终阶段核对 31,200 个文档状态，离线恢复备份再核对 5000 个，共 **36,200 次状态核对、差异为零**。最终 GC 到期积压为零，业务测量最终错误为空；全流程有 262 次按原规则退避的 BUSY。重启至安全写入且副本追平为 72.9 ms，对照 66.7 ms。

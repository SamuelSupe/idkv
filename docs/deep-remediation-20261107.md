# 深度审查问题修复与验证（2026-11-07）

基线：`350603e51ac93df923c0246cc3926e9f70f2a796`。本轮处理深度审查确认的五项问题；[审查原始证据](../bench-results/deep-audit-20261107/summary.json)保持原样，修复后的证据存于 [deep-remediation-20261107](../bench-results/deep-remediation-20261107/)。

## 修复行为

| 问题 | 修复 | 回归保护 |
|---|---|---|
| F1 相同配额下源端已确认的大索引写入无法复制 | 去除重复 base64 解码计费；回放前的租户内存压力先刷盘重试一次，仍不能容纳或单页超过配额则转有界检查点初始化；全局、磁盘、L0 资源错误继续退避 | 19 MiB 配额、16 个覆盖索引、256 KiB HTTP 写入不调配额即可追平；超大日志页的 300 条已确认文档内容和修订号逐条一致 |
| F2 中断备份任务使满盘重启整个服务失败 | 启动只在内存归一化任务状态；工作者在副作用前持久化执行阶段，失败留在任务状态，不阻止服务启动；恢复/导入绝不自动重放 | 真实 ext4 卷填至 0 可用字节，携带 checkpointing 任务重启，在释放空间前读取全部已确认数据；原恢复后新写入在两次 BackupService 打开后保持 |
| F3 128 项维护队列固定从头填充造成饥饿 | 保留下一次续扫位置，队列满时优先处理未入队租户 | 160 租户在受限消费队列中全部获得维护；同一个 20 ms 慢任务场景对比 |
| F4 启动接受的 3 MiB 配额被复制同步的 4 倍阈值拒绝 | 默认配置、在线配额及副本更新共用两倍 memtable 加有效缓存的下限 | 3 MiB 配额、1 MiB memtable、零缓存下完成初始化后仍可增量同步 |
| F5 空闲租户每 100 ms 重扫全部 SST 和目录 | 不可变版本缓存层字节数和 L0 压力；每 tick 仅核对活跃 WAL；目录每 5 秒、文件发布后或占用达到 60% 配额时全面核对 | 无新增 WAL/合并 I/O 的 32/1024/4096 SST 同负载对比；验证活跃 WAL 增长、外部变化及高占用空间释放及时核对 |

这些修改不改变 WAL/Manifest 持久格式和复制协议版本。复制检查点仍受两个在途任务及每租户退避约束。检查点所需暂存空间和校验内存不足时仍可能无法恢复，不能将重新初始化视为绕过资源配额的保证。

## 运行验证

- 全量 151 项测试通过，Clippy 全目标（包含 failpoints）零警告，发布二进制构建通过。针对性测试另覆盖 43 个库测试、8 个备份集成测试及 28 个复制集成测试。
- 256 MiB ext4 loop 卷在 checkpointing 备份中断后填至 0 可用字节：服务重启到健康约 27.8 ms；未释放空间前，2000 条已确认记录的 query、multi_get、覆盖 Lookup 和 check 均通过。任务显示 interrupted；释放空间、关闭租户后原任务显式重试 completed，数据指纹不变。
- 真实 ENOSPC、WAL write EIO、WAL fsync EIO 三场景均通过，分别保护 2000 条故障前已确认数据。未知批次重启可见数量分别为 0/0/8，均按原重试上下文安全补齐至 2008 条；未知结果后的第二批写入没有泄漏。
- fsync 故障后的计划切换在故障持续时被 IO_ERROR 拒绝；恢复故障后完成切换，新主写入，两端位置、全部内容和修订号一致。

## 并行负载和数据核对

使用最终未加调度延迟的发布二进制，原生 Btrfs，重租户 20000 条 4 KiB 文档、轻租户 200 条 128 B 文档；30 秒基线、120 秒五路并行、30 秒重启后负载。并行测量期间未并行编译或运行其他压力测试。

| 阶段 | 轻租户写入 P99 ms | 重租户写入 P99 ms | Lookup 20 P99 ms | 最终操作错误 |
|---|---:|---:|---:|---:|
| 基线 30 秒 | 18.208 | 22.917 | 1.855 | 0 |
| 写入/合并/复制/备份/GC 并行 120 秒 | 15.798 | 18.934 | 1.307 | 0 |
| 双节点重启后 30 秒 | 13.039 | 18.029 | 1.117 | 0 |

并行阶段完成并校验 4 次备份，记录 13 个五路实际推进采样区间；主从中止后重启，到可写及复制追平约 104 ms，中断备份自动续作完成（最终持久任务 CRC 校验通过）。重启前、重启后及最终的主从两租户均按 ACK 日志核对完整文档和修订号，零缺失、零不一致；最终备份离线导入第三个 Store，20000 条记录再次核对一致。GC 收敛、过期资源版本拒绝及当前版本读取通过。驱动另记录 573 次 BUSY 准入重试（并行阶段 2 次、重启后阶段 571 次），表中零错误表示最终操作没有失败，不表示所有 HTTP 调用均无拒绝；重试和等待计入操作耗时。阶段延迟属于同一修复版本内的场景测量，受暖缓存等因素影响，不能将差值视为版本改进的因果结论。

原始 ACK 日志、逐操作压缩延迟样本、备份任务、恢复日志和源码/二进制 SHA-256 均归档。`validate-evidence.py` 会复算所有阶段 P50/P95/P99、核对样本数量及源码指纹，并检查零数据不一致和满盘/并行/调度验收条件。[结构化结果](../bench-results/deep-remediation-20261107/summary.json)。

## 同负载前后对比

160 租户、单维护工作者、每任务测试延迟 20 ms、预热 3.5 秒、观察 4 秒：基线完成 170 次任务，仅覆盖 129 个租户，31 个未被调度；修复后完成 169 次，覆盖全部 160 个，未调度为 0。该延迟仅加入隔离测试副本，未进入产品代码。

原生 Btrfs、release、每规模 7 个样本，纯 Engine 常规空闲维护：

| SST 文件数 | 基线中位耗时 ms | 修复后中位耗时 ms |
|---:|---:|---:|
| 32 | 0.015042 | 0.000292 |
| 1024 | 0.376375 | 0.000208 |
| 4096 | 1.683371 | 0.000208 |

以上是暖文件元数据下的常规 tick，不是端到端请求延迟或完整维护周期；每 5 秒以及高占用时的目录全面核对仍存在。样本中没有新增 WAL/合并 I/O，校验 scheduler.completed_jobs 和 compaction_write_bytes 不变。[完整样本和对比](../bench-results/deep-remediation-20261107/comparison.json)。

## 可复现方式

Linux OrbStack，Rust 1.90，原生 `/var/tmp`。功能测试使用 `cargo test --features failpoints -- --test-threads=1`，静态检查使用 `cargo clippy --all-targets --features failpoints -- -D warnings`。

`prepare-probes.py --root /var/tmp/idkv-probe-copy` 生成隔离源码副本，为调度测试添加与审查相同的测试专用 20 ms 延迟和计数，不改变生产源码。副本运行 `cargo test --lib fixed_full_maintenance_queue -- --nocapture`；空闲维护测量运行 `cargo test --release --test idle_probe -- --nocapture`。测试目录明确使用 Btrfs `/var/tmp`，避开 tmpfs。

满盘复现运行 `python3 bench-results/deep-remediation-20261107/pending-backup-full.py --binary /path/to/tenant-kv --root /var/tmp/idkv-pending-full`。驱动只创建自己的 256 MiB ext4 loop 卷，在 finally 中关闭进程、删除凭证并卸载释放 loop；需要免密 sudo。不会填满宿主机文件系统。

## 边界

本轮为 Linux VM 的有界资格验证，不包含 macOS 运行验证、真实设备故障/掉电和长期生产压测。WAL EIO 使用限定租户目录的系统调用注入，不能代表内核实际设备错误的全部语义。此前偶发 Store 锁 BUSY 的根因未在本轮定位，不因这五项修复宣称其已解决。已有的合并与刷盘共享锁、长任务不可抢占、异步复制 RPO 等约束保持。

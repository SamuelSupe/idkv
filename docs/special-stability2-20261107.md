# 满盘升级与恢复边界审查（2026-11-07）

在上一轮 209 项测试对应的未提交修复上继续检查注册表发布、配额、索引恢复与资源故障的交叉路径。本轮确认并修复一项启动可用性缺陷，以及一项格式探测契约错误。保留此前工作树全部改动；证据位于 [special-stability2-20261107](../bench-results/special-stability2-20261107/)。

## 已复现并修复

### 健康 v4 根在满盘时升级失败，整个服务无法启动

此前 Store::open 无条件把注册表版本改成 5，即使没有待恢复的生命周期状态，也要写临时注册表并同步发布。独立 256 MiB ext4 卷实际填满后，可用字节为零：同一根目录上的旧 v4 程序仍能启动并读全 100 条确认文档，上一轮修复版则报 `IO_ERROR: No space left on device (os error 28)` 并退出。释放填充文件后可以启动，确认数据未损坏；问题是整个节点的启动可用性。

现在健康 v4 根仅打开和读取时保持原文件，下一次必要的注册表发布才同时原子升级到 v5。创建、导入、删除、恢复、配额发布和首次复制配置共用格式升级及容量预检入口；没有在 I/O 错误后忽略必须完成的生命周期日志。新根直接使用 v5，v1–v3 启动兼容迁移和待恢复 journal 的必要写入仍需要可写空间。

新增回归在旧格式根中写入确认数据，检查只读启动保留原注册表字节，随后创建租户发布 v5，再重启核对数据。该测试在修复前失败；接近 16 MiB 的历史迁移及容量拒绝无副作用两项原回归继续通过。

### 能力接口及 OpenAPI 错报格式版本

实际 v5 根上的 `GET /v1/capabilities` 返回 storage_registry=4，OpenAPI 对应常量也是 4。运行探针及既有 HTTP 工作流中新增的契约核对均复现了不一致。该错误可能误导升级、离线恢复及兼容性检查，不是已经复现的数据损坏。

现在持久格式、能力接口和 OpenAPI 使用同一个版本常量 5。该字段描述程序写出的当前格式；健康旧根延后升级时，文件本身可能仍为 v4。这一语义已同步到格式、运维和中间件文档。

## 资源耗尽恢复实测

使用真实服务写入并确认 100 条文档，强制终止进程，移除可选 WAL-SYNC 优化水位以确保走未封口 WAL 恢复路径，再分别耗尽磁盘字节或 inode。所有卷均为独立 256 MiB ext4 loop 文件系统，未填满宿主盘，也未用 syscall 注入代替这两种资源耗尽。

原版两种场景均通过：只读启动后核对 100 条确认数据，写入返回 RESOURCE_EXHAUSTED；释放填充物后 close 并重开，恢复写入第 101 条，再强制重启核对全部数据。inode 场景创建 65,502 个空文件后剩余 inode 为零，同时仍有 227,368,960 字节可用，验证了仅观察可用字节不够。没有为这些已正常工作的路径增加生产逻辑。

## 最终验证

完整 **210 项测试通过**：lib 83、backup 11、DSL 7、engine 28、HTTP 13、identity 5、middleware 14、recovery 14、reliability 4、replication 31。相比上一轮新增一项延迟升级回归，并在现有 HTTP 工作流中扩展格式契约核对；两者均保留修复前失败日志。Clippy（all-targets、failpoints、`-D warnings`）、格式检查和 release 两个服务/恢复二进制构建通过。

固定最终服务二进制 SHA-256 为 `bd0f6b04d5e27a049893a8ff1456309f9ae25efa76b90a903c5046aa922622b9`。使用相同探针及负载、独立新卷重跑，结果如下；时间为单次小数据场景记录，不作为性能改善结论。

| 最终二进制场景 | 资源状态 | 启动时间 | 确认数据与恢复行为 |
|---|---|---:|---|
| v4 健康根升级、满盘启动 | 可用字节 0 | 27.4 ms | 注册表逐字不变，100 条可读；释放空间后创建租户发布 v5，重启仍一致 |
| 未封口 WAL、字节耗尽 | 可用字节 0，WAL 161,104 B | 27.3 ms | 100 条可读、写入被拒；释放空间并 close/重开后写入第 101 条，再崩溃重启后全部一致 |
| 未封口 WAL、inode 耗尽 | inode 0，尚余 227,389,440 B | 26.4 ms | 同样只读降级、资源释放后恢复写入及重启，全部一致 |

格式接口实测从“持久版本/能力接口/OpenAPI=5/4/4”变为 **5/5/5**。另用未修改的上一轮兼容探针，确认实际旧二进制拒绝 v5 根、拒绝前后注册表哈希不变，新程序重开可读历史 Deleted 状态，三项注册表容量指标正确。

最终运行的升级、两种资源恢复和兼容场景共 **1504 次文档状态核对，差异为零**，包含升级探针中 200 次旧程序的对照核对；这是重复检查次数，不是 1504 个不同文档。按 ACK 账本逐条核对键、修订号和载荷摘要。所有实验服务已停止，独立卷已卸载并解除 loop 绑定，填充物、镜像和认证文件已清理；归档不包含数据库或密钥文件。

## 范围与限制

后端运行均使用 OrbStack Ubuntu Linux aarch64；编译目录及测试 TMPDIR 为原生 Btrfs，资源故障使用其内独立 ext4 卷。基线与修复版使用固定二进制、独立数据根和相同探针；保存源码、脚本及二进制哈希。强制终止是进程崩溃测试，不能证明真实设备写回故障或掉电恢复。没有新增长期 soak、真实 S3 或大规模部署验证，也没有提交或推送 GitHub。

本报告替代上一轮报告中“所有 v4 根在打开时立即升级”的当前行为描述；上一轮测量仍作为当时版本的历史证据保留。
